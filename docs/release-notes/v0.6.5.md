# Dockingbird v0.6.5

The nineteenth tagged version of Dockingbird. It brings the Dockingbird GUI 0.1.11, which adds, renames and forgets a host from its sidebar, and the core behind it: `dockingbird fleet hosts set`, `rename` and `forget`, and a home that holds only a hand-written `hosts.toml` claimed instead of refused. The fleet now places a swarm in the pool's host order, fetches a swarm's branch into its home itself and keeps sampling every host on time however full its homes' inboxes grow. A fleet database made by an earlier build is upgraded with migration 0005 before any install of this release starts (the Deploy paragraph below).

## Install or update

```bash
UV_INDEX_ZEUSFYI_USERNAME=license UV_INDEX_ZEUSFYI_PASSWORD="$(pbpaste)" uv tool install dockingbird --index zeusfyi=https://license.zeusfyi.com/simple/
dockingbird update
```

With a license key, install from Zeusfyi's release index: copy the key from your purchase email, then run the first line (the operator guide's [Install](../operator-guide.md#install) gives the Linux form and `dockingbird license activate`); an installed Dockingbird takes this release with `dockingbird update` alone. `dockingbird update` installs the Dockingbird GUI 0.1.11 in place of 0.1.10, the version v0.6.4 ran; a GUI that is already open keeps its version until its server stops. An update made while agents run is staged and taken once the last agent ends. `dockingbird --version` prints `0.6.5`. The GUI's repository is private, so git must reach it with your GitHub SSH key.

## What v0.6.5 changes

Deploy: the fleet now starts each agent of a swarm with its swarm, role and workload (`--swarm`, `--role`, `--engine`), so install this release on every engine home before its host's worker, in the order `dockingbird update` already uses on each host, and upgrade the fleet database as the operator guide says ([The fleet scheduler](../operator-guide.md#the-fleet-scheduler), the sentence beginning "A fleet database made by an earlier build is upgraded instead") before the workers restart: a worker of this release on a database without migration 0003 fails at its first read of the assignments, on `reviewer_told` and `tester_told`. A home still at an earlier release refuses each start with `dockingbird start: '--swarm' is not an option.`, and the fleet holds the workload with that refusal's id as the reason, `UNKNOWN_OPTION` (`dockingbird fleet why ID` says `ID is held: UNKNOWN_OPTION`): update that home, then `dockingbird fleet release ID`.

A role of a swarm definition may now name `min = 0` when it neither reviews nor tests, so `dockingbird fleet retire` can let its last agent go once it is done, and `fleet replace` now recovers an agent whose last turn failed or whose process crashed, the way you would by hand (stop, then pick up); `fleet retire` of such an agent waits until nothing is open in its inbox.

Dockingbird now adds another computer for you: `dockingbird fleet hosts set NAME --ssh DEST` (or `--gcloud VM --zone ZONE --project PROJECT`) reaches it, reads its Docker and its Dockingbird homes, and writes it into `hosts.toml` only when that worked; when it didn't, nothing is saved and the message says what to try. `dockingbird fleet hosts rename OLD NEW` and `dockingbird fleet hosts forget NAME` edit the file too, and the GUI's host headings gain the same three. Your own computer is `local` in every fleet line and in the GUI; `local` can't be a host's name. A host has one name across your file, the fleet pool and swarm definitions, so a rename of a host the pool holds is refused until it is removed there. The customer repository `zeus-fyi/dockingbird-sdk` is filled by an export of the product's own documents.

A start refused because the name belongs to the other tool's kept copy or ended agent, and a `--new` refused because the name's copy is kept, now also give the command that deletes that agent's copy, results and history and frees the name, `dockingbird clean NAME --yes`, beside the pick-up; the pick-up stays the one step `dockingbird ui` offers.

The Dockingbird GUI 0.1.11 adds, renames and forgets a host from its sidebar, with `dockingbird fleet hosts set`, `rename` and `forget`. A right click on the DOCKINGBIRD heading opens its menu, "add a host…", whose questions ask over ssh or a gcloud VM, then the ssh destination (or the VM's name, zone and project), the host's name in the sidebar (a name from the destination is offered when it is free) and, over ssh, PATH for docker there and the docker host URL there, each optional. A right click on a fleet host's heading opens its menu: "rename…" asks for the new name with the old one offered, and "forget…" forgets the host once you type `y`; `local`, this computer, has neither. The Dockingbird layer's `h` asks the same from the keyboard. While a change runs, the command bar's note says so, then gives the command's answer; a tap on a note the bar cuts short opens it whole. The DOCKINGBIRD heading now shows as soon as `dockingbird fleet hosts` answers, with this computer alone too, so a first host can be added on a fresh install.

While any of the GUI's Dockingbird forms is open (these questions, a start's or a delete's), a drag over a pane still selects and copies, and the copy view still opens, so a destination or a name can be copied from a pane into the question.

Every right-click menu's items now sit one cell in from its border, the host menus, an agent's and the tabs' and panes' alike, and a popup drawn over bold text no longer paints its border bold, which a terminal without font fallback showed as missing-glyph boxes.

A swarm definition may now leave out its `[placement]`: the swarm then goes to every pool host that takes swarms, in the pool's order (`--rank N` on `dockingbird fleet hosts add` or `dockingbird fleet hosts policy NAME`, 1 first), each in a home the fleet chooses. The fleet now places a swarm on the first host of its placement's order that has room and green lines, however full that host already is, and passes over a host whose home has no clone of the swarm's repository, so the next host in the order takes the swarm in the same pass; `dockingbird fleet why ID` names the home it passed over. When a home's `[[home]]` in `hosts.toml` names `clones`, a folder, the worker fetches the swarm's branch itself into a clone of its own there, made from the home's clone of the repository on any branch, so nobody links a branch into a home by hand. When the worker cannot, `fleet why ID` names the home with no clone to fetch from, or gives git's own last line for a fetch that failed (is the branch pushed? can the host's git reach the remote?); fix it, then run `dockingbird fleet release ID`.

Deploy: upgrade the fleet database before any install of this release starts, as the operator guide says ([The fleet scheduler](../operator-guide.md#the-fleet-scheduler), the sentence beginning "A fleet database made by an earlier build is upgraded instead"): migration 0005 adds each host's `rank`, which this release's admitter, `fleet submit` and `fleet queue` read.

The fleet worker now samples its host every 30 seconds whatever its homes' inboxes hold: a home with thousands of open rows made every sample late, so the host read `idle_millicores unread` and the fleet admitted nothing to it. The homes' inbox and checkout reads now run on a thread of their own. The engine also marks read the open status rows of its own agents once they are gone (retired, died, or their swarm done or cancelled), up to a hundred per home every 30 seconds, so an engine home's inbox no longer grows with every finished swarm; a question from such an agent, and any row from an agent the engine did not start, stays open.

A Dockingbird home you set up by hand, with only a `hosts.toml` or a `fleet.toml` in it (or both) and nothing else Dockingbird didn't make, is now used as Dockingbird's own: `dockingbird fleet hosts set`, `rename` and `forget`, and every other command, no longer refuse it as a folder with files Dockingbird didn't make (`HOME_NOT_EMPTY`). A folder holding anything else is still refused, and the message still lists what it found.

A plain `dockingbird send NAME TEXT` now asks the coordinator for NAME's open questions alone, so it answers the one question or starts a task however many rows your inbox holds; the refusal that said too many deliveries were pending is gone. An agent's turn reports no longer pile up in your inbox: each new `turn N` row from an agent replaces its previous one, and each `turn N failed` row its previous failed one, so you see the newest of each; every earlier report stays readable by its id (from `--json inbox`, `wait` or `dockingbird native message inbox --state withdrawn`) and in its thread. The coordinator's `message inbox` can list an inbox by sender and by kind, and a message sent with `supersedes_id` withdraws the message it replaces.
