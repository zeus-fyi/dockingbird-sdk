# Troubleshooting index: the fleet, swarms and the work queue

Find a message id below to see when Dockingbird prints that message. Add `--verbose` to a command and every message also shows its id. With `--json`, each envelope carries the id as its `id` key. Each id links to its entry in the [catalogue](../troubleshooting.md): the message text, the next step and the exit status. This page holds the 210 ids about hosts, the fleet scheduler, the control plane, swarms and the work queue.

## Swarm inspection

| Id | When it appears |
|---|---|
| [`INSPECT_CAPABILITIES`](../troubleshooting.md#inspect_capabilities) | You ran `dockingbird inspect capabilities`, the first read the Dockingbird GUI's Swarms tab makes: the line says what this Dockingbird can show there. With `--json` the GUI reads the same facts. |
| [`INSPECT_INSTANCES`](../troubleshooting.md#inspect_instances) | You ran `dockingbird inspect instances`: one entry per Dockingbird home on this computer, as `dockingbird homes` lists them, each with whether its Dockingbird runs (`running`), is stopped, runs another version than this one (`unreadable`) or has lost its folder (`gone`), and how many of its agents run. |
| [`INSPECT_SWARM`](../troubleshooting.md#inspect_swarm) | You ran `dockingbird inspect swarm`: this home's agents and, for every pair of them, whether one may message the other, decided as a real send is decided; nothing is sent. The line counts the agents and the swarms they were started into; with `--swarm NAME`, only that swarm's agents and the pairs among them. With Dockingbird not set up or off, the line `status` prints for that state comes instead. |
| [`SWARM_UNKNOWN`](../troubleshooting.md#swarm_unknown) | You ran `dockingbird inspect swarm --swarm NAME` and no agent of this home is in a swarm of that name: none was started with `--swarm NAME`, or each has left it. Nothing of the home is shown. |
| [`INSPECT_NOT_SUPPORTED`](../troubleshooting.md#inspect_not_supported) | You ran `dockingbird inspect swarm` or `dockingbird inspect config --agent NAME` in a home whose Dockingbird runs a version from before inspection, or one so old it names no version, so it can't answer: nothing was read. The line names its version and the version inspection exists from; `dockingbird update` in that home updates it, once its agents end if they run. |
| [`INSPECT_SCHEMA_NEWER`](../troubleshooting.md#inspect_schema_newer) | You ran `dockingbird inspect`, here or with `--host NAME`, and the Dockingbird that answered is newer: its answer is in a form this Dockingbird can't read, so nothing of it is shown. The line names both Dockingbirds and both forms; `dockingbird update` brings this one up to date. |
| [`SWARM_NAME_INVALID`](../troubleshooting.md#swarm_name_invalid) | You gave `--swarm` a name no swarm can have. A swarm's name follows the rule of an agent's name: lowercase letters, digits and `-`, a letter or a digit first. |
| [`INSPECT_CONFIG`](../troubleshooting.md#inspect_config) | You ran `dockingbird inspect config`: alone, this home's own settings; with `--agent NAME`, the settings that agent runs with, its model and effort, its limits, its tool versions and the names of its environment variables. An environment value that is not a tool's is never shown. A name of no agent is refused as `status NAME` refuses it. |
| [`INSPECT_SECRET_REFUSED`](../troubleshooting.md#inspect_secret_refused) | You ran `dockingbird inspect config --agent NAME` and the agent's settings hold a secret, so Dockingbird shows none of them rather than part. Take the secret out of the agent's config, or leave those settings unread. |

## The swarm command

| Id | When it appears |
|---|---|
| [`SWARM_ROW`](../troubleshooting.md#swarm_row) | You ran `dockingbird swarm list`: one line per swarm of this home, with how many agents are in it and whether you made it (`hand`) or the fleet runs it (`engine`). With `--json`, each member's role and the members that review and test its work come too. |
| [`SWARM_NONE`](../troubleshooting.md#swarm_none) | You ran `dockingbird swarm list` and no agent of this home is in a swarm: none was started with `--swarm`, or each one left its swarm. `dockingbird start --swarm NAME` starts an agent in one, and `dockingbird swarm add` puts an agent there. |
| [`SWARM_ADDED`](../troubleshooting.md#swarm_added) | You ran `dockingbird swarm add NAME --swarm SWARM`: the agent is now in that swarm, with the role you gave, and out of any swarm it was in before. Only this home's record changed: the agent wasn't started, stopped or told. |
| [`SWARM_REMOVED`](../troubleshooting.md#swarm_removed) | You ran `dockingbird swarm remove NAME`: the agent is in no swarm now, and no member is reviewed or tested by it any more. The agent itself keeps running; `dockingbird stop NAME` stops it. |
| [`SWARM_ROLE_SET`](../troubleshooting.md#swarm_role_set) | You ran `dockingbird swarm role NAME --role ROLE`: the agent's role in its swarm is the one you gave. Only this home's record changed. |
| [`SWARM_ASSIGNED`](../troubleshooting.md#swarm_assigned) | You ran `dockingbird swarm assign NAME`: the line names the members that review and test the agent's work now, `none` where none does. Only this home's record changed: no agent was told. |
| [`SWARM_NOT_A_MEMBER`](../troubleshooting.md#swarm_not_a_member) | You ran `dockingbird swarm remove`, `role` or `assign` for an agent that is in no swarm, so there was nothing to change. Put it in one first with `dockingbird swarm add NAME --swarm SWARM`. |
| [`SWARM_ENGINE_OWNED`](../troubleshooting.md#swarm_engine_owned) | You tried to change a swarm the fleet runs with `dockingbird swarm`. The fleet keeps its own list of who is in it and tells its agents of every change, so change it with the `dockingbird fleet` command the line names. An agent's role there is the one the fleet started it for: retire it and add one of the other role. |
| [`SWARM_ASSIGNEE_IS_SELF`](../troubleshooting.md#swarm_assignee_is_self) | You ran `dockingbird swarm assign NAME` and named the agent itself as its own reviewer or tester. Name another member of its swarm. |
| [`SWARM_ASSIGNEE_NOT_A_MEMBER`](../troubleshooting.md#swarm_assignee_not_a_member) | You ran `dockingbird swarm assign NAME` and named a reviewer or tester that is not in the agent's swarm. Put that agent in the swarm first with `dockingbird swarm add`, or name a member. |
| [`SWARM_NEEDS_SWARM`](../troubleshooting.md#swarm_needs_swarm) | You ran `dockingbird swarm add NAME` without `--swarm SWARM`, the swarm to put the agent in. Nothing changed. |
| [`SWARM_NEEDS_ROLE`](../troubleshooting.md#swarm_needs_role) | You ran `dockingbird swarm role NAME` without `--role ROLE`, the agent's new role. Nothing changed. |
| [`SWARM_ROLE_INVALID`](../troubleshooting.md#swarm_role_invalid) | You gave `--role` a word that can't be a role: a role is lowercase letters, digits and `-`, as an agent's name is. Nothing changed. |
| [`SWARM_ASSIGN_NEEDS_OPTION`](../troubleshooting.md#swarm_assign_needs_option) | You ran `dockingbird swarm assign NAME` with none of `--reviewer`, `--tester`, `--no-reviewer` and `--no-tester`, so there was nothing to change. |
| [`SWARM_ASSIGN_CONFLICT`](../troubleshooting.md#swarm_assign_conflict) | You gave `dockingbird swarm assign` a reviewer and `--no-reviewer`, or a tester and `--no-tester`, at once. Give one of the two. |
| [`SWARM_ASSIGNEE_INVALID`](../troubleshooting.md#swarm_assignee_invalid) | You gave `--reviewer` or `--tester` a word that can't be an agent's name: a name is lowercase letters, digits and `-`. Nothing changed. |
| [`SWARM_ENGINE_INVALID`](../troubleshooting.md#swarm_engine_invalid) | `dockingbird swarm` was given an `--engine` value that is not the id of a fleet workload. The fleet's own worker gives that option; you never need to type it. |

## The fleet probe

| Id | When it appears |
|---|---|
| [`FLEET_PROBE`](../troubleshooting.md#fleet_probe) | You ran `dockingbird fleet probe` on a Mac. It reads this Mac's cores and memory, its load against its line, its CPU, memory, swap and GPU, Docker's VM, containers and networks, then how much CPU and memory each category of the load uses, with how many containers or processes it counted. A figure it couldn't read says `unread`. It starts, stops and changes nothing; with `--json` it prints every figure by name on one line, for scripts. |
| [`FLEET_PROBE_CATEGORY`](../troubleshooting.md#fleet_probe_category) | One row of the load by category that `dockingbird fleet probe` prints: the category, its CPU in percent of one core (400% is four cores), the memory it uses and how many containers or processes it counted. A category with nothing in it shows 0. |
| [`FLEET_PROBE_UNREAD`](../troubleshooting.md#fleet_probe_unread) | `dockingbird fleet probe` couldn't read part of what it reads, so it names each such part and why: Docker isn't there or didn't answer, a command took too long or printed too much, a command's output had another shape than the probe reads, the Mac has no graphics accelerator to read, or a command failed. The rest of the screen is what it did read, and the command still ends 0. |
| [`FLEET_PROBE_NOT_MACOS`](../troubleshooting.md#fleet_probe_not_macos) | You ran `dockingbird fleet probe` on a computer that isn't a Mac. It reads the programs of macOS only, so it stops before it runs anything. |
| [`FLEET_PROBE_NO_SYSCTL`](../troubleshooting.md#fleet_probe_no_sysctl) | You ran `dockingbird fleet probe` and the first thing it reads, this Mac's cores, memory, load and swap from `sysctl`, failed: it took too long, printed too much or something the probe doesn't read, or failed outright. Without the cores no other figure has its scale, so the probe stops; the word in parentheses says which. |

## The fleet's home read

| Id | When it appears |
|---|---|
| [`FLEET_HOME`](../troubleshooting.md#fleet_home) | You ran `dockingbird fleet read-home`. It reads the Dockingbird home it runs under (the one `DOCKINGBIRD_HOME` names, else the default one) through that home's own `dockingbird status` and, only when Dockingbird is ready there, `dockingbird inbox --all`, then prints the home's folder, its version and whether it is ready, how many agents it has and how many are in each state, what waits in its inbox, and its open questions with the oldest one's age. A figure it couldn't read says `unread`. It starts and stops nothing itself; with `--json` it prints the whole reading on one line, for scripts: every agent with its tool, state, model and effort, and every inbox row. |
| [`FLEET_HOME_STATE`](../troubleshooting.md#fleet_home_state) | One row of the agents by state that `dockingbird fleet read-home` prints: a state, such as working, idle or stopped, and how many of the home's agents are in it. A state no agent is in has no row. |
| [`FLEET_HOME_UNREAD`](../troubleshooting.md#fleet_home_unread) | `dockingbird fleet read-home` couldn't read part of the home, so it names each such part and why: it reads the inbox only while Dockingbird is ready in that home (`not-ready`), and a read that took too long, printed too much or something read-home doesn't read, or failed, says so. The rest of the screen is what it did read, and the command still ends 0. |
| [`FLEET_HOME_NO_STATUS`](../troubleshooting.md#fleet_home_no_status) | You ran `dockingbird fleet read-home` and the first thing it reads, the home's own `dockingbird status`, failed: it took too long, printed too much or something read-home doesn't read, or failed outright, or the program the home records (`program`, written by each start and update) is not an executable file of yours that nobody else can write (`program-invalid`), so nothing ran. The agents and whether the home is ready come from it, so read-home stops without reading the inbox; the word in parentheses says which. |
| [`FLEET_HOME_NO_DISK`](../troubleshooting.md#fleet_home_no_disk) | You ran `dockingbird fleet read-home` with `--disk`. Only `dockingbird fleet probe` reads Docker's disk use, so read-home stops before it reads anything. |

## The fleet's metrics

| Id | When it appears |
|---|---|
| [`FLEET_SCRAPE`](../troubleshooting.md#fleet_scrape) | You ran `dockingbird fleet scrape --json`. It reads the Dockingbird home it runs under through that home's own `dockingbird status`, as `dockingbird fleet read-home` does, and renders each running agent's figures in the Prometheus text format, the same text the agent's container serves, under labels that name the home, the agent, its run and its tool. The line names the home, how many agents it has and how many it rendered; the JSON carries every agent with its labels, or none for an agent that isn't running, and the text a line each. Without `--json` the screen is that text alone. |
| [`FLEET_SCRAPE_NO_STATUS`](../troubleshooting.md#fleet_scrape_no_status) | You ran `dockingbird fleet scrape` and it had nothing to render: the home's own `dockingbird status` took too long, printed too much or something scrape doesn't read, or failed outright, or Dockingbird isn't ready in that home (`not-ready`: the home isn't set up, or Dockingbird there is off, of another version or slow to answer), so no agent's figures are current, or the program the home records (`program`, written by each start and update) is not an executable file of yours that nobody else can write (`program-invalid`), so nothing ran. The word in parentheses says which; nothing is printed on stdout. |
| [`FLEET_SCRAPE_NO_DISK`](../troubleshooting.md#fleet_scrape_no_disk) | You ran `dockingbird fleet scrape` with `--disk`. Only `dockingbird fleet probe` reads Docker's disk use, so scrape stops before it reads anything. |

## Every agent on every host

| Id | When it appears |
|---|---|
| [`FLEET_HOSTS_ROW`](../troubleshooting.md#fleet_hosts_row) | One line of `dockingbird fleet hosts` for each host `hosts.toml` in your Dockingbird folder names, in the file's order: its name, how it is reached (`ssh`, `gcloud` or `local`) and the ssh destination, the VM or, for a host with `local = true`, this computer. `dockingbird fleet agents --host NAME` reads that host's agents. |
| [`FLEET_HOSTS_NONE`](../troubleshooting.md#fleet_hosts_none) | You ran `dockingbird fleet hosts` and `hosts.toml` in your Dockingbird folder names no host, or isn't there, so `dockingbird fleet agents` reads `local`, this computer, alone. `dockingbird fleet hosts set NAME --ssh DEST` adds another host once it answers, or `--gcloud VM --zone ZONE --project PROJECT` in place of `--ssh` for a Compute Engine VM. |
| [`FLEET_HOSTS_FILE_INVALID`](../troubleshooting.md#fleet_hosts_file_invalid) | `hosts.toml` in your Dockingbird folder, which names the other hosts `dockingbird fleet` reads, has a mistake: a value that isn't right or is missing, a key it doesn't take, a host with more than one of `ssh`, `gcloud` and `local = true`, or none of them, two hosts with one name, a host named `local`, the name every fleet line gives this computer, text that isn't TOML, or a link, a folder or a file that isn't yours in its place. The message names the file and, where it can, the place, such as `host[2].ssh`, never a value. No host is read until it is fixed. `dockingbird fleet hosts set` refuses the same way, writing nothing, when the entry it would write breaks one of these rules. |
| [`FLEET_HOST_UNKNOWN`](../troubleshooting.md#fleet_host_unknown) | You gave `dockingbird fleet agents`, `dockingbird fleet attach` or `dockingbird fleet update` a `--host` that `hosts.toml` in your Dockingbird folder doesn't name, `dockingbird fleet update` would move a host of the pool that it doesn't name, or you gave `dockingbird fleet hosts rename` or `forget` a name it doesn't have. This computer, when it is a host of the pool, is named by a `[[host]]` with `local = true`. `dockingbird fleet hosts` lists the hosts it names, which shows a mistyped name; `dockingbird fleet hosts set NAME --ssh DEST` adds a host it lacks. |

## dockingbird fleet update

| Id | When it appears |
|---|---|
| [`FLEET_UPDATE_HOST`](../troubleshooting.md#fleet_update_host) | You ran `dockingbird fleet update`, which moves the fleet's hosts to one Dockingbird release, one host after another in the pool's order. It says each step as it starts on a host: installing the release into the host's `installs` folder, updating each Dockingbird home the host's worker serves, moving the host's services to the release and restarting them, and waiting for its worker to run the release; then that the host runs it. A host whose worker already runs the release is skipped, and the line says so. |
| [`FLEET_UPDATE_DONE`](../troubleshooting.md#fleet_update_done) | The last line of `dockingbird fleet update`: every host of the run, the ones it skipped too, runs the release. Each host's Dockingbird homes finish moving to it on their own; `dockingbird --home NAME status` shows each. When the fleet's pool has no host, the line says so and nothing was updated; `dockingbird fleet hosts add` adds one. |
| [`FLEET_UPDATE_NO_REPOINT`](../troubleshooting.md#fleet_update_no_repoint) | You ran `dockingbird fleet update`, and a host it would move has no `repoint` line in its `[[host]]` table of `hosts.toml` in your Dockingbird folder: the command that restarts that host's Dockingbird services and returns without waiting for them to stop, such as `launchctl kickstart -k gui/$UID/<label>` on a Mac or `systemctl --user restart --no-block <unit>` on Linux. Nothing ran on any host. |
| [`FLEET_UPDATE_NO_RELEASE`](../troubleshooting.md#fleet_update_no_release) | You gave `dockingbird fleet update --release V` a version that Dockingbird's source has no release of, such as a mistyped one. Nothing ran on any host. Without `--release`, the command moves the fleet to this program's own release. |
| [`FLEET_UPDATE_SOURCE_UNREAD`](../troubleshooting.md#fleet_update_source_unread) | You ran `dockingbird fleet update`, and Dockingbird couldn't read the versions Dockingbird's source lists, which name the release's commit: the network failed, or git on this computer can't read the source repository the message names. Nothing ran on any host. Once both work, run `dockingbird fleet update` again. |
| [`FLEET_UPDATE_NO_WORKER`](../troubleshooting.md#fleet_update_no_worker) | You ran `dockingbird fleet update`, and a host it would move has no Dockingbird worker that reported within the time the message names, runs a worker too old to say which Dockingbird homes it serves, one you update by hand once as the operator guide says, or has a worker that hasn't said yet which homes it serves, as right after the worker starts. Nothing ran on any host. |
| [`FLEET_UPDATE_HOST_TIMEOUT`](../troubleshooting.md#fleet_update_host_timeout) | You ran `dockingbird fleet update`, and after a host's services were restarted its worker didn't report running the release within the time the message names: its services didn't come up, or came up on another release. The update stopped there: the hosts before it run the release, and the hosts after it were left as they are. Once its worker runs the release, `dockingbird fleet update --release V` goes on, skipping every host that runs it. |
| [`FLEET_UPDATE_HOST_FAILED`](../troubleshooting.md#fleet_update_host_failed) | You ran `dockingbird fleet update`, and a step failed on a host: installing the release, updating one of its Dockingbird homes, or moving its services to the release and restarting them, a link that couldn't be moved among them. The message names the host and gives the host's own words. The update stopped there; the hosts after it were left as they are. A re-run skips every host that runs the release and repeats the rest. |
| [`FLEET_OPTION_NOT_HERE`](../troubleshooting.md#fleet_option_not_here) | You gave a `dockingbird fleet` action an option that belongs to another one: `--disk` is the probe's, `--host` is for `agents`, `attach` and `update`, `--release` for `update`, `--container` for `attach`, and `attach` takes no `--json`. Nothing is read. |
| [`FLEET_HOST_ROW`](../troubleshooting.md#fleet_host_row) | The first line of `dockingbird fleet agents`: how many agents run on `local`, this computer, or on the host `--host` names, and in how many Dockingbird homes, read from that computer's Docker whatever Dockingbird version each home runs. `dockingbird fleet hosts set` adds a host and shows its lines the same way. |
| [`FLEET_HOME_ROW`](../troubleshooting.md#fleet_home_row) | One Dockingbird home that `dockingbird fleet agents` found on the host: its folder, or `folder not known` when Docker doesn't show it, its version, whether it is running, and how many of its agents run. |
| [`FLEET_AGENT_ROW`](../troubleshooting.md#fleet_agent_row) | One agent that `dockingbird fleet agents` found running on the host: its name, `bus` or `terminal`, and whether it has a screen to open; an agent with no screen opens as its log with a line to send it a message. |
| [`FLEET_SWARM_ROW`](../troubleshooting.md#fleet_swarm_row) | One swarm with an agent running on the host that `dockingbird fleet agents` found: how many of its agents run and how many wait to start, and its project, priority and state from the fleet store; `no definition` when the store doesn't know the swarm, such as one started by hand, or couldn't be reached in time. |
| [`FLEET_ROWS_SKIPPED`](../troubleshooting.md#fleet_rows_skipped) | `dockingbird fleet agents`, or `dockingbird fleet hosts set` as it adds a host, found rows in the host's Docker listing that it couldn't read, such as a container of another shape or an agent that stopped while it read, and says how many; the host is `local` for this computer. | [`FLEET_HOST_NOT_READ`](../troubleshooting.md#fleet_host_not_read) | `dockingbird fleet agents` couldn't read the host, or `local`, this computer's own Docker: ssh or gcloud couldn't reach it, its Docker failed or took too long, it printed something else than Docker's listings, or this computer has no Docker or no `gcloud`. | [`FLEET_HOSTS_SET`](../troubleshooting.md#fleet_hosts_set) | You ran `dockingbird fleet hosts set` and the host answered: its Docker and its Dockingbird homes were read and shown as `dockingbird fleet agents --host NAME` shows them, and its entry was written at the end of `hosts.toml` in your Dockingbird folder. | [`FLEET_HOSTS_UPDATED`](../troubleshooting.md#fleet_hosts_updated) | You ran `dockingbird fleet hosts set` with a name `hosts.toml` already gives a host, and the host answered: its route is replaced, and its `[[host.home]]` tables, its place in the file and a gcloud program you named for it by hand while it stays on gcloud are kept. |---|---|
| [`RPC_PEER_HOST_MISMATCH`](../troubleshooting.md#rpc_peer_host_mismatch) | A fleet call from this computer was refused because its credential belongs to another computer: a bundle made for one computer was used on another. Leave the fleet here and join again with a bundle made for this computer. |
| [`RPC_FRAME_INVALID`](../troubleshooting.md#rpc_frame_invalid) | A fleet call from this computer carried a message the control plane's relay doesn't read (a header missing or wrong). The two computers run different Dockingbird code; update the one that is behind. |
| [`NODE_VERSION_MISMATCH`](../troubleshooting.md#node_version_mismatch) | A fleet call found the control plane at another Dockingbird version than this computer's. | [`NODE_ROUTE_REFUSED`](../troubleshooting.md#node_route_refused) | A command on this computer made a fleet call the control plane doesn't allow a joined computer to make. Dockingbird's own commands never do; run the command again with `--verbose` and report it. |
| [`NODE_SESSION_ELSEWHERE`](../troubleshooting.md#node_session_elsewhere) | You started an agent whose fleet name is live from another computer (the one the message names), so this computer could not take it over. Stop it there first, or use another name. |

| [`NODE_ALREADY_ENROLLED`](../troubleshooting.md#node_already_enrolled) | You ran `dockingbird node join` with a bundle the control plane already enrolled a computer with. Each bundle joins once; on the control plane's home, remove the host and make a new bundle, then join with it. |
| [`CP_ALREADY_INITIALIZED`](../troubleshooting.md#cp_already_initialized) | You ran `dockingbird cp init` on a home that is already the control plane. Nothing changed; `dockingbird cp status` lists the computers in the fleet. |
