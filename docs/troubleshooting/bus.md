# Troubleshooting index: the bus

Find a message id below to see when Dockingbird prints that message. Add `--verbose` to a command and every message also shows its id. With `--json`, each envelope carries the id as its `id` key. Each id links to its entry in the [catalogue](../troubleshooting.md): the message text, the next step and the exit status. This page holds the 70 ids about tasks on the bus: send, wait, the inbox, read, questions and results.

## Docker, platform and setup

| Id | When it appears |
|---|---|
| [`INSTRUCTIONS_UNREADABLE`](../troubleshooting.md#instructions_unreadable) | Your rules file for Claude or Codex (in Dockingbird's `instructions` folder) can't be read: it isn't a plain text file, is too large, or is a link. |
| [`INSTRUCTIONS_TIMED_OUT`](../troubleshooting.md#instructions_timed_out) | You started an agent, and saving your rules file for Claude or Codex for it took longer than Dockingbird waits, usually because the computer was busy. No agent started. When Docker couldn't remove the step's container, the message names it. |

The agent's tool reads this line and asks again a moment later, and you see the question then. |

## Agents: ending

| Id | When it appears |
|---|---|
| [`DELIVERY_HELD_IN_SCREEN`](../troubleshooting.md#delivery_held_in_screen) | A message you or another agent sent has waited a while at the agent's screen: someone is typing in it, its tool hasn't started yet or is still working, or its screen is still drawing. It says so once, in the message's own thread, with how long the message has waited and which of these keeps it waiting, and the message goes in once that is over: the typing sent, the tool at its prompt and done, its screen still. Typing left unsent is cleared by Dockingbird once that has been said and no key has come for five minutes, which it says once more; a box taller than the screen, or a menu left open, can keep text the clear does not reach, and the message's turn is then told as failed. When the screen took bytes, the line says what kind, when, how many bytes that read had and the bytes that decided it in hex, so a key can be told from a terminal's answer. |
| [`TURN_UNSIGNALLED`](../troubleshooting.md#turn_unsignalled) | A message you or another agent sent went into a Codex agent's screen, and no sign came that its work was done: nothing was drawn after it for the time a tool takes to show it took a message, or what was drawn then stopped for that long. Dockingbird stops waiting for that one message and says which, in its own thread; the agent goes on, and sits idle when it has nothing to do. |
| [`TURN_COMPLETION_UNSEEN`](../troubleshooting.md#turn_completion_unseen) | A message went into a Codex agent's screen and the agent took it: its screen showed it at work. Then its screen stayed still with no sign that the work was done, as when the agent asks a question of its own and waits for the answer. Dockingbird stops waiting for that one message and says so in its own thread; the message counts as read and is not told as failed. Look at the agent's screen: it may be waiting for an answer. |
| [`TURN_INTERRUPTED_BY_OWNER`](../troubleshooting.md#turn_interrupted_by_owner) | While an agent worked on a message, the owner pressed Esc or Ctrl-C in its screen, and the next thing it worked on was a line of the owner's own: one they sent while it worked, or right after the key. The message's turn ended there, so this summary carries no result: what the agent answered next was the owner's line, and stays with it. Whatever the agent had already sent or done for the message stands. |
| [`TURN_DEADLINE_IN_OWNERS_TURN`](../troubleshooting.md#turn_deadline_in_owners_turn) | While an agent worked on a message, the owner pressed Esc or Ctrl-C in its screen, and the agent then worked on a turn of the owner's own there. The message's time ran out while that turn ran. Dockingbird ends a message's turn at its deadline by pressing Esc, but never presses a key in the owner's own turn, so it pressed none: the message's turn ended there, with no result, and the owner's turn went on. Whatever the agent had already sent or done for the message stands. |

## Configs, trust and the agents' own commands

| Id | When it appears |
|---|---|
| [`INSTRUCTION_FILE_REFUSED`](../troubleshooting.md#instruction_file_refused) | You started an agent with `--agent-md` or `--claude-md` (or picked up one that started with it), and the file is missing, a link, not a regular file, larger than the limit, not UTF-8, or has a Dockingbird credential. Nothing was started. |
| [`INSTRUCTION_FILE_UNREAD`](../troubleshooting.md#instruction_file_unread) | You started an agent with `--agent-md` or `--claude-md` where its tool would not read that file at startup: a scratch folder, Codex with `--claude-md`, a config's command whose repo settings don't load for Claude (its `repo_settings` is off, or the checkout isn't trusted), or Codex in a trusted checkout whose branch has `AGENTS.override.md`. Nothing was started. |
| [`INSTRUCTION_FILE_CARRIED`](../troubleshooting.md#instruction_file_carried) | You picked up an agent with `--as`, and it started with `--agent-md` or `--claude-md`: an agent keeps its instruction files for its whole life, so this start reads the same file again from the same path. |
| [`INSTRUCTION_FILE_FIXED`](../troubleshooting.md#instruction_file_fixed) | You picked up or reconnected to an agent with `--as` and gave `--agent-md` or `--claude-md` another file than the one it started with, or a file it started without. An agent keeps its instruction files for its whole life; a new agent (`--new`) can use another. |
| [`INSTRUCTION_FILE_SAVED`](../troubleshooting.md#instruction_file_saved) | A new agent's start found that an earlier agent had changed the AGENTS.md or CLAUDE.md that `--agent-md` or `--claude-md` gave it. Dockingbird saved the changed file to its agent logs folder, then put the repo's own file back; nothing was lost and nothing reached the repo. |
| [`INBOX_ROW_UNKNOWN`](../troubleshooting.md#inbox_row_unknown) | You gave a row number no message in your inbox has now, or your inbox is empty. A message keeps the number `dockingbird inbox` or `dockingbird wait` first showed it with while it waits, on any page; the id `dockingbird --json inbox` shows always works. |
| [`INBOX_ROW_RESOLVED`](../troubleshooting.md#inbox_row_resolved) | You gave a row number of your inbox instead of an id. The line says which message the row was when the command read it, before it acts on it. |
| [`DELIVERY_EXCEEDS_LINE`](../troubleshooting.md#delivery_exceeds_line) | An agent asked to read a message, and not even the shortest page of it fits in one answer of the agent's tools (they are given a most characters an answer may have). Nothing was read, so the message waits as it was. The line names what does not fit, the message's subject or the rest of it, and how long an answer it needs; an agent whose answers may be that long can read it. |
| [`SEND_AMBIGUOUS`](../troubleshooting.md#send_ambiguous) | You sent an agent a plain message while two or more of its questions to you are still unanswered, so Dockingbird can't tell which one it answers. Nothing was sent; say which with `--reply-to` and the question's row in `dockingbird inbox` (an inbox row, not its number in `dockingbird questions`), or answer it by that number with `dockingbird answer`. |
| [`SEND_REPLY_ANOTHER_AGENT`](../troubleshooting.md#send_reply_another_agent) | You replied with `--reply-to` to a message in your inbox that is another agent's question, not one of the agent you sent to: the words would have answered the other agent. Nothing was sent. Send them to the agent the line names with the same `--reply-to`, or find the question you meant in `dockingbird inbox`. |
| [`SEND_NOT_ON_BUS`](../troubleshooting.md#send_not_on_bus) | You sent a message to an agent that runs in a terminal without the bus's read tool: Dockingbird's default environment, or a config whose tool set lacks it. It could never read the message, and nothing was sent. `dockingbird start` starts an agent on the bus, which can read it. The same line, in its start form, refuses a `dockingbird start` with a task that would run in a terminal (with `--terminal`, or a config whose mode is terminal) without that tool: the agent could never read the task, so nothing was started. |
| [`SEND_PAYLOAD_INVALID`](../troubleshooting.md#send_payload_invalid) | `dockingbird send --kind KIND --payload JSON` with a payload larger than the bound: nothing was sent; give the kind's fields as one JSON object. The shape form: the payload is not one JSON object, nests deeper than the bound, repeats a key or has a decimal number, and nothing was sent either. |
| [`RESULTS_FULL`](../troubleshooting.md#results_full) | Saving an agent's results would take its results folder past its limit, so that file was not saved; `--to` saves into a folder of your own, whatever is already in it. After `dockingbird read`, the file is one the agent attached to that message: make room in the folder and read the message again. |
| [`RESULTS_TAKEN`](../troubleshooting.md#results_taken) | Saving an agent's results found that file's name already taken in the folder by something else: a link, a folder, a file with other content, or the same name in other letter case. Dockingbird left it as it is and saved nothing there. After `dockingbird read`, the file is one the agent attached to that message: move the other thing away and read the message again. |
| [`RESULTS_COPY_OWN`](../troubleshooting.md#results_copy_own) | You copied an agent's results into a folder of your own with `--to`. Those copies are yours: `dockingbird clean` never removes them. |
| [`RESULTS_TO_INVALID`](../troubleshooting.md#results_to_invalid) | You gave `--to` a folder that doesn't exist, isn't a folder, or is inside Dockingbird's own folder. Nothing was copied. |
| [`SEND_TEXT_CONTROL`](../troubleshooting.md#send_text_control) | You sent a text with a control character a message can't carry, such as the escape in a terminal's colour codes, or a NUL. Nothing was sent: remove it and send again. A tab, or an invisible mark such as a right-to-left override, is no problem: the message keeps it, and its subject, made from the text's first line, shows a space there. |
| [`INBOX_ROW`](../troubleshooting.md#inbox_row) | You ran `dockingbird inbox`: each row is one message waiting for you, in the inbox's order (priority, then age), with the number it got when you first saw it, here or from `dockingbird wait`; it keeps that number while it waits, and the numbers start at 1 again once your inbox is empty. `dockingbird read` takes the number or the id. The operator form: Dockingbird itself sent it. |
| [`INBOX_EMPTY`](../troubleshooting.md#inbox_empty) | You ran `dockingbird inbox` and no message is waiting for you. With `--priority` or `--questions`, no waiting message matches them; others may wait, which `dockingbird inbox` lists. |
| [`INBOX_MORE`](../troubleshooting.md#inbox_more) | Your inbox has more messages than one page shows. The page lists the most urgent first and, at each priority, the newest first, so the messages past it are older or lower in priority. `dockingbird inbox --all` lists them all, each with its row number; a message keeps its number while it waits, on any page. With `--priority` or `--questions` it counts only the messages that match and names the same options with `--all`. |
| [`SEARCH_ROW`](../troubleshooting.md#search_row) | You ran `dockingbird search TEXT`: one line per message whose subject or body has every word of TEXT, the newest first, in every thread of your agents: who sent it, its kind, its subject and how long ago. With `--json` each line carries the message's id and its thread's. |
| [`SEARCH_EMPTY`](../troubleshooting.md#search_empty) | You ran `dockingbird search TEXT`, and no message has every word of TEXT. Try fewer words, or other ones. |
| [`SEARCH_MORE`](../troubleshooting.md#search_more) | You ran `dockingbird search TEXT`, and more messages have its words than one page shows. Add words to narrow it. |
| [`INBOX_PAGE_MORE`](../troubleshooting.md#inbox_page_more) | You ran `dockingbird inbox --page N` and later pages hold more messages: how many, and the command that shows the next page, with the same `--priority` or `--questions` you gave. |
| [`INBOX_PAGE_EMPTY`](../troubleshooting.md#inbox_page_empty) | You ran `dockingbird inbox --page N` for a page past the last one: nothing is on it, and the message says how many pages your inbox (or the messages that match your `--priority` or `--questions`) fills. |
| [`INBOX_PAGE_ZERO`](../troubleshooting.md#inbox_page_zero) | You ran `dockingbird inbox --page 0`. Pages count from 1, the page `dockingbird inbox` shows; nothing ran. |
| [`INBOX_NAME_OPTION`](../troubleshooting.md#inbox_name_option) | You ran `dockingbird inbox NAME` with an option that only works on your own inbox: `--priority`, `--questions`, `--page` or `--clear`. Nothing ran; an agent's inbox takes only `--all`. |
| [`INBOX_SWARM_INVALID`](../troubleshooting.md#inbox_swarm_invalid) | You gave `dockingbird inbox` or `dockingbird read` a `--swarm` value with an item that isn't a swarm's name (lowercase letters, digits and `-`, up to 63 characters), or an empty one, as two commas in a row or one at the end make. Nothing ran; `dockingbird swarm list` shows this home's swarms. |
| [`INBOX_ENGINE_INVALID`](../troubleshooting.md#inbox_engine_invalid) | You gave `dockingbird inbox` or `dockingbird read` an `--engine` value with an item that isn't a workload's id: a UUID in lower case, as `dockingbird swarm list --json` shows it. Nothing ran. |
| [`INBOX_ROW_NOT_OWNED`](../troubleshooting.md#inbox_row_not_owned) | You read a message with `--swarm`, `--engine` or `--no-swarm`, and by this home's swarm record its sender is outside them: on a home that others share too, one of their agents sent it. Nothing was read or marked, so it stays in the inbox for its own reader; `dockingbird read ROW --keep` shows it without settling it. |
| [`INBOX_CLEAR_UNSCOPED`](../troubleshooting.md#inbox_clear_unscoped) | You ran `dockingbird inbox --clear` with no `--swarm`, `--engine` or `--no-swarm` on a home whose swarm record has two or more swarms, such as a fleet engine home that others share: one clear would settle everyone's stopped agents' notices at once. Nothing ran; name the swarms whose stopped agents you clear, or all of them, as the line shows. |
| [`INBOX_ROWS_NOT_KEPT`](../troubleshooting.md#inbox_rows_not_kept) | Your inbox has so many open messages that their row numbers would take Dockingbird's `state.json` past the size it reads, so the numbers shown last for this command only. The rows are still listed, the newest first; read one by the id `dockingbird --json inbox` shows, or answer some to bring the count down. |
| [`INBOX_CLEARED_ROW`](../troubleshooting.md#inbox_cleared_row) | You ran `dockingbird inbox --clear`: one row for each item it cleared that an agent that has stopped left you, with the agent, the kind, `read` for a notice it marked read or `closed` for a question it closed, and the id that still reads it. |
| [`INBOX_CLEARED`](../troubleshooting.md#inbox_cleared) | You ran `dockingbird inbox --clear` and it cleared what agents that have stopped left you: their notices are marked read and their open questions closed. Nothing is deleted: `dockingbird read ID` still reads each message. |
| [`INBOX_CLEAR_NOTHING`](../troubleshooting.md#inbox_clear_nothing) | You ran `dockingbird inbox --clear` and no agent that has stopped left a notice or an open question in your inbox, so nothing changed. |
| [`INBOX_CLEAR_LEFT`](../troubleshooting.md#inbox_clear_left) | You ran `dockingbird inbox --clear` and agents that have stopped left messages that ask you to act: a task, a review request or work handed over. They stay in your inbox; `dockingbird inbox --all` lists them. |
| [`QUESTION_ROW`](../troubleshooting.md#question_row) | You ran `dockingbird questions`: each row is one question an agent is asking you, with the number it got when you first saw it (kept until it is answered), who asks, what kind of question it is, its text, its options numbered, and how long ago. The typed form: the question takes any text. The not-waiting forms (with options, and typed): the agent asked without waiting for the answer, so the row says so and the agent's row in `dockingbird status` doesn't count it. `dockingbird answer` takes the number or the id. |
| [`QUESTIONS_EMPTY`](../troubleshooting.md#questions_empty) | You ran `dockingbird questions` and no agent is waiting for an answer. |
| [`QUESTIONS_MORE`](../troubleshooting.md#questions_more) | More questions are open than one page shows; a question after the page gets its row once earlier ones are answered. |
| [`QUESTION_ROW_UNKNOWN`](../troubleshooting.md#question_row_unknown) | You gave `dockingbird questions` or `dockingbird answer` a row number no open question has: a question keeps its number until it is answered, and the id `dockingbird --json questions` shows always works. |
| [`QUESTION_NOT_OPEN`](../troubleshooting.md#question_not_open) | You gave `dockingbird answer` the id of a question that is no longer open, or `dockingbird send --reply-to` answered a question someone else had answered meanwhile, and nothing was sent. The default form: the question was answered, the line names who and when; its first step lists what is still open, its second tells the agent something without answering again. The withdrawn form: the agent took the question back, asked it again (the new one is in `dockingbird questions`) or ended; its second step sends the answer to the agent as a reply. The replied form: the answer lost a race with another answer to the same question; its steps are the default form's. |
| [`QUESTION_HEADER`](../troubleshooting.md#question_header) | You ran `dockingbird questions ROW`: who asks, what kind of question it is and which tool; its text and options follow. The replied form: you answered it; the on-screen form: it was answered in the tool's own dialog on the agent's screen; the replied-by form names who else did (a rule, a helper agent); the dropped form: it was withdrawn, since its agent moved on or ended. |
| [`QUESTION_OPTION_ROW`](../troubleshooting.md#question_option_row) | One option of the question shown: its number, which `dockingbird answer --option N` takes, its label and, in the described form, what the tool says about it. |
| [`QUESTION_ANSWER_HINT`](../troubleshooting.md#question_answer_hint) | The last line of a question shown whole: the command that answers it, by an option's number or, in the typed form, in words. |
| [`ANSWERED`](../troubleshooting.md#answered) | You ran `dockingbird answer` and the answer was recorded for the agent. The on-screen form: the agent works at a terminal, so its tool shows its own dialog on its screen, where you pick it with the arrow keys and Enter; `dockingbird ui` opens that screen from the agent's row. The sent-on form: a Codex agent on the bus takes your words as its next turn. The at-prompt form: a Codex agent at a terminal takes them typed at its prompt; you type them there, in its screen, which `dockingbird ui` opens from the agent's row. |
| [`ANSWER_NEEDS_ONE`](../troubleshooting.md#answer_needs_one) | You ran `dockingbird answer` without an option number or an answer, or with both; give one of them. |

| [`ANSWERED_NOT_SENT`](../troubleshooting.md#answered_not_sent) | You answered a Codex agent's turn end on the bus; the answer was recorded, but sending it as the agent's next turn failed (the line quotes why; the lost form: the docker call behind the send gave no answer, and `--verbose` shows its detail). | [`ANSWER_ONE_LINE`](../troubleshooting.md#answer_one_line) | You answered a question of an agent at a terminal with a text that has a line break, a tab or another control character; `dockingbird ui` types the answer into the tool's dialog, where a line break ends it early and a tab moves to another question, so write it on one line. Nothing was answered. |
| [`READ_HEADER`](../troubleshooting.md#read_header) | You ran `dockingbird read`: the message's kind, sender, priority and subject. Its body follows, every control character escaped, then the files it names. The operator form: Dockingbird itself sent it. |
| [`READ_BODY_LINE`](../troubleshooting.md#read_body_line) | You ran `dockingbird --json read`: each envelope carries a piece of the message's body, in order, so the agent's text never stands outside an envelope. |
| [`BODY_ARTIFACT_ROW`](../troubleshooting.md#body_artifact_row) | The message you read names a file an agent attached: its name, type, size and id. `dockingbird results` saves the files of the agent's task thread. |
| [`SENT`](../troubleshooting.md#sent) | You ran `dockingbird send` and the message went; the line shows its id. The ended form: the agent has stopped, so the message waits until you continue it with the command the line names: the agent's own command for an agent of a config, and `dockingbird start --as NAME` for one of the default environment, whose own terminal can't read messages. The not-running form: the agent's start began but no container of it runs (that start stopped before its container ran), so the message waits until it starts; the command the line names starts it. | [`SENT_QUESTION_OPEN`](../troubleshooting.md#sent_question_open) | You ran `dockingbird send` and the agent has bus questions to you that are still open. | [`WITHDRAWN`](../troubleshooting.md#withdrawn) | You ran `dockingbird send --withdraw`: the message's deliveries that no agent had taken yet are withdrawn. The cancel form: an agent had accepted it, so its work is asked to stop, and the delivery stays accepted until the agent settles it. |
| [`WAIT_DELIVERY`](../troubleshooting.md#wait_delivery) | You ran `dockingbird wait` and a message you hadn't seen yet was waiting, or arrived while it waited, wherever it sorts in your inbox. The line gives its row number for `dockingbird read`, and no later wait shows it again. The operator form: Dockingbird itself sent it. |
| [`WAIT_TIMED_OUT`](../troubleshooting.md#wait_timed_out) | You ran `dockingbird wait` and no message you hadn't seen arrived before its time ran out. Run it again to keep waiting. The unread form: messages still wait in your inbox. |
| [`RESULTS_WRITTEN`](../troubleshooting.md#results_written) | You ran `dockingbird results`: each line is one file it saved from the agent's task thread, with the file's type. | [`RESULTS_NONE`](../troubleshooting.md#results_none) | You ran `dockingbird results` and the agent's task thread has no attached files yet. |
| [`RESULTS_NO_THREAD`](../troubleshooting.md#results_no_thread) | You ran `dockingbird results` for an agent this Mac started without a task, or did not start, so no task thread is recorded for it. Nothing was saved; `dockingbird read` shows the files a message names. |
| [`WAITING_ENDED_ROW`](../troubleshooting.md#waiting_ended_row) | `dockingbird status` shows an agent that has ended while messages were still waiting for it, after the questions: how many wait, what the first of them is (its kind and subject; after `dockingbird stop` in the middle of a task, that is the task the agent was working on), and the command that continues the agent, which hands it them. Nothing delivers them until you run it. The unnamed form shows when the inbox's row carries no kind or subject text. |
