# Troubleshooting index: benchmark jobs

Find a message id below to see when Dockingbird prints that message. Add `--verbose` to a command and every message also shows its id. With `--json`, each envelope carries the id as its `id` key. Each id links to its entry in the [catalogue](../troubleshooting.md): the message text, the next step and the exit status. This page holds the 51 ids about Harbor benchmark jobs.

## Harbor jobs

| Id | When it appears |
|---|---|
| [`HARBOR_PIN_INVALID`](../troubleshooting.md#harbor_pin_invalid) | You ran `dockingbird harbor` with a `--harbor-commit` that isn't a full commit, or in a task repository whose `.github/workflows/validate-harbor.yml` names a Harbor commit that isn't one, or can't be read safely. Nothing ran; the line says where the commit came from, never what it was. |
| [`HARBOR_PIN`](../troubleshooting.md#harbor_pin) | You ran `dockingbird harbor run`, `baseline`, `check` or `version`: the Harbor commit it uses, and whether it came from `--harbor-commit`, from the task repository's CI workflow or from Dockingbird's own pin. |
| [`HARBOR_PIN_NOT_FOUND`](../troubleshooting.md#harbor_pin_not_found) | Dockingbird cloned Harbor to install a commit, and Harbor's repository has no such commit. Nothing of the install was kept; check the commit, or give another with `--harbor-commit`. |
| [`HARBOR_INSTALLING`](../troubleshooting.md#harbor_installing) | A `dockingbird harbor` command needed a Harbor commit that isn't installed yet, and installs it, once per commit: the clone, the packages of Harbor's own lock file, then the checks. Another command installing the same commit is waited for. |
| [`HARBOR_OUTPUT_LINE`](../troubleshooting.md#harbor_output_line) | One of the last lines a failed step of Harbor's install printed, or one mise printed while it read or installed a repo's tool versions (under a failure's message, and each as it comes when you start with `--verbose`), shown with any control character escaped. |
| [`HARBOR_INSTALL_FAILED`](../troubleshooting.md#harbor_install_failed) | A step of Harbor's install failed, ran past the install's time bound, or couldn't run (uv missing from your PATH, for one), or the commit's lock couldn't be used: it has a package with no wheel for this computer (the install builds none), or it can't be read. The step's last lines are shown; the commit's install folder was removed, so the next command starts over. |
| [`HARBOR_COMMIT_UNTESTED`](../troubleshooting.md#harbor_commit_untested) | Harbor was installed at a commit whose private APIs differ from those Dockingbird's Harbor plugin was tested on. Jobs with the oracle and nop agents run as usual. |
| [`HARBOR_VERSION`](../troubleshooting.md#harbor_version) | You ran `dockingbird harbor version`: whether the Harbor commit in use is installed, and the folder it is (or will be) installed in. |
| [`HARBOR_NOT_A_TASK`](../troubleshooting.md#harbor_not_a_task) | You ran `dockingbird harbor run` or `baseline` in a folder, or named one with `-p`, that has no `task.toml`, so it isn't a Harbor task. Nothing ran. |
| [`HARBOR_TASK_INVALID`](../troubleshooting.md#harbor_task_invalid) | The task's `task.toml` couldn't be used: it is too large, a link, not UTF-8 or not TOML, or a setting Dockingbird reads (the task's name, which Harbor takes only as org/name, its operating system, its timeouts, resources or network modes) isn't of the kind Harbor takes, or its count of cpus or of memory is below zero or more than Docker can take, so no job with it would run anywhere. Nothing ran; the line names the setting, never its value. |
| [`HARBOR_TASK_UNSUPPORTED`](../troubleshooting.md#harbor_task_unsupported) | The task's `task.toml` has steps, or sets its operating system to Windows. Dockingbird runs Harbor tasks of one step on Linux, as the platform's local checks do; run any other with Harbor itself. Nothing ran. |
| [`HARBOR_NETWORK_POLICY_REFUSED`](../troubleshooting.md#harbor_network_policy_refused) | The task's `task.toml` asks, in its `[environment]`, `[agent]`, `[verifier]` or `[verifier.environment]` section, for a network other than public, or turns the internet off. Dockingbird runs Harbor tasks on the public network, as the platform does, and refuses the others before anything runs. |
| [`HARBOR_TASK_LAYOUT`](../troubleshooting.md#harbor_task_layout) | You ran `dockingbird harbor run` or `baseline` on a task folder that Harbor wouldn't run as one task: its `environment` folder, its `instruction.md` or its `tests/test.sh` is missing or is a link, it has an `environment/.env`, which compose would read on this Mac, its `environment/Dockerfile` is a link leading outside that folder, or a `Dockerfile.rego` lies beside it, which Docker's build would read on this Mac as a build policy, or a folder inside it has another `task.toml`, which Harbor would run instead. When the task's verifier runs in a container of its own, built from its `tests` folder, a link in its place, a `.env` in it, a `Dockerfile` in it that is a link leading outside it, or a `Dockerfile.rego` beside that Dockerfile, is refused the same way. Nothing ran. |
| [`HARBOR_COMPOSE_REFUSED`](../troubleshooting.md#harbor_compose_refused) | A compose file of the job (the task's `environment/docker-compose.yaml`, the `tests/docker-compose.yaml` of a verifier that runs in a container of its own, or one you gave with `--extra-docker-compose`) sets something Dockingbird doesn't run: a key outside the ones that keep the task's containers to themselves (`ports`, `volumes` or `privileged`, for example), a build folder outside the file's own folder, a build's Dockerfile that is a link leading outside the file's own folder, or a `.rego` file beside it, the host's or another container's network, a network Dockingbird didn't make, a label of Dockingbird's or compose's, or a build path or label that compose would interpolate (`$`). Nothing ran; the line names where, never the value. |
| [`HARBOR_COMPOSE_INVALID`](../troubleshooting.md#harbor_compose_invalid) | A compose file of the job (the task's, the verifier's own or one you gave) couldn't be checked: it is too large, missing, a link, not UTF-8 or not one YAML document, it uses a YAML alias or a YAML tag, it nests deeper than a compose file does, or has something other than what a compose file has where Dockingbird reads it. Nothing ran; the line never shows what the file has. |
| [`HARBOR_AGENT_UNSUPPORTED`](../troubleshooting.md#harbor_agent_unsupported) | You gave `dockingbird harbor run` an agent with `-a` that Dockingbird doesn't run: it runs Harbor's oracle, nop and claude-code agents, since any other needs a key in its environment, which Dockingbird never hands Harbor that way. Nothing ran. |
| [`HARBOR_ENVIRONMENT_UNSUPPORTED`](../troubleshooting.md#harbor_environment_unsupported) | You gave `dockingbird harbor run` an environment with `-e` other than docker. Dockingbird runs Harbor jobs in Docker on this Mac, in its own environment, which labels the job's containers so they are removed afterwards. Nothing ran. |
| [`HARBOR_OPTION_REFUSED`](../troubleshooting.md#harbor_option_refused) | You gave `dockingbird harbor run` an option Dockingbird doesn't pass on to Harbor, and nothing ran. Dockingbird passes only the options of Harbor's `run` it knows, and refuses by name the ones that mount folders of this Mac into the task's container (`--mounts`, `--mounts-json`) or replace the environment Dockingbird runs jobs in (`--environment-import-path`); the ones that would run a task or a dataset it hasn't checked (a job config, a dataset, another task or a repository); `--env-file`, which would change the environment it gives Harbor; the ones that change the classes Harbor runs the job with (a plugin, a verifier, a simulated user, environment keywords); the ones that send the job to Harbor Hub or Hugging Face; `--override-gpus` and `--override-tpu`, which would give the container a device of this computer; `--ae` or `--ve` with a key, token, password or other credential in the variable's name, which would land on a command line and in the trial's logs (save it with `dockingbird login` instead); and any option it doesn't know at this Harbor commit. `baseline`, which runs oracle then nop and names both jobs itself, also refuses `-a`, `--agent-import-path` and `--job-name`, and a `-k` that isn't a whole number of one or more. Both `run` and `baseline` also refuse `-k`, `-n`, `--n-concurrent-agents` or `-r` over the count the message names, and more `-m` models than that: a job that big wouldn't finish on this Mac (give a smaller number, or leave the option out). Both also refuse an option that takes a value when it is the last word and no value follows it (`--skill` alone, say): the message names the option as you typed it, and a value after an equals sign, even an empty one (`--skill=`), counts as given. Give the option a value, or leave it out. |
| [`HARBOR_JOB_NAME_INVALID`](../troubleshooting.md#harbor_job_name_invalid) | You gave `dockingbird harbor run` a `--job-name` that isn't a job name: lowercase letters, digits and hyphens, starting with a letter or digit, up to the length the message names. Nothing ran. |
| [`HARBOR_RUNNING`](../troubleshooting.md#harbor_running) | You ran `dockingbird harbor run` or `baseline`: the job's folder is made and Harbor is about to start. The line names the job, its agent and the folder its results go to; Harbor's own live display follows on the terminal. |
| [`HARBOR_JOB_DONE`](../troubleshooting.md#harbor_job_done) | A job of `dockingbird harbor run` or `baseline` ended: one row for each trial that finished (its name, its agent, its reward, how long it ran and, if it failed, the kind of error), then the job's folder. When a trial hit an error or left no readable result, the message says so and the command exits 1, though Harbor itself exits 0 after such a job. After a Ctrl-C the message says the job was interrupted. |
| [`HARBOR_TRIAL_ROW`](../troubleshooting.md#harbor_trial_row) | One trial of a Harbor job, in the lists `harbor run`, `baseline` and `harbor results` print: its name, its agent, the reward it earned (`-` when it has none), how long it ran and, when it failed, the kind of error. A trial with no readable result shows `no result`. Whatever the trial's files hold is shown with control characters escaped. |
| [`HARBOR_LEFTOVERS_REMOVED`](../troubleshooting.md#harbor_leftovers_removed) | A Harbor job ended and Dockingbird cleaned up after it: the Docker images the job built are removed, each by its exact id; an image a running container still uses stays; and the containers, networks and volumes the job left behind, if any, are removed too. A later Harbor command that finds what a job left when it ended without cleaning up (it crashed or was killed) says so the same way, naming the job; when what it found belongs to no job it can name, the message says only that a Harbor job ended without cleaning up. |
| [`HARBOR_IMAGES_NOT_MADE`](../troubleshooting.md#harbor_images_not_made) | A Harbor job ended, and Docker held images that weren't there when it started but that the job didn't make: another program's or another Dockingbird folder's, a base image the job's task pulled, or another job's. Dockingbird removes only what the job built, so these stay; remove one yourself with `docker image rm` if you no longer need it. |
| [`HARBOR_IMAGE_KEPT`](../troubleshooting.md#harbor_image_kept) | Docker refused to remove an image a Harbor job built, for a reason other than a container using it. The message gives Docker's own words and the command that removes the image by hand; nothing else is affected. A later `dockingbird harbor clean` that cannot remove an image says it the same way. |
| [`HARBOR_BASELINE_OK`](../troubleshooting.md#harbor_baseline_ok) | You ran `dockingbird harbor baseline`: the task's oracle run scored 1 on every attempt and its nop run scored 0, so the task's checks pass. |
| [`HARBOR_BASELINE_FAILED`](../troubleshooting.md#harbor_baseline_failed) | You ran `dockingbird harbor baseline` and it found a problem with the task: a trial that scored other than 1 for the oracle or 0 for nop, shown with the last lines its verifier printed; a trial that hit an error, with the last lines of its output; a trial with no result; a job that didn't run the task Dockingbird checked; or a job that ended with a failing status before a verdict. The command exits 1. |
| [`HARBOR_JOB_UNEXPECTED`](../troubleshooting.md#harbor_job_unexpected) | A Harbor job ended and what it left doesn't match what Dockingbird started: Harbor wrote no result for the job, the job ran another task than the one Dockingbird checked, or it ran another number of trials than were planned. The rows still print and the command exits 1. |
| [`HARBOR_RESOURCES_OVER_VM`](../troubleshooting.md#harbor_resources_over_vm) | The task asks for more cpus or more memory than Docker's virtual machine has. Harbor runs the job anyway; the message gives the option that fits the task to the machine. |
| [`HARBOR_COMPOSE_MISSING`](../troubleshooting.md#harbor_compose_missing) | You ran a `dockingbird harbor` command that runs a job, and Docker has no compose plugin, which Harbor needs. Nothing ran. Docker Desktop includes it. |
| [`HARBOR_DOCKER_FAILED`](../troubleshooting.md#harbor_docker_failed) | A docker command a `dockingbird harbor` command runs failed; the message gives the command and Docker's own words. Before a job starts, nothing ran; when the command that failed was the image listing made once the job's folder exists, that folder stays, empty (under `--json`, with an empty log), as it does when Dockingbird's own record of the job can't be written: `dockingbird harbor clean` removes it when it is under Dockingbird's own jobs folder, and one under a `-o` folder of yours is yours to remove. After a job ran, the listing that finds the images and leftovers to clean up failed, so some may remain: the job's own files are complete, the command exits 1, and `dockingbird harbor clean` removes what is left. `dockingbird harbor clean` can fail the same way while cleaning up, after it removed some leftovers. |
| [`HARBOR_JOB_RUNNING`](../troubleshooting.md#harbor_job_running) | You ran `dockingbird harbor run` or `baseline` with a job name that another `dockingbird harbor` command is still running. Nothing was made and nothing ran. |
| [`HARBOR_PROGRAM_MISSING`](../troubleshooting.md#harbor_program_missing) | You ran `dockingbird harbor run` or `baseline`, and the Harbor that Dockingbird installed can no longer be started: its folder was changed or broken after the install. Harbor never ran, so nothing ran, and the job's record is ended. The message names the Harbor commit, the folder and what the system said; remove that folder, then run the command again, and Dockingbird installs Harbor again. |
| [`HARBOR_JOBS_DIR_MISSING`](../troubleshooting.md#harbor_jobs_dir_missing) | You gave `dockingbird harbor run` or `baseline` a `-o` folder that isn't there, or isn't a folder. Nothing ran: Harbor would make the whole path wherever you can write, and Dockingbird makes no folder outside its own for you. Create the folder, or leave `-o` out to use Dockingbird's own jobs folder. |
| [`HARBOR_RECORD_FAILED`](../troubleshooting.md#harbor_record_failed) | Dockingbird's own record of a Harbor job (`dockingbird.json` in the job's folder) couldn't be written, or under `--json` its log (`dockingbird.log`) couldn't be opened, or the job's folder itself couldn't be made; the message names the folder and what the system said, and the command exits 1. When it fails before the job starts, nothing ran; the folder that was made stays, empty (under `--json`, with an empty log): `dockingbird harbor clean` removes it when it is under Dockingbird's own jobs folder, and one under a `-o` folder of yours is yours to remove; when the folder itself couldn't be made, nothing is there. When it fails at the end, the job ran and was cleaned up and its rows were printed, but `dockingbird harbor jobs` shows it as stopped; `dockingbird harbor results` still reads Harbor's own files. |
| [`HARBOR_SIGNIN_TOO_SHORT`](../troubleshooting.md#harbor_signin_too_short) | You ran `dockingbird harbor run -a claude-code` with no saved Claude key or token, and the Claude sign-in on this Mac isn't known to last the whole trial. Claude Code in a trial never picks up a sign-in that renews while it runs, so the sign-in must outlast the task's agent timeout, its build timeout, Harbor's setup and a margin, for every wave of its attempts (`-k` attempts, `-n` at a time, each retried `-r` times), with the verifier's timeout and a retry's wait between one run and the next; the message says how long it has and how long the trial needs (or that the trial needs a little more than the sign-in has, when the two would read alike), or that the trial would need it for longer than the bound the message names, or that the task sets no agent timeout, or that a timeout multiplier you gave leaves it no finite time bound, or that the sign-in names no expiry. Nothing ran. Save a long-lived token (`claude setup-token`, then `dockingbird login claude --oauth-token -`) and trials use it. |
| [`HARBOR_NO_SIGNIN`](../troubleshooting.md#harbor_no_signin) | You ran `dockingbird harbor run -a claude-code`, and Dockingbird has neither a saved Claude key or token nor a Claude sign-in to give the trial. Nothing ran. Save a long-lived token (`claude setup-token`, then `dockingbird login claude --oauth-token -`) and run it again. |
| [`HARBOR_COMMIT_UNTESTED_AGENT`](../troubleshooting.md#harbor_commit_untested_agent) | You ran `dockingbird harbor run -a claude-code` on a Harbor commit that Dockingbird's plugin wasn't tested with, taken from the task repository's pin or Dockingbird's default: the claude-code agent relies on parts of Harbor that may differ there, so it doesn't run. When the sign-in's pipe is what failed, the job's folder was made already and stays, with its record ended: `dockingbird harbor clean` removes it when it is under Dockingbird's own jobs folder, and one under a `-o` folder of yours is yours to remove. | [`HARBOR_SIZES_UNREAD`](../troubleshooting.md#harbor_sizes_unread) | `dockingbird harbor clean` couldn't read the size of some files in a Harbor job's folder or Harbor's install, so the sizes it shows leave them out. |

| [`HARBOR_NOTHING_TO_CLEAN`](../troubleshooting.md#harbor_nothing_to_clean) | You ran `dockingbird harbor clean` and there was no job folder, no leftover and nothing else of Harbor's to remove. |
