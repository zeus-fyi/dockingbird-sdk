# Troubleshooting index: the GUI, the MCP server and shell completion

Find a message id below to see when Dockingbird prints that message. Add `--verbose` to a command and every message also shows its id. With `--json`, each envelope carries the id as its `id` key. Each id links to its entry in the [catalogue](../troubleshooting.md): the message text, the next step and the exit status. This page holds the 27 ids about the GUI, the MCP server and shell completion.

The Dockingbird GUI is not yet available to customers.

## Configs, trust and the agents' own commands

| Id | When it appears |
|---|---|
| [`MCP_CONNECTED`](../troubleshooting.md#mcp_connected) | You ran `dockingbird mcp install` and it connected Dockingbird's tools to Claude Code or Codex with the tool's own `mcp add`, and recorded it; the line shows how to undo it. The by-hand form: `--connected NAME` recorded a connection you made yourself. |
| [`MCP_ALREADY_CONNECTED`](../troubleshooting.md#mcp_already_connected) | You ran `dockingbird mcp install` (or its `--check`) and the tool already has Dockingbird's tools, or you gave `--connected` a name already recorded. Nothing was changed. |
| [`MCP_CONNECT_FAILED`](../troubleshooting.md#mcp_connect_failed) | You ran `dockingbird mcp install` and the tool's own `mcp add` failed or didn't answer, so nothing was recorded. What the tool printed is not shown; the message gives the command to run yourself, then the one that records it. With a `DOCKINGBIRD_HOME` that is not the default, that command passes it, on a second line after a `\`, so copy both lines. |
| [`MCP_NOT_FOUND`](../troubleshooting.md#mcp_not_found) | You ran `dockingbird mcp install` and no `claude` or `codex` program it can run is on your `PATH`. The message shows Dockingbird's server definition, `{"command": "dockingbird", "args": ["mcp"]}`, to add to any other tool by hand; with a `DOCKINGBIRD_HOME` that isn't the default, it adds `"env": {"DOCKINGBIRD_HOME": ...}`, so the server reaches that folder. |
| [`MCP_SHOW`](../troubleshooting.md#mcp_show) | You ran `dockingbird mcp install --show`: the server definition, `{"command": "dockingbird", "args": ["mcp"]}` (stdio), to add to a tool's MCP settings yourself; with a `DOCKINGBIRD_HOME` that isn't the default, it adds `"env": {"DOCKINGBIRD_HOME": ...}`. Nothing was connected. |
| [`MCP_CHECKED`](../troubleshooting.md#mcp_checked) | You ran `dockingbird mcp install --check`: a connection it recorded is gone from the tool, no `claude` or `codex` program on your `PATH` could be used now, or it was made by hand for another tool, which can't be checked; or nothing is recorded yet. |
| [`MCP_DISCONNECTED`](../troubleshooting.md#mcp_disconnected) | You ran `dockingbird clean --all` and it disconnected a harness `dockingbird mcp install` had connected, with the harness's own remove command. |
| [`MCP_CONNECTED_BY_HAND`](../troubleshooting.md#mcp_connected_by_hand) | You ran `dockingbird clean --all` with a harness you had connected yourself (`dockingbird mcp install --connected`). Dockingbird changed none of that harness's settings, so it leaves them; the line names the remove command if you want it gone. |
| [`MCP_DISCONNECT_FAILED`](../troubleshooting.md#mcp_disconnect_failed) | You ran `dockingbird clean --all` and a harness's remove command failed, or the program is gone. Run the command the line shows yourself. |

## The Dockingbird GUI

| Id | When it appears |
|---|---|
| [`UI_NOT_A_TERMINAL`](../troubleshooting.md#ui_not_a_terminal) | You ran `dockingbird ui` where it has no terminal to draw on: in a pipe, from a script, or with `--json`. The Dockingbird GUI it opens draws on the terminal and reads your keys and mouse there, so it needs a Terminal window. Run it there. |
| [`UI_STOP_WITH_INSTALL`](../troubleshooting.md#ui_stop_with_install) | You ran `dockingbird ui stop` with `--install`. One stops the GUI's server, the other installs the GUI: run them one at a time. |
| [`GUI_MISSING`](../troubleshooting.md#gui_missing) | You ran `dockingbird ui`, and the Dockingbird GUI it opens isn't on this computer: there's no `dockingbird-gui` in the `bin` folder in Dockingbird's folder, where `dockingbird ui --install` puts it, nor in a folder of your `PATH`. Install it with `dockingbird ui --install`. When the line names a file instead, you set the variable that picks the GUI's file, and nothing is at its path: fix the path, or unset the variable to use the installed GUI. |
| [`GUI_SESSION_EMPTY`](../troubleshooting.md#gui_session_empty) | You ran `dockingbird ui` or `dockingbird ui stop` with the variable that names where the GUI runs set, but empty. That variable is for development and tests: it names another place for the GUI than the one every home shares. Unset it, or give it a name. |
| [`GUI_PREVIOUS_OPENED`](../troubleshooting.md#gui_previous_opened) | You ran `dockingbird ui`, and two GUIs run on this computer: the one you had before Dockingbird 0.4.4, and the one 0.4.4 started beside it under a name of its own. `dockingbird ui` opens the one from before, with its tabs, from every folder. The other keeps running, with whatever runs in its tabs, until you end it with the line's last command; the line's third command opens it. When the line says it could not be checked, run `dockingbird --verbose ui` to see why. |
| [`GUI_NOT_EXECUTABLE`](../troubleshooting.md#gui_not_executable) | You ran `dockingbird ui`, and the file it found for the Dockingbird GUI can't be run: it isn't a program file you may run, or it didn't start, as a program built for another kind of computer doesn't. `dockingbird ui --install` puts a good copy in its place; run the command with `--verbose` to see why. |
| [`GUI_WRONG_VERSION`](../troubleshooting.md#gui_wrong_version) | You ran `dockingbird ui`, and the Dockingbird GUI it found is another version than the one this Dockingbird works with, or didn't say its version when asked. The line names both versions and the file; `dockingbird ui --install` installs the version it needs. |
| [`GUI_INSTALLING`](../troubleshooting.md#gui_installing) | You ran `dockingbird ui --install`, or `dockingbird update` found no dockingbird-gui installed, or one at another version than the one this Dockingbird expects. Dockingbird is getting that version from the GUI repository with your own git and SSH key. With none installed, `dockingbird update` gets it only once Dockingbird is set up, and never on a computer this Dockingbird pins no dockingbird-gui build for. |
| [`GUI_INSTALLED`](../troubleshooting.md#gui_installed) | The dockingbird-gui Dockingbird got matched the checksum it expects, and it is now installed in the `bin` folder of your Dockingbird home, in place of the one before, with a link to it beside `dockingbird` on your `PATH`, so `dockingbird-gui` is a command too (run bare, it opens its own default view, not this home's: use `dockingbird ui`). `dockingbird ui` opens it. The form without the `PATH` line made no link; the one-line form comes from `dockingbird update`, which made the link again. |
| [`GUI_LINK_IN_THE_WAY`](../troubleshooting.md#gui_link_in_the_way) | You ran `dockingbird ui --install`, and where Dockingbird links dockingbird-gui beside `dockingbird` there is already a file that isn't its link, such as a build of your own. Dockingbird left it as it is, so the dockingbird-gui your `PATH` finds may not be the one it installed; `dockingbird ui` runs the installed one. Remove the file and run the install again to get the link. |
| [`GUI_LINK_REFUSED`](../troubleshooting.md#gui_link_refused) | You ran `dockingbird ui --install` or `dockingbird update`, and the folder `dockingbird` is in refused the link to dockingbird-gui. The GUI is installed all the same and `dockingbird ui` runs it; run the command with `--verbose` to see why. |
| [`GUI_CHECKSUM_MISMATCH`](../troubleshooting.md#gui_checksum_mismatch) | The dockingbird-gui file Dockingbird got doesn't have the SHA-256 checksum this Dockingbird expects for that version: the release was replaced by another build, or the file is damaged. Nothing was installed, and the dockingbird-gui you had stays. The line shows both checksums, to compare with the release's `SHA256SUMS`. |
| [`GUI_PLATFORM_UNSUPPORTED`](../troubleshooting.md#gui_platform_unsupported) | You ran `dockingbird ui --install` on a computer dockingbird-gui has no build for: it is built for Macs with Apple silicon and for Linux on arm64. The line names this computer's system and processor. Its other form says this Dockingbird has no checksum for that version's build of this computer yet, so it installs nothing it can't check. |
| [`GUI_FETCH_FAILED`](../troubleshooting.md#gui_fetch_failed) | Getting dockingbird-gui failed, so nothing was installed and the one you had stays. Usually git couldn't read the private GUI repository over SSH (the line shows git's own words, such as a refused key), or that version has no release there. Other forms say git isn't on your `PATH` or couldn't start, that no answer came in time, or that the answer was larger than Dockingbird reads. |
| [`COMPLETION_INSTALLED`](../troubleshooting.md#completion_installed) | You ran `dockingbird completion --install`: Dockingbird wrote the completion script for your shell into its own folder and added the line that loads it to your shell's startup file (`~/.zshrc`, `~/.bashrc`, or fish's `~/.config/fish/conf.d/dockingbird.fish`). Open a new terminal to use it. The one-line form comes from `dockingbird update`, which rewrote an installed script for the version it installed. |
| [`COMPLETION_ALREADY`](../troubleshooting.md#completion_already) | You ran `dockingbird completion --install` again: your startup file already loads the script, so nothing was added to it, and the script was written again for this version. |
| [`COMPLETION_SHELL_UNKNOWN`](../troubleshooting.md#completion_shell_unknown) | You ran `dockingbird completion --install` without naming a shell, and the `SHELL` variable names a shell Dockingbird has no completion for, or isn't set. Name `zsh`, `bash` or `fish` after `--install`. Nothing was written. |
| [`COMPLETION_RC_REFUSED`](../troubleshooting.md#completion_rc_refused) | You ran `dockingbird completion --install`, and Dockingbird couldn't read or write your shell's startup file: the system refused it, it isn't a regular file, or it is very large; run the command with `--verbose` to see why. The script was written and the startup file is unchanged. The other form says `HOME` isn't set, so there is no startup file to name. |
