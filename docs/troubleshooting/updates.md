# Troubleshooting index: updates

Find a message id below to see when Dockingbird prints that message. Add `--verbose` to a command and every message also shows its id. With `--json`, each envelope carries the id as its `id` key. Each id links to its entry in the [catalogue](../troubleshooting.md): the message text, the next step and the exit status. This page holds the 43 ids about checking for and installing updates, pins and the switch to a new version.

## Typing a command

| Id | When it appears |
|---|---|
| [`VERSION`](../troubleshooting.md#version) | You ran `dockingbird --version` (or `-v`): Dockingbird's version, the commit it was installed from (or that it came from a local checkout, when you installed it from a folder), and the versions of Claude Code and Codex it runs. |

## Docker, platform and setup

| Id | When it appears |
|---|---|
| [`VERSION_MISMATCH`](../troubleshooting.md#version_mismatch) | The `dockingbird` command you ran is older than the Dockingbird that is running, so it won't talk to it. `dockingbird status NAME` says this too, since its own record can't answer for the agent. |
| [`STATE_NEWER`](../troubleshooting.md#state_newer) | A newer Dockingbird last wrote the files Dockingbird keeps for you (`state.json` in its folder), and the `dockingbird` command you ran is older, so it reads them but won't change them. Update it, or run the newer one. |
| [`STATE_FILE_REFUSED`](../troubleshooting.md#state_file_refused) | Dockingbird keeps its records of your agents, sign-ins and kept copies in `state.json` in its folder, and reads that file only when it is a plain file within its size limit. The file is over the limit, or is a link, a folder or a file Dockingbird can't open; or the change the command would make would take it past the limit. Rather than write over what it can't read, Dockingbird changed nothing. `dockingbird status` shows the same lines under "Needs your attention". |
| [`STATE_FILE_NOT_UPDATED`](../troubleshooting.md#state_file_not_updated) | A command did what you asked, but the record of it couldn't go into `state.json`: the file is over its size limit, a link, a folder or a file Dockingbird can't open, or this record would have taken it past the limit. What the command did stands; Dockingbird left the file as it was. |

## Update

| Id | When it appears |
|---|---|
| [`UPDATE_GETTING`](../troubleshooting.md#update_getting) | You ran `dockingbird update`: the first step gets the latest Dockingbird, and its line ends with the versions before and after. When the output goes to a pipe or a file, the line prints at once and a "still getting the latest Dockingbird" line follows once a minute while it runs. |
| [`UPDATE_REBUILDING`](../troubleshooting.md#update_rebuilding) | `dockingbird update` rebuilds Dockingbird, with an estimate from the last build when a build runs, and none when the new version is already built; then it gets the tools' latest releases, one line each. When the output goes to a pipe or a file, the line prints at once and a "still updating" line follows once a minute while it runs. |
| [`UPDATE_DONE`](../troubleshooting.md#update_done) | You ran `dockingbird update`, and there was nothing to change: no newer Dockingbird to install and nothing to rebuild. |
| [`UPDATE_TOOLS`](../troubleshooting.md#update_tools) | After its rebuild, `dockingbird update` got each tool you have used once at its latest version, or found the one you have is the latest, and says which; when the channel names an older version than the one you have, the one you have stays. It doesn't get a tool you never used. |
| [`PIN_DONE`](../troubleshooting.md#pin_done) | You ran `dockingbird pin` with a tool and a version, and it wrote that version into `versions.toml` in your Dockingbird folder. The tool's next start runs it, downloading it first if it isn't there; agents already running keep the version they started with. |
| [`PIN_FOLLOWS`](../troubleshooting.md#pin_follows) | You ran `dockingbird pin --clear`, or `pin` with `latest` or (Claude Code only) `stable`. The tool now follows that release from its next start: for the latest, its line is gone from `versions.toml`. Agents already running keep their version. |
| [`PIN_INVALID_VERSION`](../troubleshooting.md#pin_invalid_version) | The version you gave `dockingbird pin` isn't a release number like `2.1.285`, `latest`, or (Claude Code only) `stable`. Nothing was written. |
| [`PIN_ARGUMENTS_REQUIRED`](../troubleshooting.md#pin_arguments_required) | You ran `dockingbird pin` without a tool and a version, or gave `--clear` a version too. The message shows both forms of the command. |
| [`UPDATE_LOCAL_INSTALL`](../troubleshooting.md#update_local_install) | You installed Dockingbird from a folder on this Mac, so `update` doesn't change its version; it still rebuilds Dockingbird. |
| [`UPDATE_COMMIT_INSTALL`](../troubleshooting.md#update_commit_install) | You installed Dockingbird pinned to one commit (`uv tool install git+...@<commit>`), so `update` doesn't change its version; it still rebuilds Dockingbird. `update --check` says only this. To move on, install the release or commit you want the same way. |
| [`UPDATE_NOT_SET_UP`](../troubleshooting.md#update_not_set_up) | You ran `dockingbird update` before the first set-up. It updated only the command; the first `dockingbird claude` sets up the rest. |
| [`UPDATE_LATEST`](../troubleshooting.md#update_latest) | `dockingbird update` (or `update --check`) found nothing newer: for an install from a release tag, no release tag above the one you installed; `update --check` names that tag. |
| [`UPDATE_AVAILABLE`](../troubleshooting.md#update_available) | `dockingbird update --check` found a newer version. |
| [`UPDATE_RELEASE_AVAILABLE`](../troubleshooting.md#update_release_available) | You installed Dockingbird from a release tag (`uv tool install git+...@v0.1.0`), and `dockingbird update --check` found a newer release tag; `dockingbird update` moves to it. |
| [`UPDATE_FINISHING`](../troubleshooting.md#update_finishing) | You upgraded the command yourself (with uv), so the next command finishes the update by rebuilding Dockingbird. When the output goes to a pipe or a file, the line prints at once and a "still updating to" line follows once a minute while it runs. |
| [`UPDATE_UV_FAILED`](../troubleshooting.md#update_uv_failed) | Getting the latest Dockingbird with uv failed. The message shows the exact command (for an install from a release tag, the install of the newer tag), so you can run it yourself and see why; nothing else changed. For an install from the release index the command ran with this computer's download token, so check the network and `dockingbird license status` instead. |
| [`UPDATE_CHECK_FAILED`](../troubleshooting.md#update_check_failed) | `dockingbird update --check` (or, for an install from a release tag, `dockingbird update`, which reads the source's release tags first) couldn't read the source's versions from the source repository: the network is down, or git on this Mac can't read that private repository over https (the operator guide's Install section gives the one-time git line for it); or the source lists no release tag at all. Nothing changed. For an install from the release index, the index's listing couldn't be read: the network, or a license that is no longer active (the index refuses it); `dockingbird license status` says which. |
| [`UPDATE_SCRIPT_FAILED`](../troubleshooting.md#update_script_failed) | `dockingbird update` got the new version, but the new version couldn't start its rebuild. Nothing was rebuilt. |
| [`UPDATE_MOVING_PYTHON`](../troubleshooting.md#update_moving_python) | `dockingbird update` found Dockingbird's own tool on a Python other than 3.12, as an install made before this change is, and moves it with `uv tool upgrade --python 3.12 dockingbird` before it rebuilds. When the output goes to a pipe or a file, the line prints at once and a "still moving" line follows once a minute while it runs. |
| [`UPDATE_PYTHON_MOVE_FAILED`](../troubleshooting.md#update_python_move_failed) | `dockingbird update` ran `uv tool upgrade --python 3.12 dockingbird` to move Dockingbird's own tool to Python 3.12, and uv failed, or Dockingbird found no uv. Nothing was rebuilt. |
| [`UPDATE_PYTHON_NOT_MOVED`](../troubleshooting.md#update_python_not_moved) | `dockingbird update` moved Dockingbird's tool to Python 3.12, but the moved program still ran on another Python, so it stopped instead of moving it again. Nothing was rebuilt. |
| [`UPDATE_KEEPING`](../troubleshooting.md#update_keeping) | You ran `dockingbird update` while agents are working: before it installs the new version, it keeps a copy of the version they run, which your commands use until they end. When the output goes to a pipe or a file, the line prints at once and a "still keeping" line follows once a minute while it runs. |
| [`UPDATE_MIGRATES`](../troubleshooting.md#update_migrates) | You ran `dockingbird update`, and the new version changes the records Dockingbird keeps. Once it takes over, the version that runs now can't run on them, so Dockingbird can't go back to it if the new one doesn't come up. When Dockingbird can't read which version its records are at, the line says the update may change them, and that it may not go back. |
| [`UPDATE_ROLLING`](../troubleshooting.md#update_rolling) | You ran `dockingbird update`: the new version takes over now, and each agent the line names takes it at its next stopping point, between its turns, keeping its conversation; agents at a terminal keep theirs until their terminal closes. When the update changes Dockingbird's engine too, the agents it names for that restart on it at their stopping points and keep their conversation. `dockingbird status` shows how far it got. Run again for the same version, `dockingbird update` names the agents still to take it, or says that none is waiting. When no working agent is to take it, or none runs, the line says only that the new version takes over now, and, after a rebuild, what is kept. |
| [`UPDATE_NO_ROLL_FLOOR`](../troubleshooting.md#update_no_roll_floor) | You ran `dockingbird update` while agents are working, and the Dockingbird that runs is too old to give its agents a new version in place. The agents, each named with the version it runs, keep it until they end; then Dockingbird switches by itself. Once the new version runs, later updates reach working agents at their stopping points. |
| [`UPDATE_VERSION_UNKNOWN`](../troubleshooting.md#update_version_unknown) | You ran `dockingbird update`, and the Dockingbird running in this home doesn't say which version it is, or says something that isn't a version, so `update` can't tell whether the new version is newer or older. Nothing was read, built, installed or staged. Fix the host, then run `dockingbird update` again. |
| [`UPDATE_DOWNGRADE_RUNS`](../troubleshooting.md#update_downgrade_runs) | You ran `dockingbird update` from a program older than the Dockingbird running in this home while agents are working, each named with the version it runs: an older version can't take over from a newer one while agents work. Nothing was read, built, installed or staged. Once they have ended, run it again; agents at a terminal alone don't stop it. |
| [`UPDATE_IN_PROGRESS`](../troubleshooting.md#update_in_progress) | You ran `dockingbird update` while another `update` on this computer is installing a version or switching to one. Nothing changed; run it again when that one ends. |
| [`UPDATE_SWITCHING`](../troubleshooting.md#update_switching) | Dockingbird is switching to the version `dockingbird update` installed, and your command waits until the switch is done, then goes on. A start can also wait while `dockingbird stop` or `dockingbird clean --all` runs. When the output goes to a pipe or a file, a "still switching" line follows once a minute while it waits. When agents are working, the finished line says the new version took over and that the agents take it at their next stopping point. |
| [`UPDATE_SWITCH_UNDER_WAY`](../troubleshooting.md#update_switch_under_way) | Your command met a newer Dockingbird in the middle of its work, where it can't wait for the switch, so it started the switch and stopped. Run it again once `dockingbird status` shows the new version. |
| [`UPDATE_SWITCH_FAILED`](../troubleshooting.md#update_switch_failed) | The switch to the version `dockingbird update` installed didn't work, so the older version still runs, and your commands with it. Dockingbird doesn't try again by itself; `dockingbird update` shows why and tries again. `status` shows it under "Needs your attention". When the new version, or new code of the same version, changed the records Dockingbird keeps and then didn't come up, the code that ran before can't run on them: fix the cause and run `dockingbird update` again. While agents were taking a new version: when Dockingbird or the code installed here couldn't be read for a long time, the roll stopped, and once the cause is fixed the next command here resumes it; when the new version's code is gone from this home, the roll stopped, and `dockingbird update` installs it again; when the Dockingbird running here was put on other code by hand twice during one update, the roll stopped, and `dockingbird update` rolls it again. |
| [`UPDATE_SWITCHED_UNDER`](../troubleshooting.md#update_switched_under) | Dockingbird switched to the version `dockingbird update` installed while your command ran, so the command stopped; run it again. When it was the start of an agent and the update changed Dockingbird's engine, the agent didn't start and nothing of it was made. |
| [`UPDATE_TWO_PROGRAMS`](../troubleshooting.md#update_two_programs) | Two `dockingbird` programs with different code use this home, such as the one on your path and a checkout's, or the GUI's. The other one switched Dockingbird last, so this one won't switch it back by itself, which would go back and forth. Use one program for the home; `dockingbird update` run from this one switches to it. |
| [`UPDATE_STAGE_UNREADABLE`](../troubleshooting.md#update_stage_unreadable) | You ran `dockingbird update`, and the record of an update staged in this home (`update/stage.json`) can't be read: it was changed, or a newer Dockingbird wrote it. Nothing changed. If no other `dockingbird` program on this computer staged it, move it aside and run `dockingbird update` again. |
| [`UPDATE_SWITCH_OLDER_ENDED`](../troubleshooting.md#update_switch_older_ended) | Dockingbird's log, `dockingbird.log` in its `logs` folder, has this line when an update is staged here while the older Dockingbird's process that finishes an update once the agents end was still running: that process can't read the new update, so Dockingbird ended it and started its own, which finishes the update. Nothing is needed from you. |

## Set

| Id | When it appears |
|---|---|
| [`SWITCH_CODE_UNKNOWN`](../troubleshooting.md#switch_code_unknown) | You ran `dockingbird set NAME --switch-code KEY`, and this home has no Dockingbird code by that key, so nothing was asked of the agent. `dockingbird update` installs a new version's code here and asks the agents to take it. |
| [`SWITCH_NO_SPEC`](../troubleshooting.md#switch_no_spec) | You ran `dockingbird set NAME --switch-code KEY` with a key that changes Dockingbird's engine. Taking such a key restarts the agent in place and keeps its conversation, which needs the note Dockingbird keeps of how the agent started; there is none for this agent's start (it started before Dockingbird kept one), so nothing was asked. The agent keeps the version it runs until it ends, and its next start runs the version installed here. |

## Configs, trust and the agents' own commands

| Id | When it appears |
|---|---|
| [`STATE_FILE_UNREADABLE`](../troubleshooting.md#state_file_unreadable) | `dockingbird mcp install` can't read Dockingbird's `state.json`: it is damaged, too large or not a plain file. Rather than write over it, it recorded nothing: with no `Connected` line before it, no tool was asked; after one (the file changed while that tool connected), that tool stays connected but unrecorded, and no other tool was asked. |
