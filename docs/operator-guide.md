# Operator guide

This page is the long reference for running Dockingbird, one section per topic. The [quickstart](quickstart.md) is the short path through the same steps.

### Install

You need:
- an Apple silicon Mac (or arm64 Linux);
- Docker Desktop, sharing your home folder (its default; it includes the buildx plugin Dockingbird builds its image with, which Docker Engine on Linux gets from Docker's `docker-buildx-plugin` package);
- [uv](https://docs.astral.sh/uv/) (`brew install uv`);
- git at `/usr/bin/git`.

With a license key, install from Zeusfyi's release index: copy the key from your purchase email, then run `UV_INDEX_ZEUSFYI_USERNAME=license UV_INDEX_ZEUSFYI_PASSWORD="$(pbpaste)" uv tool install dockingbird --index zeusfyi=https://license.zeus.fyi/simple/` (on Linux, `read -rs UV_INDEX_ZEUSFYI_PASSWORD` first, paste the key and press Enter, use `"$UV_INDEX_ZEUSFYI_PASSWORD"` in place of `"$(pbpaste)"`, and `unset UV_INDEX_ZEUSFYI_PASSWORD` once uv is done). The key reaches uv in its environment only, never your shell's history or a command line, and uv's record of the install keeps the index's address without it. Then `dockingbird license activate` gives this computer its seat (see "Licensing"); from then on `dockingbird update` reads the index with this computer's activation and needs no key. The index serves an active license only, so a trial can't install from it.

`dockingbird completion --install` adds tab completion; open a new terminal: it writes the completion script for the shell `$SHELL` names (or the one you name, `zsh`, `bash` or `fish`) to `DOCKINGBIRD_HOME/completion/` and adds two lines to `~/.zshrc` or `~/.bashrc`, a comment and one that loads the script when it is there (for fish, the file `~/.config/fish/conf.d/dockingbird.fish` holds them), once however often you run it; the zsh script loads `compinit` itself when your `~/.zshrc` never did, and `dockingbird update` keeps the script current. `dockingbird clean --all` removes the script but not those two lines, which then load nothing; delete them yourself if you like. Never use a bare `uv tool install dockingbird`: that PyPI name is not ours. If `dockingbird` is not found afterwards, run `uv tool update-shell` and open a new terminal. The first `dockingbird claude` downloads about 1 GB, once, and takes about 5 minutes; the first start of each tool then fetches that tool's latest release into the program store and waits for it, `dockingbird start` too, with or without `--json` (see "Tool versions"). To uninstall: `dockingbird clean --all`, then `uv tool uninstall dockingbird`. Uninstalling first would leave Dockingbird's containers, volumes and image behind. Docker keeps the build cache of Dockingbird's image, shared with every other project's; `docker builder prune` frees all of it. The image's Ubuntu packages come from Dockingbird's apt pool, a folder under `~/.local/share/dockingbird/apt-pool/` that holds a copy of the pinned Ubuntu snapshot's files the image installs, one for every Dockingbird home of your user on that computer. Every build checks the folder against the list Dockingbird ships, each file's size and sha256, and reads it alone, with or without Docker's build cache, so it builds while Ubuntu's snapshot service is down. The first build on a computer without the folder (the first `dockingbird claude`, or the first `dockingbird update` after this change) fills it from that service, 441 MB once per snapshot, and says so in one line; when the service cannot be reached then, the build stops and `--verbose` names the folder and the first file it could not get. A copy of the folder from another computer (`rsync`) does as well: a build fetches only the files the folder lacks or holds with other bytes.

### The commands

| Command | What it does |
|---|---|
| `dockingbird claude`, `dockingbird codex` | Start Claude Code or Codex on the repo you are in, each in its own container. The first run sets everything up |
| `dockingbird status`, `dockingbird status claude-1` | Who is working on what, what was shared today, and what needs you; with a name, one agent in detail. An agent that reported on its task and has nothing waiting for it shows idle until `dockingbird stop NAME`, one whose tool says its turn ended, or that it waits at its prompt, shows idle too, and one that asks you something shows "asks you" with how many questions it waits for and `dockingbird questions` (an agent that asked without waiting, `blocking` false, shows working or idle as its hooks say, and its question stays listed under what needs you); `status NAME` lists each of its shares that was not published, with why. It only looks: it never starts anything |
| `dockingbird homes` | Every Dockingbird home on this computer, one line each: each `DOCKINGBIRD_HOME`, the default one included, read back from its coordinator's own `logs` folder, with its folder, its coordinator (running or stopped) and version (a home under `homes/` of the default home is listed by its name, the default home as `default`; a home of that folder with no coordinator yet reads "no Dockingbird started here yet"), and whether its commands would leave its coordinator as it is; a home whose commands would not says whether `dockingbird inspect swarm` reads it ("readable for inspection") and what a command from here would do (see [Reading across versions](#reading-across-versions)); a home whose folder is gone, or whose `logs` folder is not its own, shows no folder. `--json` gives each home's `home` (its folder, or null), `profile`, `version`, `coordinator`, `readable`, `agents_running`, `this`, `default`, `gone`, `name` (its name, or null for a home outside the default home's folder), `inspectable` and `inspect_from`, which the GUI reads. It only reads: it starts, builds and changes nothing, in any home |
| `dockingbird ui` | The Dockingbird GUI (see "The GUI"), built from herdr, mouse first: a tab for each running agent at a terminal, a sidebar row for each agent and one for the inbox, and a command bar for the agent you select; `ctrl+b`, then `d`, then a letter acts on an agent (`n` starts one, `x` stops a working agent and deletes a stopped one after a y, `a` opens its screen, where you answer it), each action showing the `dockingbird` command it runs, and `i` opens the inbox in a tab. It reads Dockingbird again every 2 minutes, and at once on `r`. It has no key that changes an agent's settings or sends it a message: `dockingbird set NAME` and `dockingbird send NAME TEXT` (or `send --all`, `--role ROLE` or `--swarm SWARM` for a group) do. `ctrl+b q` detaches and every pane keeps running. `dockingbird ui stop` stops its server, and `dockingbird ui --install` installs or updates it |
| `dockingbird sync` | Take the agents' commits on the branch you are on, and send them yours |
| `dockingbird login claude`, `dockingbird login codex` | Sign in again, or as someone else; `--api-key` uses an API key instead |
| `dockingbird logout claude`, `dockingbird logout codex` | Sign out in Docker and remove the saved API key |
| `dockingbird update` | Get the latest Dockingbird, Claude Code and Codex, and on a Mac keep an installed Dockingbird GUI at the version Dockingbird pins; `--check` only says whether one is out. With agents running, it gets and builds the new version now, keeps the one they run for your commands, and switches by itself when the last one ends. |
| `dockingbird clean`, `dockingbird clean codex-1` | Free disk space; with names, delete those stopped agents (each one's kept copy, results and history), so `status` no longer lists them; `--all` removes everything Dockingbird made |
| `dockingbird stop`, `dockingbird stop claude-1`, `dockingbird stop claude-1 codex-1` | Stop every agent and turn Dockingbird off, or stop each named agent in turn. Nothing is lost |
| `dockingbird serve convert` | Run, here and as you, what agents ask of a program you connected as a service (see "Folders, databases and services"), one request at a time until Ctrl-C or you close its terminal; `--once` returns after one. The program runs only while this runs |
| `dockingbird watch claude-1` | Watch, or take over, the browser of an agent whose config asks for one (`browser = "chrome"`, see "Delegated agents"): it prints `vnc://127.0.0.1:<port>`, opens it in your VNC viewer (`--no-open` prints the address alone) and prints the VNC password once the viewer connected; the port takes your viewer's connections, from this Mac alone, one at a time, for the life of the watch (macOS Screen Sharing connects once to ask for the password and again to sign in), and no container port is published. Anything you type or paste into that browser is visible to the agent, which reads the page: sign in to nothing you would not hand it. Your Mac's clipboard does not cross: text copied on this Mac does not paste into that browser, and nothing copied there reaches your Mac. Closing the viewer ends the watch a moment later (it waits `WATCH_RECONNECT_WAIT_S` for the viewer to connect again), and so does Ctrl-C; the browser runs on |
| `dockingbird completion zsh` | Print a completion script (zsh, bash or fish); `dockingbird completion --install` installs it for your shell, and `dockingbird update` keeps it current |
| `dockingbird mcp` | The MCP server your own Claude Code or Codex starts, to start and steer agents from it (below); you never run it yourself |
| `dockingbird harbor baseline`, `dockingbird harbor run -a claude-code` | Run a Harbor benchmark task's two baselines (oracle must score 1, nop 0), or one real trial with your own login; `dockingbird harbor jobs`, `dockingbird harbor results JOB`, `dockingbird harbor clean` and `dockingbird harbor version` show, remove and name what ran (see "Harbor benchmark tasks") |
| `dockingbird cp ...` | The fleet's control plane, on the home made for it: `cp init` turns this home into it, given the hub's address, `cp token` makes the bundle a computer joins with, given its label and platform (printed once), `cp status` lists the computers in the fleet and their fleet inboxes, `cp remove LABEL` takes a computer out at once, and `cp off` turns the control plane off once no computer is in it |
| `dockingbird node ...` | This computer's place in the fleet: `node join` reads a bundle from standard input and joins, so each agent started here gets a fleet inbox beside its own; `node leave` leaves once no agent here still uses the fleet. Neither touches a running agent |
| `dockingbird org login HOST --as user --role ROLE`, `dockingbird org status` | This computer's login to your organisation's store, one PostgreSQL role for each kind of command (see "The fleet scheduler"); for an admin, the store itself: `org create` makes it or brings it to this release, and `org projects`, `org roles`, `org people` and `org members` list and change its projects, the model and effort of each kind of role, its persons and their projects |
| `dockingbird license activate`, `dockingbird license status` | This computer's seat (see "Licensing"): `activate` takes one with your license key, asked for and never on the command line, and `trial` starts a trial instead; `status` shows the plan, the seats and the term; `activations` lists the computers that hold the seats and `--release ID` frees one; `deactivate` gives this computer's seat back |

On `claude` and `codex`, `--as NAME` picks the agent's name and `--new` always starts a new one; a name has lowercase letters, digits and `-`, and one that doesn't is a usage error (exit 2) with the name to try instead ("Try: dockingbird claude --as my-agent"). Everything else after the tool's name goes to the tool, as in `dockingbird claude -p "Summarize the open TODOs"` or `dockingbird codex exec "Fix the tests"`; a `--` right after Dockingbird's options is dropped, so `dockingbird claude -- --help` shows Claude Code's own help (no agent starts). `--verbose` adds ids, codes, paths and timings, and `--json` prints JSON for scripts; for `claude` and `codex` they go before the tool's name (`dockingbird --verbose claude`), since everything after it is the tool's. `dockingbird -h` shows the help, as does `-h` after any command (`dockingbird sync -h`), and `dockingbird --version` (or `-v`) the versions. No command needs a state folder, an id or a path.

`--agent-md PATH` and `--claude-md PATH` (also `--agent-md=PATH`), on `claude`, `codex`, `start` and every config's command, give the agent your file as the root `AGENTS.md` or `CLAUDE.md` of its copy: the copy's own file is replaced, or made when the branch has none, before the tool starts, so the tool reads yours and not the repo's, as in `dockingbird claude --agent-md RESEARCH-AGENTS.md`. Your checkout is never touched and the file never reaches a commit: in the copy, git hides it (a replaced file is marked skip-worktree, a new one is listed in `.git/info/exclude`), so `git status` there stays clean and `dockingbird sync` never brings it to you. The file is read on this Mac first and must be a regular UTF-8 text file of at most 1 MB with no Dockingbird credential in it, else nothing starts. Codex doesn't read `CLAUDE.md` at startup, so `dockingbird codex --claude-md PATH` is refused. In a checkout that isn't trusted, `claude` gets your files as its own user memory, so it reads them and not the repo's; a config's command whose repo settings don't load (its `repo_settings` is off, or the checkout isn't trusted) is refused, because Claude reads no instruction file there. In a trusted checkout, Codex is refused a branch that holds `AGENTS.override.md`, which it reads instead of `AGENTS.md`. With `--agent-md`, Claude reads `AGENTS.md` beside a `CLAUDE.md`, and it still reads a `.claude/CLAUDE.md` beside yours. With `--claude-md` alone, Claude reads your `CLAUDE.md` and no longer the repo's `AGENTS.md`, as it does in any repo that has a `CLAUDE.md`; a `.claude/AGENTS.md` is read beside your `AGENTS.md`. An agent keeps the files it started with for its whole life: `--as NAME` picks it up or reconnects with the same files, and another file is refused (start a new agent with `--new` for that). A new agent without the options uses the repo's own files; on a kept copy it puts them back, and a copy of the given file that the earlier agent changed is first saved to Dockingbird's agent logs folder, and the start says where. A commit that adds, changes or deletes the given file is never published, so it never reaches your branch, `dockingbird sync` or a push.

`--skills PATHS`, on `claude`, `codex`, `start` and every config's command, gives the agent skills its tool lists as its own, as a config's `[skills]` does (see **Skills** under [Your own commands (configs)](#your-own-commands-configs)): skill folders, comma-separated, or a skills folder, each path relative to the folder you run the command in, or absolute. `dockingbird claude --skills .agents/skills` gives every skill of that folder, and `--skills .agents/skills/a,.agents/skills/b` those two. A skill it names replaces a config's skill of the same name. A running agent takes more through `dockingbird set NAME --skills PATHS` (see [Delegated agents](#delegated-agents)).

Streams and exit codes: for `claude` and `codex`, Dockingbird's own lines go to stderr and stdout is the tool's, so a redirected one-shot holds only its answer. The other commands print results on stdout and problems on stderr. They exit 0 when done, 1 for a problem Dockingbird printed with its next step, and 2 for a usage error. `claude` and `codex` exit with the tool's own status once it has started, 0 when the agent keeps working without a terminal, and 1 if Dockingbird stopped before starting it. Only `claude`, `codex` and `login` set Dockingbird up (a first `login claude --api-key` sets it up, then saves the key, and the first start after it is an ordinary start, with no set-up line): before the first run, `sync`, `stop`, `clean`, `logout`, the exchange commands (`send`, `inbox`, `read`, `wait`, `results` and `search`), `connect`, `connections`, `revoke` and `disconnect` print status's "Dockingbird isn't set up yet." line, which ends "Start here: dockingbird claude" inside a repo and "cd into a repo, then: dockingbird claude; or, with no repo, sign in first: dockingbird login claude" anywhere else, and set nothing up (`sync`, the exchange commands, `connect`, `connections`, `revoke` and `disconnect` exit 1, as they could not do what was asked; `stop`, `clean` and `logout` exit 0, with nothing to do), while `update` upgrades only the command and says the first `dockingbird claude` will set it up, and `dockingbird clean --all` still removes whatever a failed setup left. Lines wrap to the terminal's width, down to 50 columns for a half-width pane (and at 80 in a pipe or a file), and never inside a command, a size, a duration or a count and its noun: "Get it: dockingbird sync" moves to a line of its own rather than break, as "(1 MB)" and "1 commit" do, an end line too narrow for the pane breaks after its sentence first, "... done" keeps its dots ("Setting up Dockingbird, first time only" over "... done (2 s)"), a command or a path too long for the pane stays whole on its own line, and a message never ends on a fragment of one or two words. When the output is not a terminal (a pipe or a file: a script, an agent, or `dockingbird claude` piped to `tee`), nothing is drawn live: the first setup, an update's uv step and its rebuild, and a tool's download print their heading at once ("Setting up Dockingbird, first time only (about 5 min):", "Getting the latest Dockingbird ...", "Getting the latest Claude Code ..."), then a progress line at most once a minute (`SETUP_PROGRESS_INTERVAL_S`, 60 s) while they run ("still setting up: step 12 of 41, 3 min so far", "still setting up: step 12 of 41, no output for 2 min", "still getting the latest Dockingbird, 2 min so far", "still getting Claude Code 2.1.296: 45 MB of 89 MB, 1 min so far"), then their done line, so a caller can tell a slow setup from a hang; on a terminal the same work is one line redrawn in place. Before the build's first step there is no step to name, so a build Docker never starts gets no progress line until the stall check below stops it. With `--json`, only the final envelope comes. With `--verbose`, each message also shows its ID in brackets on a line of its own, such as `[NOTHING_NEEDS_YOU]`. The ID is the message's heading in [troubleshooting](troubleshooting.md).

With `--json`, every message is one line of JSON: `ok`, `exit_code`, `id`, `lines` (never wrapped), `next_step` when it has one, and `fields`, the values its lines were filled with, so a script never parses a sentence. A help screen is one too (`dockingbird --json -h`, `dockingbird --json help status`): `id` `HELP`, the screen's `lines`, and `fields.command`, null for the top screen. Text is sanitized as on the screen, counts are numbers, sizes are bytes, durations are seconds and lists are arrays. Each `status` row is an envelope of its own: an agent's row adds `name`, `tool`, `repo`, `branch`, `state` (`working`, `idle`, `waiting`, `preparing`, `stopped` or `crashed`), `terminal` (whether a terminal shows it), `next_step` (its reconnect or pick-up command, or null) and `next_argv` (that command's words as an array, such as `["dockingbird", "claude", "--as", "claude-1"]`, when that step is one plain command ending `--as NAME`, which a program can run without a shell; else null: a step that switches branch or changes folder first, a stop, a send with its text still to write, a step in words, or none), `screen` (`tty` when the agent has a screen that `dockingbird claude --as NAME` or `dockingbird codex --as NAME` shows: a running agent at a terminal, and a running agent on the bus that has a screen of its own, see "Its screen." under "Delegated agents"; `none` for any other running agent; null when it has no running container), `container` (its running container's name, or null) and `attach_argv` (the words that show its screen, such as `["dockingbird", "claude", "--as", "notes-1"]`, with the agent's own tool, a config's agent's too, whenever `screen` is `tty`, even while a terminal shows it; else null); a `preparing` row adds `step` (`environment` or `dependencies`), `since` and `last_output_at` (when that step began and when its command last printed, as the agent's own summary wrote them, or null); a repo's heading adds `behind` (the commits you lack; 0 when the heading says nothing, null when behind by an unknown count), `both_moved` (true when you have new commits too, so `sync` merges, false when it fast-forwards, and null when Dockingbird can't tell, as its heading says) and `head` (the agents' published head, the full commit id to compare with `git rev-parse origin/BRANCH`, or null when Dockingbird has no record of the repository); `today`'s row has its `count` and `names`, for example `{"count": 1, "names": ["claude-1"]}`; a kept copy under "Needs your attention" has its row's `state` (`stopped` or `crashed`), `terminal` (false), its pick-up as `next_step` and `next_argv`, and `mode` (`bus` or `terminal`) and `command` (its config's command), as the cache recorded how the agent ran, each null when no record says; and the first line, with the sign-ins, has `claude` and `codex`, each `api-key`, `signed-in` or `none`. Agent names, in `names` too, come in the order the agents started. An agent's end line carries the run's own status: when the tool exits 3, its envelope has `"ok": false` and `"exit_code": 3`, as the process does.

### Your first run and a normal day

`cd myapp && dockingbird claude` does everything once: it first checks the branch you are on, so a branch holding files the agents don't take is refused in seconds, every one of them named, with nothing set up (no image, no Dockingbird, no sign-in; see "Sending yours" below); then it checks the platform and starts Docker Desktop if needed, builds the image (progress lines, live on a terminal; about 5 minutes), starts Dockingbird, and copies the branch you are on for the agents ("Copying myapp (main) for the agents"). The first time, it also downloads Claude Code's latest release into the program store and waits for it ("Getting Claude Code 2.1.296 ..." while it downloads, then its done line; in a pipe, the progress lines described above), as the first start of each tool does, `dockingbird start` with or without `--json` included; `dockingbird --version` names the version once that start has finished. Then it starts `claude-1` in its container. When Claude has no sign-in yet, the start line says so ("Starting claude-1 on myapp (main). Claude will show a sign-in link: open it on this Mac, sign in, then paste the code here. Only this once."; in a pane too narrow for its lines, each sentence starts a line of its own, for Codex too), and its own `claude auth login` runs first, inside the container: open its link on this Mac, sign in and paste the code. Quit the sign-in and the agent ends with "Claude isn't signed in yet. Run dockingbird claude again to sign in." and the API key route, "Or use an API key: dockingbird login claude --api-key": its empty copy is removed, never called work kept, and the next start shows the sign-in again. Codex's first start runs `codex login --device-auth`: open the link and enter the one-time code; quit it and Codex's end line has the same first sentence, then "(If device code login is off, turn it on in ChatGPT's security settings.)" and the API key route. Until a build has been timed, the setup line shows no countdown, only "first time: about 5 min"; later builds count down from the last one's time. When Docker Desktop's Resource Saver has stopped its VM, the setup line says "waking Docker" until Docker answers `docker version` in time (within `DOCKER_WAKE_CALL_S`, 5 s, or, after slower answers on a busy Mac, the slowest recent one plus `DOCKER_WAKE_MARGIN_S`, at most `DOCKER_WAKE_CALL_CAP_S`, 30 s); after `DOCKER_WAKE_TOTAL_S`, 2 minutes, it ends with "Docker is answering slowly." when Docker kept answering too late, and "Docker isn't running." when it gave errors. A build Docker takes but never starts (no output and no context taken for `BUILD_STALL_S`, 2 minutes, before its first step) is stopped and sent once more after that check; a second one ends with "Docker didn't start the build." (Docker Desktop paused or still starting, or a base system that couldn't be downloaded) and the step to check Docker Desktop and the network. A build step that prints nothing for `BUILD_QUIET_S` (1 minute; a download waiting on the network) is named above the setup line by what it downloads ("Downloading Claude Code is quiet (1 min). Still waiting."), the setup line says how long it has waited ("no progress for 3 min"), and after `BUILD_QUIET_CHECK_S` (3 minutes) the note adds "Check your connection or Docker Desktop."; both go once the step moves, and the build goes on. In a pane too narrow for the whole setup line (under about 70 columns), its words show once on a line of their own ("Setting up Dockingbird, first time only (about 5 min):"), with the same estimate the countdown under it starts from, and only the bar stays live; no live line ever reaches a pane's last column. Ctrl-C during the setup ends it with "Set-up didn't finish. Nothing changed. Run this again." If Docker refuses Dockingbird's own `logs` folder ("bind source path does not exist", which Docker Desktop's file sharing says of a folder deleted and made again while it ran), the start says "Docker Desktop can't see ~/.local/share/dockingbird/logs, so Dockingbird couldn't start." and to restart Docker Desktop; when Dockingbird never got as far as writing its log, its refusal shows what Docker said instead of naming a log. Before anything else, a command needs Docker to answer `docker version`: when Docker takes that request and gives no answer within `STATUS_DOCKER_TIMEOUT_S` (10 s), as a Docker Desktop waking from Resource Saver can, "Waking Docker ..." shows while it asks again for as long once more; one that still answers nothing gets "Docker isn't answering. Restart Docker Desktop, then run this again." On a terminal, the last start line is "To leave it working, close this window.", except for a Codex start that waits for Enter (see Trust below), where "Press Enter to open Codex." follows it.

- **Its copy.** Each agent works in its own copy of your branch, from your last commit, mounted at `/work/<repo-name>` in its container (a safe form of the folder's name: `My App` runs at `/work/My-App`). A second checkout whose folder has the same name gets a suffix, and its first start says so before it copies: "Another checkout is already called My App, so this one is My App-2." It never sees your uncommitted edits, and it runs without permission prompts, because the container is its sandbox.
- **Claude's first screens.** Claude starts without its onboarding screens, the theme choice among them: Dockingbird gives it the `auto` theme, which follows your terminal's light or dark background. A theme you pick with `/theme` lasts until the agent's container ends. Your own `~/.claude.json` on this Mac is never read for it.
- **Trust.** Every checkout is trusted unless you mark it untrusted on this Mac with `dockingbird trust --off` (`dockingbird trust` marks it trusted again; `--forget` is `--off` under its older name), or make untrusted the default: a `trust` line at the top of `DOCKINGBIRD_HOME/config.toml`, `trust = "untrusted"` or `trust = "trusted"`, sets what a checkout with no mark is (no line is `"trusted"`); you edit it by hand, there is no command or flag for it. Trust covers the repo's mise config too: its `[env]` and `[settings]` load only in a trusted checkout (see "Toolchains"). A mark decides over the default: a checkout you marked with `dockingbird trust` is trusted and one you marked with `trust --off` is untrusted whatever the line says (the marks are files under `DOCKINGBIRD_HOME/trust/` and `DOCKINGBIRD_HOME/untrusted/`, and a record Dockingbird 0.2.0 wrote in `trust/` for a checkout you trusted counts as its trusted mark). Any other `trust` value, or a `config.toml` that isn't TOML, is refused by every command that reads trust and never read as either default: a start stops before anything runs, `dockingbird -h` and `config list` say it and go on without the repo's own configs. Dockingbird changes nothing in that file but its own build-timer line, `last_build_seconds`, and leaves every other byte as you wrote it; a `config.toml` holding anything of yours stays through `dockingbird clean --all` too (one holding only that line goes), and a fresh or cleaned `DOCKINGBIRD_HOME` holding only your `config.toml` is Dockingbird's to use, so you can set the default before the first start. - **Your newest commits first.** When you have commits the agents don't, the start sends them first ("Sent your 1 new commit to the agents first."). When both sides have new commits, it offers sync's merge on a terminal, and starts nothing without it. An agent in a scratch folder uses no branch, so a pause stops neither its start nor its pick-up.

A bare `dockingbird claude` reconnects to the one Claude on this repo that has no terminal (with two, it lists them). `dockingbird claude --as NAME` reconnects to NAME from any branch or checkout, as status's row says; while another terminal shows NAME, it takes the agent over, and nothing asks: that terminal lets go of it (the agent keeps working, never stopped), leaves the agent's screen, says "claude-2 is now shown in another terminal. It keeps working." then "To show it here again: dockingbird claude --as claude-2" and returns to its shell (exit 0), and this terminal shows the agent with its conversation. (with arguments, "so it can't take these arguments."), then the way to reconnect and, for `--new`, "Or start a new Claude: dockingbird claude --new". A one-shot `--as NAME` pick-up continues the agent's conversation: Claude's `-p` runs after `--resume <id>`, and Codex's `exec` runs as `exec resume <id>`. Nothing new to share."), never "done", and one that shared first and then failed says both ("claude-1 ended with status 3 after sharing 1 commit on main. Get it: dockingbird sync"); a failed tool whose copy is kept is named the same way ("claude-1 ended with status 3. Its copy is kept: dockingbird claude --as claude-1"). An empty copy is removed at once; the agent keeps its name, which `--as NAME` continues (see Names). Empty means by the count Dockingbird takes once the tool and everything it started have ended, and by a second count of its own once the agent's container is gone, so a file written in between keeps the copy: after a crash (the out-of-memory killer, `docker kill`) or a restart, the last count may be older than the tool's last change, so the copy is always kept and the line says so ("claude-1 crashed, ... Its copy is kept and may hold work:"). When Dockingbird refused to start the tool (its sign-in check failed, say), the line says why in plain words and names the copied log ("claude-1 stopped before it started: Claude's sign-in check failed."), never "done", and the command exits 1; `--verbose` adds the refusal's code.

Dockingbird turns itself off after 30 minutes with no agent (`COORDINATOR_IDLE_STOP_S`), and the next command turns it back on. At most once a day (`REPO_MAINTAIN_INTERVAL_S`, 86400 s), the sweep of a start, `sync`, `stop` or `clean` also tidies each repository the agents share: Dockingbird packs its refs and repacks and prunes what nothing reaches, such as a refused import's leftovers, under the repository's lock (`repo maintain`), and leaves a repository alone while a share of it is unsettled or paused.

### Making a repository ready: `dockingbird init`

Run `dockingbird init` anywhere in a repository. It writes `.dockingbird/project.toml`, the project's file: its `slug` (the project's name in your organisation's store: `--project SLUG`, else the name of the repository's `origin` remote, else its folder's; lowercase letters, digits and `-`), the release that wrote it, its rules file, each shipped role's harness, model and effort, and `[lint] forbidden`; `.dockingbird/rules.md`, the lines every agent of the project gets after Dockingbird's own rules; an example swarm in `.dockingbird/swarms/example/` (fill its `[placement] hosts` from `dockingbird fleet hosts`, then `dockingbird fleet submit .dockingbird/swarms/example`); this release's skills in `.agents/skills/`, with the link `.claude/skills` to them, its agent definitions in `.claude/agents/`, and `.dockingbird/skills.lock`, which lists every file it installed with its digest. Keep them in git: `git add .dockingbird .agents .claude && git commit`. A later run changes only what a new release changed: an installed file you edited is kept and named, and `--force` replaces it; `project.toml`, `rules.md` and the swarms are never rewritten. `dockingbird init --check` writes nothing and exits 1 when an installed file is not the running release's, so a repository's own checks can run it; the lock's `release` line only records which release last wrote it and is never judged. `init` writes nothing through a link: a `.dockingbird`, `.agents` or `.claude` that is a link, or a `.claude/skills` that links anywhere but `../.agents/skills`, stops it before anything is written. Last, with an org login on this computer, `init` adds the project to your organisation's store as your `user` role: its slug, the `origin` remote's address, the default branch and this release, once (a later run says the store has it). Only an admin adds a project: a login that is not one, a store that isn't made yet (an admin runs `dockingbird org create`) or a store that doesn't answer is named on that line, and `init` still ends 0. With no org login the line says to log in first (`dockingbird org login HOST --as user --role ROLE`), and `dockingbird init --no-register` skips the step.

### Sync

`dockingbird sync` works on the branch you are on, in the checkout you run it in, and its one-line results name that branch ("My App (feature/notes): up to date."). After a sync that ends well, each other linked branch of the same checkout that lacks the agents' commits gets one more line with the step that takes them: "My App (main) is behind too: git switch main, then dockingbird sync" (or "My App (main) has new commits from the agents too: ...", when you have new commits there as well, or Dockingbird can't tell). It says "too" only when this sync took the agents' commits; after "up to date." or "sent your 1 commit", the line is the same without it ("My App (main) is behind: git switch main, then dockingbird sync"). A branch you made under a deleted branch's name is never called behind there: its line says what `status` says, with the sync that asks first ("My App (feature/x) has a deleted branch's name, so sync asks first: git switch feature/x, then dockingbird sync"). On a branch no agent has worked on yet, sync says so and names those branches the same way, without "too" ("No agent has worked on feature/notes yet." and "My App (main) is behind: git switch main, then dockingbird sync", or "has new commits from the agents"), and says "Start one: dockingbird claude" only when nothing of the checkout waits; it exits 1 either way.

- **Taking the agents' commits.** Their branch arrives as a git bundle, read with `index-pack --strict` into the named ref `dockingbird/<branch>`. When you are behind, sync takes the agents' commits at once: it fast-forwards your branch and names each commit with the agent that shared it, from Dockingbird's own record, never the author field. When you both have new commits, it stops so you can look first: `git log -p main..dockingbird/main` shows theirs. It sends only what this checkout lacks when it can, and the whole history once when that is refused.
- **Turning a commit down.** Don't want an agent's commit? Undo it with a commit of your own: `git revert COMMIT`, then `dockingbird sync`, which sends your revert to the agents. Resetting or deleting your branch doesn't remove it: the agents' copy keeps it, so the next sync brings it back. Made the branch again under its old name and said no to the agents' commits? `dockingbird sync --let-go` asks once, names what goes, and makes yours the branch; the agents' copies keep their work, but a copy built on the commits let go can't share until it syncs onto yours.
- **Your open edits.** Edits you haven't committed stay as they are. Only when the agents changed a file you are editing, ignored files included, does sync change nothing and name the files: commit or stash those, then run it again.
- **Both sides moved.** On a terminal, sync offers to merge theirs into yours ("Merge theirs into yours now? [Y/n]"). Yes runs your own `git merge` with sync's protections and then sends the merge to the agents. A conflict leaves the merge for you to finish, and a merge still in progress stops every later sync and start until you commit it. Without a terminal it shows the same "you and the agents both have new commits" heading and rows, then the look-first command and "When you are ready: git merge dockingbird/main, then dockingbird sync". Ctrl-C at the question merges nothing, prints those two lines and exits 130.
- **Sending yours.** Your commits go to the agents as a bundle (`repo advance` in Dockingbird), only what they lack. A symlink whose relative target stays inside the repo goes to the agents as it is. A branch that would bring in a symlink to an absolute path, one leaving the repo or pointing into `.git`, a chain of symlinks too long or looping, a symlink with an unusable target or in place of a git file, a submodule or a Git LFS file is refused before anything is bundled (and, on a start, before anything is set up), naming each such file with its kind and, for a symlink, where it points ("b-link -> ../../outside (symlink leaving the repo)"): at most 100, the rest counted, and the next ones listed once these are fixed. When the commits sync takes from the agents add a symlink or change where one points, sync notes each one with its target ("Note: the agents added or changed a symlink:"), for you to look at before you build or run anything.
- **Protections on your Mac.** Every git call sync makes in your checkout runs `/usr/bin/git` with a scrubbed environment, hooks off (`core.hooksPath=/dev/null`), fsmonitor off, submodule recursion off, git's automatic gc and maintenance off (so no background repack keeps running in your checkout after sync ends), no transport and `GIT_LFS_SKIP_SMUDGE=1`, so no LFS download or hook an agent chose runs here. Like your own `git pull`, sync follows the agents' `.gitattributes`: a filter or merge driver your own git config defines runs when they name it. When your hooks folder is inside the work tree and the incoming commits change it, sync merges nothing and names the files. When the agents changed `.gitattributes`, `.gitmodules` or `.lfsconfig`, sync shows the new lines: your own later git commands will follow them. Review the agents' commits before you build or run them.
- **Paused.** When the agents' copy of a branch was changed outside Dockingbird, sharing pauses and nothing is lost. `dockingbird status --verbose` shows what changed, and `dockingbird sync --accept 5555555` (the commit sync names) goes on from there.
- **When it can't finish.** A sync that Dockingbird or git could not finish says why and what to do (your checkout moved to another branch while it ran, your branch and the agents' copy share no history, a step took too long or got no answer, the agents' commits are over what Dockingbird takes at once, or your checkout has too many changed or untracked files for it to check), and only an error with no step of yours to take says an unexpected error stopped it (a git that fails is one, never "moved to another branch" or "share no history"); `--verbose` adds the code of either. Such a stop that left your checkout as it was says "Nothing changed."; once sync has merged the agents' commits into your branch (you said yes, and sending the merge was refused as a move), a stop of its next attempt leaves that sentence out and its last line says the merge stays ("The merge of their commits stays. Review: git log -p c91f6c7..main", a command that names the branch, so it shows the merge wherever your checkout is by then). A `dockingbird sync --accept 5555555` that took too long may or may not have gone through: it says so, with `dockingbird status` as the step that finds out, then run it again.

### Status and stop

`dockingbird status` shows every repo and branch, each agent's paths and how long it has been working, who waits for whom, today's shares, how far behind you are (or "you and the agents both have new commits", never "behind", when sync would merge, and "the agents have new commits" when Dockingbird can't tell whether you have new commits too), with a step that runs from where you stand (in a pane too narrow for the whole line, on the next line, two columns in like the rows): `dockingbird sync` for the branch you are on, "git switch main, then dockingbird sync" for another branch of the checkout you run it in, and `cd` to another checkout first, its path quoted as a shell needs, with `git switch` too when that checkout is on another branch (`--json` marks the heading you stand on with `here` and gives the whole step as its `next_step`), and "Needs your attention" for what it can't repair: each agent that stopped with its copy kept, with its pick-up command (the config's command it ran, for an agent that ran one on the bus, else its tool's, as in `dockingbird claude --as claude-1`), which runs from where you stand as a heading's step does ("Pick it up: git switch feature/r7, then dockingbird claude --as keep7" on main; `--json` gives the same `next_step`), a merge left in progress in your checkout, a crash, and a branch whose last start stopped because Dockingbird couldn't make the agents' copy of it, with why and the command that starts it again ("My App (main)   the last start failed 3 min ago: the clone of the agents' copy failed or ran out of time. It only looks: it reads `state.json`, `docker ps` and the coordinator's state, never starts Docker or Dockingbird, and never waits longer than `STATUS_DOCKER_TIMEOUT_S` (10 s). Before the first run it says "Dockingbird isn't set up yet. Start here: dockingbird claude" inside a repo, and how to get to one anywhere else (as `sync`, `stop`, `clean` and `logout` do then, setting nothing up), and while Docker or Dockingbird is off it shows the sign-ins and the kept work from its cache, each copy's pick-up from where you stand (a scratch agent's kept folder is listed once Dockingbird runs); with nothing linked yet (after a first `dockingbird login claude --api-key`, say) it ends with "Nothing is linked yet. Start here: dockingbird claude" inside a repo and "Nothing is linked yet. cd into a repo, then: dockingbird claude" anywhere else, and in a repo with no work kept, with "Start one here: dockingbird claude". In a repo whose branch isn't linked yet and holds files the agents don't take, each of these start steps gives way to "myapp (main) can't be linked yet: it has 3 files the agents don't take. See them: dockingbird claude" (after the first sentence alone: "Dockingbird isn't set up yet.", "Nothing is linked yet." or "No agents are working."): status checks the branch once, read only, within `STATUS_TREE_CHECK_BUDGET_MS` (2 s), and claims nothing when git is slower.

An agent whose container runs and whose tool hasn't started yet is `preparing` until the tool's first sign of life, with the step and how long it has taken: "claude-1   preparing: setting up the environment, {elapsed}" while its container sets up the versions its repo names, and ", no output for {quiet}" after it once the step's command has printed nothing for `BUILD_QUIET_S` (60 s) (`{elapsed}` and `{quiet}` stand for the times it shows, which depend on the repo and the network); an agent started before 0.5.0, or with the image's versions, says "setting up the environment" with the time since its start. `dockingbird status claude-1` adds a `toolchain` row after the model rows: the versions it started with ("Python 3.12.7 and Node 20.18.1", with "(locked)" when the checkout's `mise.lock` names every one of them), or "the image's versions". Under "Needs your attention", a running agent whose repo now asks for another version than it runs says so, with the restart that gives it the new one: "claude-1 runs Node 20.18.1; the repo now asks for 22.11.0. To restart it: dockingbird stop claude-1, then dockingbird claude --as claude-1" (`status` reads this from the agent's record and the repo's last look, which every start and every `dockingbird env` rewrites, and runs nothing); and an agent whose container couldn't set up its environment says that in place of a crash, with mise's last lines and its pick-up ("claude-1's environment couldn't be set up. Its last lines:"; when the checkout is untrusted and its mise config needs trust, it says so and offers `dockingbird trust`).

Under `--json`, every running agent's row (a preparing or retrying one too), and the line of `dockingbird status claude-1`, also carries the figures its supervisor writes in the agent's `summary.json`, after its model, effort and context: `phase`, `turns`, `turn_running`, `last_turn_at`, `last_turn`, `context_window`, `compact_at_asked`, `changed`, `untracked`, `screen_held`, `token_failed`, `sign_in_retry`, `bus_losses`, and the harness's last result, `result_input_tokens`, `result_cache_creation_tokens`, `result_cache_read_tokens`, `result_output_tokens`, `result_cost_usd` (in US dollars; Claude only), `result_turns`, `result_duration_ms` (in milliseconds) and `result_reasoning_output_tokens` (Codex only), each as the tool reported it and never summed (a Codex agent's token figures are its thread's running totals, from its last `turn.completed`, and its `result_turns` and `result_duration_ms`, which Codex names neither of, are the requests its last turn made, read from its rollout, and that turn's wall time), and the cumulative figures of its process (Claude) or thread (Codex): `model_usage`, a list of one object per model it sent requests to (`model`, `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_creation_tokens` and `cost_usd`, each null when it is no figure; a Claude agent's totals count its subagents' and its compaction requests' too, and the cost is Claude Code's own estimate; a Codex agent's are the sums of the requests its rollout records, a request's `input_tokens` being its whole prompt, cached tokens included, where Claude's are the uncached part, with no cost), `compactions`, the compaction events its stream wrote since its process started (Claude) or the compactions its thread's rollout records (Codex), and `api_retries` (Claude only), the API retry events its stream wrote since its process started. A Codex agent's `model_usage` and `compactions` are null until its rollout was read, and its `result_cost_usd` and `api_retries` stay null: Codex names no cost and no API retry in its stream or its rollout. `phase` is the supervisor's word (`starting`, `running`, `exited` or `refused`), never the row's state; `compact_at_asked` is the compact point asked, beside `compact_at`, the point that applies. Each is null, or false for a yes-or-no figure, when the summary holds none (`model_usage` is also null for a list of more than `MODEL_USAGE_MODELS_MAX` models, or one that names a model twice), and the screen shows none of them. Under `--json`, the row of a running agent on the bus (not one at a terminal) also carries four figures for the requests other agents sent it that wait in its inbox, read from the first page of it: `pending`, how many review requests and tasks from other agents are open (pending or accepted; a status note or an alert is no wait, nor anything the host sent, the fleet scheduler's briefs among them; at most `PAGE_MAX_ITEMS`), and, for the oldest of them, `oldest_pending_s` (its age in whole seconds), `oldest_pending_from` (the sender's name) and `oldest_pending_subject` (printable, at most 120 characters); the three of the oldest are null when none waits, and all four are null when the inbox could not be read in time. That row also carries `resume`, how the agent picked up when it continued an earlier session: `native` (its own conversation), `stale` (an older one, since its last session saved nothing) or `packet` (a summary of it, since its conversation could not be restored), else null; the fleet scheduler briefs a `packet` agent again. The screen shows none of them; `dockingbird status NAME` of a bus agent has one row for them, "inbox", such as "2 deliveries waiting, the oldest 6 min from review-1".

`dockingbird stop` asks before stopping working agents (`--yes` skips the question; without a terminal it refuses; any answer but yes prints "Nothing stopped." and exits 1, and Ctrl-C at the question prints it too and exits 130), then turns Dockingbird off and says what it stopped: "Stopped claude-1. Dockingbird is off until you next use it.", or with no agent running, "Stopped Dockingbird. It's off until you next use it." ("Nothing is running. Dockingbird is off." when it was off already). `dockingbird stop claude-1` stops one agent. Its work is kept, and the next `dockingbird claude --as claude-1` picks it up; when its copy is kept on another branch or in another checkout, the line says where and gives the step from where you stand ("keep9 isn't running. Its work is kept in My App (feature/r9)." and "To pick it up: git switch feature/r9, then dockingbird claude --as keep9"), as the restart line and status's notes of an agent that stopped unexpectedly do; after `git branch -m`, each names the branch as it is now, as status does. Every screen that names several agents (status, stop, update, login, logout, clean, the reconnect list) names them in the order they started.

### The fleet probe

`dockingbird fleet probe` reads this Mac and its Docker once and prints what it found, a line per figure: its cores, memory and load against the load line (`FLEET_LOAD_LINE_PERCENT`, 130% of its cores), how busy its CPU is and how many cores are idle, its free and compressed memory and its swap, how busy its GPU is, Docker's CPUs and memory and what Docker's VM holds resident, the containers running and in all, the networks, then each kind of process (agents, coordinators, sidecars, other containers, Docker's VM, the harness host, tests, the system, PostgreSQL, the rest) with its CPU, memory and count. It shows numbers and those kinds only, never a name a program printed. With `--json` it prints one line, whose `fields` hold the whole reading: every container of every home by its id, with its labels and figures, the heaviest process names (`FLEET_PROBE_PROCESS_NAMES_MAX`, 200), the disk Docker's data is on, and `unread`, each part it couldn't read with why (a timeout, an output too large, a shape it doesn't know, no GPU, no Docker, or a failed command), whose figures are `null` there and "unread" on the screen, which then ends with "Not read:" and the same parts. `dockingbird fleet probe --disk` also reads Docker's disk use, which can take a while on a large image store. It only looks, as `dockingbird status` does: it starts, stops and changes nothing, Docker included, gives each read at most `FLEET_PROBE_COMMAND_TIMEOUT_S` (20 s) and stops after `FLEET_PROBE_TIMEOUT_S` (60 s) in all, and ends 0 with whatever it read. It runs on a Mac only, and `dockingbird -h` doesn't list it.

`dockingbird fleet read-home` reads the Dockingbird home it runs under (the default one, or the one `DOCKINGBIRD_HOME` names) once and prints what it found, a line per figure: the home's folder, this CLI's version and whether Dockingbird is ready there ("ready", "not ready" or "not set up"), how many agents the home has and how many are in each state, how many rows wait in its inbox, and its open questions with the oldest one's age. It reads them with the home's own commands, run by the program the home records (as `dockingbird fleet scrape` runs them), for that home in its own folder with nothing else of your environment, so what it reports is the same wherever you run it: `dockingbird status --json`, then, only while Dockingbird is ready there, `dockingbird inbox --all --json` (reading the inbox can start Docker or Dockingbird, so a home that isn't ready gets no inbox read, and its inbox is "unread"), each given at most `FLEET_HOME_READ_TIMEOUT_S` (30 s). It shows the home's folder, numbers and fixed words only, never a name, subject or other text the two commands printed. With `--json` it prints one line, whose `fields` hold the whole read: every agent by name with its tool, state, session, model and effort (asked and reported), context, claims, questions, last error and kept copy, the counts by state of all its agents, listed or not, the open questions, every open inbox row, at most `FLEET_HOME_ROWS_MAX` (200) agents and rows each with the rest counted, and `unread`, the inbox when it couldn't read it, with why (Dockingbird not ready there, a timeout, an output too large, a shape it doesn't know, or a failed command); the screen then ends with "Not read from this home:" and the same part. A home whose folder doesn't exist yet is "not set up", and nothing runs for it. Without the home's status there is nothing to report: it says why and ends 1; otherwise it ends 0 with whatever it read. It starts, stops and changes nothing itself, `dockingbird fleet read-home --disk` is refused (`--disk` is the probe's), and `dockingbird -h` doesn't list it. The fleet's collector will run it for each home.

`dockingbird fleet scrape` prints the figures of each running agent of the home it runs under in the Prometheus text format: the same lines, with the same values, that the agent's container serves at `/metrics` on its port `METRICS_PORT` (9464) inside its own network, which no port of this Mac reaches, under the home's labels: `profile`, then the agent's name (`agent`), its session (`session`) and its tool (`tool`). It reads them from the home's `dockingbird status --json`, run as `dockingbird fleet read-home` runs it (in the home's own folder, with nothing else of your environment, at most `FLEET_HOME_READ_TIMEOUT_S`, 30 s), by the program the home records, the `program` file in the home, which each `dockingbird start` and `dockingbird update` writes (one line: the absolute path of the `dockingbird` script that ran, its links resolved), so one exporter reads every home of a host whatever version each runs, and a home moved to another build is read right after its first start or update there; a home with no such file is read by this command's own script, and a record that is no executable file of yours that nobody else can write is `program-invalid`: the read says so and runs nothing. It writes the text itself, so it connects to no container, and an agent's figures are as fresh as the last ones its container wrote: its last turn's end, its last renewal or its last change, seconds to a minute behind. The page holds each family's `# HELP` and `# TYPE` lines once, then one sample line per agent in the order status lists them, and one `# EOF` line ends it. A kept copy, a stopped or crashed agent and an agent with no session yet print nothing. With `dockingbird fleet scrape --json` it prints one line, whose `fields` hold when it read the status (`read_at`), the home's folder and profile, every agent by name with its session, tool, state and labels (`null` for one that prints nothing), at most `FLEET_HOME_ROWS_MAX` (200) agents with the rest counted, and the text as its lines (`exposition`). A home whose status it can't read, or where Dockingbird isn't ready, has no figures to print: it says why and ends 1. It starts, stops and changes nothing itself, `dockingbird fleet scrape --disk` is refused (`--disk` is the probe's), and `dockingbird -h` doesn't list it.

### Every agent on every host

`dockingbird fleet agents` lists every Dockingbird agent running on this computer, in every home and on every version, with its home, version, mode and whether it has a screen, read from Docker alone: it runs no Dockingbird command in those homes and changes nothing. This computer is `local` in every fleet line, as in the GUI ("local: 5 agents running in 3 homes"; with `--json`, its rows' `host` is `null`), and a fresh install shows `local`, its homes and its agents, from nothing you wrote. `dockingbird fleet agents --host NAME` does the same on another host your `hosts.toml` names, in one call given at most `FLEET_PROBE_COMMAND_TIMEOUT_S` (20 s); one that can't be read says why and ends 1, and a NAME the file lacks is refused with the command that adds it. `dockingbird fleet hosts` lists the file's hosts, or says that none is set and how to add one.

These commands add, rename and forget the hosts of the file:

```
dockingbird [--json] fleet hosts set NAME --ssh DEST [--path PATH] [--docker-host URL] [--home HOME]
dockingbird [--json] fleet hosts set NAME --gcloud VM --zone ZONE --project PROJECT
dockingbird [--json] fleet hosts rename OLD NEW
dockingbird [--json] fleet hosts forget NAME
```

`dockingbird fleet hosts set NAME --ssh DEST` adds a host. It first reaches the host over your own ssh and reads its Docker and its Dockingbird homes exactly as `dockingbird fleet agents --host NAME` reads them, the same call under the same bound, which starts and changes nothing there; only once that read succeeded does it write the host into `hosts.toml`, then it prints the host's rows, as `fleet agents` and the GUI will show them, and says so ("lab: ssh lab.example, saved in ~/.local/share/dockingbird/hosts.toml."). A NAME the file already has is updated the same way ("updated in"): its route is replaced, and its home tables and its place in the file are kept. When the host can't be read, nothing is saved: the command ends 1 with what went wrong and what to try yourself first (`ssh DEST docker version` for a host over ssh), and you run `set` again once that works. NAME is lowercase letters, digits and dashes, at most `TEXT_FIELD_MAX_CHARS` (56) characters, and never `local`, this computer's own name.

DEST is any destination your own ssh reaches without asking, with your own configuration and agent; a host that doesn't answer within `FLEET_SSH_CONNECT_TIMEOUT_S` (15 s) is not reached. For a Mac whose login there doesn't find Docker Desktop's `docker` on its `PATH`, `--path PATH` sets the `PATH` the commands there run with (folders that hold that `docker`), and `--docker-host URL` sets their `DOCKER_HOST`, for Docker Desktop's socket; the ssh refusal says when to add them. `--home HOME` adds a `[[host.home]]` table that names a home of the host by its name (`dockingbird homes` lists them there), without checking that it exists: a home is made by the first command that runs in it, and a second `set` with the same name changes nothing. A Linux host is added the same way, with Docker Engine there.

A Compute Engine VM is added with `dockingbird fleet hosts set NAME --gcloud VM --zone ZONE --project PROJECT` and reached through your own `gcloud compute ssh`; another cloud's VM is a host over ssh. A stopped VM must be started first: `set` can't read it, and its refusal says so, with `gcloud compute ssh VM -- docker version` to try. The `gcloud` it runs is the one on your `PATH`, else one where the Google Cloud SDK installs it; when yours is elsewhere, name it by hand as the host's `gcloud_program` in the file, which a later `set` of that host keeps while the host stays on `--gcloud` and drops, with the other gcloud keys, when it moves to `--ssh`.

`dockingbird fleet hosts rename OLD NEW` gives a host a new name in the file, its home tables kept, and `dockingbird fleet hosts forget NAME` removes its entry and its home tables. They change the file alone: never the fleet pool's records or a swarm definition that names the host (the rename's second line says so); the GUI keeps a host's group folded or open under its new name after a rename it runs. With a `fleet.toml` in your home, each reads the pool before it changes the file and refuses a host the pool holds, since the pool's row keeps the name: drain and remove it there (`dockingbird fleet hosts drain NAME`, then `dockingbird fleet hosts remove NAME`), rename it in the file, then enrol it under the new name; a fleet database that doesn't answer, or turns the login down, ends the command as it ends every fleet scheduler command (69 or 78), the file unchanged. Without a `fleet.toml`, nothing but the file is read.

`hosts.toml` in your Dockingbird home is the record: one `[[host]]` per host, its `name` and one route, `ssh` (with `path` and `docker_host`) or `gcloud`, `zone` and `project` (with `gcloud_program`). It may still be edited by hand. The three commands write it whole (0600) under the lock `locks/hosts.lock`, so a second command meanwhile says another is changing the file and changes nothing; a write keeps every table in its order, but loses the file's comments and the order of the keys inside a table. A home's own program is named by hand: a `[[host.home]]` table under its host (`path`, the home's folder there, and `program`, its `dockingbird`), or a top-level `[[home]]` table for a home of this computer; `set` and `rename` keep them with their host, and the send line below and the fleet worker read them.

A host has one name across your file, the fleet pool and swarm definitions. A pool host is reached under its pool name, its worker's `--host`, so `set` it under that name; and the admitter's home names a gcloud pool host under that same name, since the admitter finds the VM to start by the pool's name in its own `hosts.toml`. A pool host your file doesn't name is in `fleet queue` and not in `fleet hosts` or `fleet agents`, where `--host NAME` of it gives the `set` command that adds it.

The Dockingbird GUI's sidebar runs the same three commands: "add a host…" on its DOCKINGBIRD heading asks for the route, the destination and the name, and for a host over ssh also "PATH for docker there (or empty)" and "docker host URL there (or empty)", its `--path` and `--docker-host`, each optional (an empty answer leaves it out); "rename…" on a host's heading asks "rename OLD: its new name" in a popup that offers the old name (the first key you type replaces it), and "forget…" forgets it once you type `y`; `local` has neither.

`dockingbird fleet attach --container ID` opens one of the agents `fleet agents` lists in your terminal (with `--host NAME`, one on that host): its screen, which you leave with Ctrl-] then Ctrl-\ while it keeps running, or, for an agent with no screen, its log as it grows and a line to send it a message, which runs that home's own `dockingbird send -- NAME TEXT` when `hosts.toml` names that program (`[[host.home]]` with `path` and `program`, or `[[home]]` on this computer). When the log of an agent on another host ends, ssh's own line may follow it: "Connection to NAME closed." The Dockingbird GUI on your Mac reads them too and lists every agent under its host and home; a click opens it the same way. `dockingbird -h` doesn't list `fleet`.

Each agent also shows its state, read from its home's coordinator in the same call: `working`, `idle`, `asks` with how many questions it waits for (a question an agent asked without waiting is not counted), or `unknown` with the reason (`no-coordinator`, `timeout`, `refused`, `unexpected-shape`, `not-read`, `no-session`). The read runs only in the coordinators of homes whose agents run, and changes nothing there.

### Joining a computer to the fleet

A fleet is one control plane and the computers that join it. The control plane is a Dockingbird home of its own, made for the fleet; every other computer joins it from one of its homes with a bundle the control plane makes for that computer, and leaves it the same way. The commands below run on each computer's own host, as every other command does. The word names two things here: the fleet scheduler (`dockingbird fleet ...`, the pool of hosts that places swarms, each host under the name `fleet hosts set NAME` gave it) and the control plane's fleet (the computers that joined with `node join`, each under the label `cp token --host LABEL` gave it); a computer carries both names, chosen apart, so a host the scheduler calls `lab-1` may be `lab` to the control plane, and its agents' fleet sessions carry the label.

```bash
# On the control plane's home, once, with its IPv4 address on your tailnet:
dockingbird cp init --hub-address <ipv4>
# For each computer: the first line on the control plane's home, the second on that computer's home:
dockingbird cp token --host <label> --platform macos|linux
dockingbird node join
# On the control plane's home, at any time:
dockingbird cp status
# To join a computer again (a lost home, a removed computer):
dockingbird cp remove <label>
dockingbird cp token --host <label> --platform macos|linux
dockingbird node leave
dockingbird node join
# Once every computer is removed:
dockingbird cp off
```

`cp init` turns the control plane's home into it, given the hub's address: the IPv4 address on your tailnet at which the other computers reach it. It makes the control plane's key, keeps it on that home's state volume beside the hub's address and configuration, and records its public key; a home already initialized refuses it.

`cp token` adds one computer, given its label and its platform (`macos` or `linux`). The label names the computer in every fleet agent's name it holds: one to eight lowercase letters and digits, starting with a letter. A label a computer in the fleet already holds, or one an agent of the project is named under, is refused. It prints one line, the bundle: the computer's hub, node id, label, key and token, shown this once and stored nowhere on the control plane, which keeps only the computer's public key and its token's digest. Paste it into `node join` on that computer's home, which reads it from standard input.

`cp status` lists each computer on one line: its label, node id and platform, whether it joined, is waiting to join or was removed, its fleet version, how many of its agents have a fleet inbox, and how long ago the control plane last heard from one of them, by the control plane's clock. With `--json`, each computer's line also carries when it joined and when it was removed.

`cp remove` takes a computer out at once, with no precondition: it disables the computer, revokes its token, ends its fleet agents' sessions and names them, and drops the computer from the hub. A computer whose home was lost, or that was removed, joins again with a new bundle: `cp remove`, then `cp token` once more, and on that computer `node leave`, then `node join` with the new bundle. `cp off` turns the control plane back into a plain home once every computer is removed; while one is in the fleet it is refused.

**Before the first computer joins.** The hub listens on the control plane's computer on `NATS_PORT` (4222), which Docker publishes on that computer's loopback only. On that computer, serve the port to your tailnet with the first line below. A member that is not a device of yours on the tailnet, such as a computer in a cloud under a tag, also needs the grant on the second line in your tailnet's policy, with its tag and the control plane's device in place of the placeholders. Frames between computers are as private as the tailnet.

```text
tailscale serve --bg --tcp 4222 tcp://127.0.0.1:4222
{"src": ["tag:<the member's tag>"], "dst": ["<the control plane's device>"], "ip": ["tcp:4222"]}
```

**After the control plane's computer restarts.** The first `dockingbird cp status` on the control plane's home starts the control plane and its hub again, as the first command after a restart starts any home, then lists the computers; the fleet sessions survive as rows, and every member's fleet-link reconnects by itself.

**Updating a fleet.** Update the control plane's home first, then each member, each with `dockingbird update` as "Update" says. Until a member updates, every fleet frame of it is refused with `NODE_VERSION_MISMATCH` ("This computer runs Dockingbird 0.15.2 and the control plane runs 0.15.3, so fleet messages wait until they match."), and its agents keep working on their home, without the fleet.

**What a member's agents get.** On a joined home, `dockingbird start` opens each agent's fleet session on the control plane after the agent's own session and before its container, and the agent gets a fleet inbox there beside its own; its fleet name is the computer's label, a dash and its name. An agent whose tools include `bus_send` gets ten more: `fleet_send`, `fleet_inbox`, `fleet_read`, `fleet_ack`, `fleet_wait`, `fleet_thread`, `fleet_withdraw`, `fleet_artifact_put`, `fleet_artifact_get` and `fleet_whoami`. `fleet_send` reaches a fleet agent by its fleet name, an agent of the control plane's home by its name, or, with no `to`, `parent`, the operator on the control plane's home, where `dockingbird questions` lists a `question` sent to it and `dockingbird answer ROW` answers it. The agent reads both inboxes, the more urgent delivery first, and a choice its tool puts up or a plan to approve is asked on the control plane first and on its own home when the control plane does not take it. When the control plane does not answer at the start, the agent starts all the same and the start says so ("notes-1 has no fleet inbox yet: the control plane didn't answer. It works here as usual and gets one once the control plane answers."). On the member, `dockingbird status` shows under each running agent `fleet: <label>-<name>, heartbeat <age>, asks <n>` (the open questions of its fleet session), `fleet: not open` while its fleet session is not open yet, or `fleet: none`. What does not cross: a home's work, runs, claims and publication stay the home's, a fleet thread and a home thread are two threads, a message sent on one store is never seen on the other, and a home's own `questions` lists none of the fleet's.

**Limits.** A computer's label is at most `HOST_LABEL_MAX_CHARS` (8) characters. An agent's name on a joined home is at most `SLUG_MAX_CHARS` (63) less the label's length and its dash; a start of a longer one is refused with `FLEET_NAME_TOO_LONG`. The control plane's overview lists at most `STATUS_LIST_MAX_ROWS` (100) fleet sessions and says `truncated` past it, in the `Fleet` section of `dockingbird status` on the control plane's home and in `dockingbird cp status`, and a fleet agent it does not list is unknown to a command that names it. A bundle decodes to at most `NODE_BUNDLE_MAX_BYTES` (4096 bytes). A fleet call waits at most `NATS_REQUEST_TIMEOUT_S` (30 s) for its answer, and an agent's own fleet inbox reads and heartbeats at most `AGENT_PERIODIC_RPC_TIMEOUT_S` (10 s). A member's fleet-link finds a silent control plane within (`NATS_PING_MAX` + 1) times `NATS_PING_INTERVAL_S`, 40 s, then reconnects by itself, and fleet calls are refused at once meanwhile. A message to a fleet agent whose home is asleep or offline waits on the control plane's store until that home reads it, at most `PENDING_DELIVERIES_MAX` (200) for one agent. The hub takes at most `NATS_MAX_CONNECTIONS` (1024) connections, one for each member's fleet-link and one for the control plane. A fleet attachment is at most `ARTIFACT_MAX_BYTES` (1048576 bytes).

**A computer in a cloud.** A computer in a cloud that the fleet scheduler places swarms on may join like any other, on four conditions: its credential acts for its own home only, opening fleet sessions under its own label and reading the replies to its own inbox; the credential lives only in `<home>/fleet/container/` and the fleet-link's read-only bind, never in an agent's container, a log or a command line; `dockingbird cp remove <label>` cuts it off at once with no precondition, and `dockingbird node leave` on it removes the credential; and its fleet sessions expire with their hours. A compromised member can send instructions to any agent of the fleet, including ones whose grants reach repositories, and read what is addressed to its own agents, attachments included; it cannot read another computer's inboxes, the harness's sign-in or either database. `dockingbird cp remove <label>` ends it.

### The fleet scheduler

The fleet scheduler queues swarms on the fleet's hosts and admits each where its reservation fits and the host's live gate is green, by priority, then age. Every fleet scheduler command reads this computer's org login first: the org pointer, `~/.config/dockingbird/org.toml` (under `$XDG_CONFIG_HOME` when that names a folder from `/`), which names the fleet database's `host` (the address the hosts reach it at), its `port` and `database` (`dockingbird_fleet` by default), the `project` that the leases of `fleet_admin` count against, and the role each kind of command connects as: `user` for your own commands (`fleet_admin`, the role that owns the fleet database, for its admin, your own login role for every other person, their coordinators and runners included), `worker` for a machine's worker and `admitter` for the admitter. It never holds a password: each role's password is its line of `~/.pgpass` (or of the file `PGPASSFILE` names), PostgreSQL's own password file, which `psql` reads too; that file must be yours and readable by you alone (`chmod 600`), a file anyone else can read is refused, and no refusal ever shows a password. `dockingbird org login db.example.net:5433 --as user --role fleet_admin` writes both, asking for the password without echo, or reading it whole from standard input with `--password-stdin` (a password is never a word of the command line); `dockingbird org status` shows the login and connects once as `user`, and `dockingbird org logout` takes it away (`--as worker` takes one kind's). A command with no org login ends 78, naming `dockingbird org login HOST --as user --role ROLE`; one whose kind has no role in the pointer, or whose role has no line in `~/.pgpass`, ends 78 naming the login to run. Without an org pointer, a command falls back to the `fleet.toml` of your Dockingbird home. If that file holds a `password`, the command refuses it. It connects nothing (`fleet run` runs no command). It names the file and prints the line that moves the login: `dockingbird org login --from-fleet-toml --as worker`. Use `--as user` or `--as admitter` for the other kinds, whichever kind that home's commands connect as. The command ends 78. Running that line reads the file, moves its login into the pointer and `~/.pgpass`, and removes the password from the file after you answer yes (`--yes` where there is no terminal). When both files exist, the command reads the pointer and prints a line saying it ignored the file. Every command opens its own connection and waits at most `FLEET_DB_CONNECT_TIMEOUT_S` (5 s) for the database. Two cases end 69: the database does not answer, or it ends the work for a passing reason such as a restart or too many connections. The command then names the database's host and the role it tried, and quotes the connection's own words for the failure. A database that answers no is a different case: the login or the database's roles are wrong, and the database is up. A wrong password, or a role or database it doesn't have, is refused with that role and the database's words. So is an error code once connected. Both end 78. A refusal sent before the password is asked, because the database's access rules don't list this computer, reads as no answer, with the database's own words on the line.

Install the fleet in the order below, before you run the first fleet command. Step one is the fleet database, on PostgreSQL 18, and its admin role. Run these three statements as the cluster's superuser: `CREATE ROLE fleet_admin LOGIN CREATEROLE;`, `CREATE DATABASE dockingbird_fleet OWNER fleet_admin;` and `\password fleet_admin`. The superuser does nothing else in this install. PostgreSQL 16 and later give a role with `CREATEROLE` the `ADMIN OPTION` on every role it creates, so `fleet_admin` makes, grants, revokes and drops the fleet's groups itself. The fleet's roles log in over TCP with passwords, so the cluster needs two settings. `listen_addresses` in `postgresql.conf` names the loopback address and the address the hosts connect to, on the private network they share. PostgreSQL reads it at its restart. `pg_hba.conf` gets `host` lines for `dockingbird_fleet`, from the loopback address and the hosts' addresses on that network, with the method `scram-sha-256`, PostgreSQL 18's default for the passwords it stores. PostgreSQL reads that file at its reload.

Then its schemas, once per database, as `fleet_admin`: log in as it on the computer you run it from (`dockingbird org login db.example.net:5433 --as user --role fleet_admin`, below), then run `dockingbird org create`. It makes, in one transaction, the `fleet` schema with its row-level security, the `org` schema (the organisation's projects, the model and effort of each kind of role, its persons and their projects), the `work` schema (the organisation's work queue, see "The work queue") and the group roles `fleet_submitter` and `fleet_worker` where the cluster has none yet, none able to log in, and says the store's version, the last migration it carries; run again, it says the store is current, and a role that is no member of `fleet_admin` is refused (exit 77). A fleet database made by an earlier build is upgraded instead, once, after the update, by the role that owns the `fleet` schema's tables (`SELECT DISTINCT tableowner FROM pg_tables WHERE schemaname = 'fleet'` names it): `dockingbird org create` as `fleet_admin` where `fleet_admin` owns them, which applies each migration the database lacks, each in one transaction, and names the version it reached; else the role that owns them applies the migrations, and no customer command does that yet; afterwards `dockingbird org create` says the store is current. A worker or the admitter at a build whose migrations the store lacks refuses to start, naming a migration the store lacks and `dockingbird org create` (`FLEET_STORE_BEHIND`); under its service manager's restart loop such a worker publishes no sample, so after `HOST_STALE_S` (180 seconds) its host is stale and its swarms are interrupted until `org create` migrates the store and the sample returns: run `org create` at the new build before any worker or the admitter restarts at it. A worker or an admitter of an earlier build keeps running against a store a later build migrated, unless that migration's row in [Migrations and older workers](#migrations-and-older-workers), below, says it restarts first. Then restart every machine's worker that runs swarms and the admitter at the new build, and only then use `fleet retire`, `add`, `replace` or `prune`: a worker still at the earlier build reads a retired, retiring, picked-up or held agent as gone and interrupts its swarm. Move the workers first, each publishing one sample at the new build, then the admitter and the submitters: a `fleet submit` at the new build refuses every swarm whose hosts' workers have not yet published their homes' checkouts.

Then the login roles, in `psql -d dockingbird_fleet` as `fleet_admin`: one admin, one login for each machine's worker and one for each person; no project has a login of its own. The admin connects as `fleet_admin` itself, the one login the admin's machines and the admitter share. Each machine of the pool gets its own: `CREATE ROLE "fleet_worker_<host>" LOGIN;`, `GRANT fleet_worker TO "fleet_worker_<host>";` and `INSERT INTO fleet.role_host (role_name, host) VALUES ('fleet_worker_<host>', '<host>');`, `<host>` its name in the pool (its worker's `--host`). Each person gets their own: `CREATE ROLE "<person>" LOGIN;`, then `dockingbird org people add <person> --account <account>` records the person in the store, and `dockingbird org members add <person> --project <slug>` makes them a member of each project they act for. The projects' groups are `fleet_admin`'s to make and to grant: it may grant, revoke and drop `fleet_submitter`, `fleet_worker` and each project's group `fleet_submitter_<project>` it makes. A fleet database made before this release, whose groups the superuser made, needs these lines once, as the cluster's superuser: `ALTER ROLE fleet_admin CREATEROLE;`, `GRANT fleet_submitter TO fleet_admin WITH ADMIN TRUE, INHERIT FALSE, SET FALSE;` and, for each project group it holds, `GRANT "fleet_submitter_<project>" TO fleet_admin WITH ADMIN TRUE, INHERIT FALSE, SET FALSE;`: a group the superuser made gives `fleet_admin` no right to grant it by itself. Give each login its password with psql's `\password` (`\password fleet_admin`, `\password "fleet_worker_<host>"`, `\password "<person>"`), which asks for it and sends only its hash, so the password itself reaches no statement and no server log: paste it from your own secret store, and give it to `dockingbird org login HOST --as user --role ROLE` (or the kind its commands connect as) on each computer that logs in as that role, which keeps it in that user's `~/.pgpass` alone: no TOML file holds it, and `psql` reads the same line. A machine's worker connects as `fleet_worker_<host>`, whose `fleet.role_host` row names that same host. A person acts for a project as a member of its group. `fleet submit` and `fleet run` take the group of the project they act for, `fleet_submitter_<project>`, before they write anything; a person who is not its member, or a project with no group yet, is refused, nothing recorded, naming the person, the project and `dockingbird org members add <person> --project <slug>`, which makes the group when the project has none yet (a project `dockingbird init` registered), and the command ends 77. `fleet_admin` takes no group and acts for any project. Reading the queue and the controls take no group: a person sees and acts on the workloads of every project they are a member of, and of no other. A host's or a project's name may hold `-`, so a role name holding one is written in double quotes.

Each machine and each person then logs in once, as each kind its commands connect as: `dockingbird org login db.example.net:5433 --as user --role fleet_admin --project myapp` on the admin's machines (`--project` where the admin's leases run), `--as admitter --role fleet_admin` on the admitter's machine, `--as worker --role fleet_worker_<host>` for a machine's worker, and `--as user --role <person>` on each person's computers, their coordinators' and runners' included, each with `--database` where the cluster's differs from `dockingbird_fleet` and the address's port where its port does; one login serves every Dockingbird home of that user on the computer, and `dockingbird org status` checks it. A machine's worker also reads `hosts.toml` in its home. The file holds one `[[home]]` table for each home the worker starts agents in. A table names its home in one of two ways. `name` points at the home `homes/<name>` of the worker's user, whose `program` is that home's own program file unless the table names one. The older way is `path`, that home's folder, with `program`, that home's own `dockingbird`. The worker runs that program's `start` there. A third key, `clones`, is optional: an absolute folder where the worker keeps one clone per repository and branch it starts swarms from. `path` may be spelled as the file system folds it. The worker identifies the home by its real path, as the home's own `dockingbird` does, and logs the real path at start when the spellings differ.

Last comes the checkout a swarm starts in. Each home the worker starts agents in links one checkout of the `[source]` repository, on any branch, in a folder whose last part is the repository's name (for `example-org/example-app`, a folder named `example-app`). Sign the home in first if it isn't yet: `dockingbird login claude --here`, with `DOCKINGBIRD_HOME` naming it. Then, in the checkout, `dockingbird start --as fleet-link` links it. Given no task, that command starts an agent that waits and runs no turn. `dockingbird stop fleet-link --yes` stops that agent, and the link stays. From then on the worker starts a swarm in the first of three places that applies. First, a clone of its own of the swarm's branch, when the home's `[[home]]` in `hosts.toml` names `clones` and the clone is already under it (`<clones>/<branch, its slashes dashes>-<7 hex digits>/<repository name>`). Second, the home's linked checkout on the swarm's branch, when exactly one exists. When more than one checkout is on that branch, the swarm is held (`many`). Third, with `clones`, a new clone of its own there. It is made from the checkout the home links on any branch (its objects and `origin`) and fetched over `https` or `ssh` with your own git configuration and credentials (the worker's `HOME`, `PATH` and ssh agent). The swarm's first start links that clone. The pass never places a swarm on a host whose placed home has no checkout of the repository; `fleet why` names the home and `no_seed`. Four cases hold the swarm (`no_checkout`; `fleet why ID` names which): a start that finds no checkout to fetch from, a fetch git refuses (an unpushed branch, a remote your git cannot reach, an `origin` that is a local folder or a `git://` URL), a clone folder it cannot make (a read-only or full disk), and a clone of its own switched to another branch. Fix the cause, then run `dockingbird fleet release ID`. Every start attempt, the one `fleet release` makes included, first fetches and fast-forwards a clone of its own from its `origin`, so a fix you pushed reaches the start; a clone that cannot fast-forward (it holds commits not yet pushed) is used as it is, and the worker's log says so.

`dockingbird fleet submit swarm.toml` checks a swarm definition (its project, key, priority, source, placement and roles, each brief read under the definition's folder) against the pool and queues it: `<id> pending, position <n>`. A definition your project sent before with the same key answers that first swarm instead. A `[[role]]` names a `model` or an `effort` only to override them: `fleet submit` takes each from the role itself, else from the repository's `.dockingbird/project.toml` (`[roles.<kind>]`, when its `harness` is the role's), else from your organisation's store, whose rows `dockingbird org roles` lists and an admin sets with `dockingbird org roles set <kind> --harness claude --model <model>` (and `--effort`), and refuses a role that none of them gives one. A role's kind is its `kind`, any slug, else `reviewer` for a role that reviews, `tester` for one that tests and `implementer` for any other, as the role library's `index.toml` names them; a role whose entry names any of `use`, `instructions`, `connections`, `subagents`, `send_to`, `workspace`, `tools`, `egress`, `allow`, `env` or `skills` (the next paragraph) looks its model and effort up under its own name, then its library role's, its kind and that default. A `[[role]]` may also name `compact_at`, its agents' compact point in the forms a start takes (`500000`, `500k`, or `auto` for the tool's own), `session_hours`, how long each may run (1 to 168 hours), and `min` and `max`, the fewest of its agents a retire leaves and the most an add reaches, each the role's `count` when left out; every agent the fleet starts is started as `dockingbird start --compact-at 500000 --session-hours 48` unless its role names its own point or life (the shipped roles name `300k` for `coordinator` and `hands` and `500k` for the other four), so a long-running agent compacts at half a 1M window instead of being replaced by hand, and lives two days. The fleet admits a swarm once its roles' `min` agents fit its host and starts those; each agent above a role's `min` waits as a `fill` row and starts once its host has room for it, one at a time and before the fleet admits any new swarm, so a running swarm fills up ahead of a waiting one of any priority (a check run is not slowed: swarms never reserve its lease headroom). `fleet submit` refuses a swarm when no home of its placement links a checkout of its `[source]` repository, on any branch, as of each host's last sample (`refused: source: no home of the placement links a checkout of the repository, as of its host's last sample`; a refusal's rule is said in its whole words, on the screen and under `--json`, up to 120 characters, never cut at the screen's text limit): each machine's worker publishes its homes' linked checkouts every `HOST_SAMPLE_INTERVAL_S` (30 seconds). A `[placement]` names a host's home with `home.<host>`, by name as that host's worker publishes it, or by its folder's path. A definition may leave `[placement]` out: its swarm then goes to every pool host that takes swarms, in the pool's order (`dockingbird fleet hosts add NAME --rank N` and `dockingbird fleet hosts policy NAME --rank N`, 1 first; unranked hosts after the ranked ones by name), each in a home of that host that fixes nothing (one with a checkout of the repository first, then the fewest running agents, then by path; a host whose placed home has none is held `no_seed` until it has one); the pass places a swarm on the first host of its placement's order with room, green lines and a seeded home, and only among hosts the placement does not rank on the fullest under `RESERVE_CAP_PERMILLE`. While a swarm runs, the engine watches its reviewers' and testers' inboxes through the home's `status --json`: when a review request or an approved commit has waited `FLEET_WAIT_LINE_S` (five minutes) for one of them, it gives that implementer to another agent of the role that is idle with nothing waiting, telling all three, or else adds one agent of the role within the role's `max` and the host's room; it records each decision (`wait_passed`, `reassigned`, `agent_added`) and never stops, restarts or moves a working agent. A home whose `status` carries no waiting figures is never judged: the engine records `figures absent`. At the first start each implementer is given a reviewer and a tester, round-robin, and every brief's roster names them. `dockingbird fleet queue` shows the pool and the queue: each host's liveness and policy, its sample's age, its cores and memory reserved against what it may reserve with the load of everything the fleet didn't start, and its gate lines with their colours; then each workload not yet ended, in the order the fleet admits them, with its project, priority, state and age, the cores, memory and agents it needs (what its reservation holds), and where it is, why it is held, or what keeps it waiting first. Under a swarm it names the agents still working, the agents waiting to start with the first thing that holds them (the hold's word and the host, from the fleet's latest `growth_blocked` record; "no pass has weighed them yet" before one), and the agents about to start. `dockingbird fleet queue --host NAME` shows one host, and `dockingbird fleet queue --metrics` prints the fleet's metrics in the Prometheus text format instead (the queue's depth by priority, each host's reservations, headroom, red gate lines, staleness and interrupted workloads, and the holds by reason; counters of each host's admissions, starts and seconds of queue wait, and of each role's agent seconds and idle seconds on each host, which only grow, so Prometheus's `rate` gives their means; and each host's fullest home's agents against its agent cap; as the admitter serves them at `FLEET_SCHED_METRICS_PORT`), for the workloads your role can see; it takes neither `--json` nor `--host`. `dockingbird fleet why ID` names, for a waiting workload, the first thing that keeps it off each host with its figures (a gate line's value and bound, what a host has against what the workload needs), and for any other its state and host, and for a running swarm with agents waiting to start, which they are and what holds them, with its figures.

A definition the checkout keeps in `.dockingbird/swarms/<name>/swarm.toml` is submitted by its name from anywhere in the checkout, `dockingbird fleet submit NAME` (a path is still a folder or a file). A submit takes values for the definition: `--set KEY=VALUE`, repeatable, where `KEY` is a parameter the definition declares (`N=4`), a role's setting (`grader.count=6`) or its subagent's (`grader.helper.max=4`), and `--values FILE`, a JSON document of the same shape, `{"params": {...}, "roles": {"<role>": {...}}}`, a role's subagents under its `subagents`; a `--set` beats the file for the same key, and the settings a submit may give are a role's `count`, `min`, `max`, `model`, `effort`, `compact_at` and `session_hours`, its fallback's `harness`, `model`, `effort` and `placement` (`grader.fallback.harness=codex`, or the role's `fallback` object in the values document, each key laid over the role's own table, or making one for a role that names none; a role whose subagent is named `fallback` keeps that subagent's meaning) and a subagent's `model`, `effort` and `max`. A definition may declare `[params]`, each an `int`, a `choice` or a `text` with its default and bounds, and write `{{<name>}}` in its roles' values and texts and in its `key`, `priority` and `[source]` values (`repository = "{{source-repository}}"`, given with `--set source-repository=<owner>/<repo>`; a built-in such as `{{branch}}` is refused there, since those values give it), never in `project` or `[placement]`. A definition without `key` queues a new swarm at each submit, keyed `<name>-<UTC time as YYYYMMDDhhmmss>`, unless `--key KEY` names one. `fleet submit` runs every rule before it stores anything and prints every refusal, one `refused: <field>: <rule>` line each in a fixed order, then ends 1; `fleet queue` and `fleet why` show the values a swarm was given. A role whose `fallback` table's `placement` is `require-login` needs its placement home signed in to the role's tool and to its fallback tool, as of the host's last sample (`signed` or `key`; `not-yet`, and a home whose words the sample did not read, are not): the fleet holds its swarm off a host whose home is not (`no_fallback_login`, judged again at each pass), and a role whose `hosts` pin such a host is refused at submit (`refused: role[N].fallback.placement: a host whose home is not signed in to the role's harness and its fallback's, as of its last sample`); sign in there with `dockingbird login claude` or `dockingbird login codex`. A `[[role]]` may take its settings and texts from a role library: `use = "<name>"` names the project's `.dockingbird/roles/<name>.toml`, and `use = "dockingbird/<name>"` the role of that name Dockingbird ships (`coordinator`, `implementer`, `reviewer`, `tester`, `reader` and `hands`), which `dockingbird init` copies into `.dockingbird/roles/` with the library's `index.toml` (a copy you edited survives a later `init`, as a skill's does); each key the entry gives replaces the library role's, a subagent's table field by field. A role may also name `instructions`, a text its agents get after Dockingbird's own rules and the project's; `connections`, the home's connections its agents are granted at start (the delegated agents' connections), each refused at submit when no enabled connection of the home has that name; a `[subagents.<name>]` table for each helper its harness runs, with the helper's own `model`, `effort` and `instructions` and the `max` of them running at once; `workspace`, `egress`, `allow` and `env`, as a session config takes them, `context`, `kept` or `fresh`, a new conversation for every task delivery of the role's agents (as a config's `context`, "Your own commands (configs)"), and `tools`, `bus`, `full` or a list, which keeps every bus tool (`refused: role[N].tools: drops a tool of the bus set` otherwise); and `send_to`, the roles of the swarm its agents may message beside their parent (`[]` for the parent alone; left out, any agent of the project, as before). A role may also name `skills`, a table as a session config's `[skills]` takes it (`path`, one skill or skills folder or a list of them, each a path from the top of the swarm's source, a library role's too; `into`, `both`, `claude` or `agents`), whose trees every start reads from the swarm's clone, where its agents run, and places as a config's skills are placed. `fleet submit` reads the paths from the top of the checkout the definition is in by a config's rules (no link, no hidden entry, the skills' bounds) and refuses what it cannot read at its key (`refused: role[N].skills.path: not a skills table: path (skill or skills folders of the source checkout), into (both, claude or agents)`, or at `role[N].skills.<name>` for one skill and `role[N].skills` for the set's bounds), as it refuses `skills` in a swarm with no `[source]`, which has no clone; `fleet describe` reads no tree. A start whose clone lacks a path (its branch moved after the submit) holds the swarm (`skills_refused`; the worker's log names the agent, its role, the key and the cause) until you push the fix and run `dockingbird fleet release ID`. A Codex role whose `path` is the clone's own `.agents/skills` lists each skill twice, the placed copy and the repository's; name a folder outside it to list each once. A role may name a fallback too, the keys of a config's `[fallback]` table ("A fallback tool", below) as `[role.fallback]` and `[role.fallback.on]` under its `[[role]]`, or `[fallback]` in a library role's file, whose table an entry's own replaces whole: each key is checked as a config's and refused at `role[N].fallback.<key>`, a `harness` that is the role's own is refused (`fallback-same`), and a `model` or an `effort` the table leaves out comes from the project file's `[roles.<kind>]` when its `harness` is the fallback's, else from your organisation's row for the kind and the fallback tool (`dockingbird org roles set <kind> --harness codex --model <model>`), the role refused when neither gives one (`fallback-model`). The role's config carries the table to each of its agents, which follow its rules as an agent started with that config does. `dockingbird fleet describe NAME` prints, as JSON and connecting to nothing, every parameter and every role's settable field with its type and its bounds or words, and its default with where it comes from (`file`, `params.<name>`, `library` or `project`) when the checkout gives one (a model or an effort it does not give is `required`, from the org store or the submit); it takes no values, so a parameter with no default is `required` too, unless a role's value, `key` or `priority` names it: that one is refused `params.<name>: missing`, as at the submit. Its defaults alone are a values document `--values` takes.

A check run takes a lease rather than a swarm: `dockingbird fleet run --cores 4 --memory 8g --bound 30m -- make test` records a lease of 4 cores and 8 GiB, waits for a host to take it (reading its row every `HOST_SAMPLE_INTERVAL_S`, 30 s, and holding no connection between two reads), then runs `make test` here, in a process group of its own, with `FLEET_LEASE_CORES` and `FLEET_LEASE_HOST` in its environment, and ends with its exit status once it ends, the lease ended with it. `--hosts H,...` names the hosts it may run on, `--wait 10m` how long it may wait (`LEASE_WAIT_S`, 30 minutes, by default; a lease not taken by then is given up, naming what kept it off each host, and ends 1), and `--kind picker --exclusive` keeps a second lease of that kind off the host. Durations name their unit (`90s`, `20m`, `2h`), at most `LEASE_DURATION_MAX_S` (a day). At its `--bound` the command is interrupted, then stopped after `LEASE_KILL_GRACE_S` (15 s), and `fleet run` ends 124; `dockingbird fleet cancel ID` of a running lease interrupts it the same way. On Linux the command runs inside a transient scope of your own systemd user manager (`systemd-run`) whose `CPUQuota` and `MemoryMax` are the lease's (a kill at `MemoryMax` is the command's own status, 137); on a Mac nothing bounds it, and a lease there counts cores only. When the fleet database doesn't answer, `fleet run` says so on one line, naming the database, the role and why, and runs the command without a lease, as checks ran before; when it answers no (a turned-down login, an error code), `fleet run` is refused, ends 78 and never runs the command. Stopping `fleet run` (Ctrl-C, or a SIGTERM from a service manager) interrupts the command's process group too, and the lease ends with it. `fleet_admin` maps to no project, so its leases count against the org pointer's `project`.

The controls take a workload's id: `dockingbird fleet hold ID --reason TEXT` keeps a waiting one out of every pass and `dockingbird fleet release ID` puts it back; `dockingbird fleet pause ID`, `dockingbird fleet resume ID`, `dockingbird fleet cancel ID` and `dockingbird fleet done ID` act on a running team, each of whose agents stops after its running turn, never during it, and the answer names the state entered and the agents still working; `dockingbird fleet set ID --priority P0` changes a priority in any state but an ended one, the workload keeping its age. `fleet retire ID NAME [--reason TEXT]` retires one agent of a running swarm at the first tick of its host's worker that finds it idle with no question open and no request it has not taken yet (one that never started retires at once), and gives its share back to the pool. A request it has not taken yet is a review or task request from another agent that no turn of it has carried, the one `status --json` names in `oldest_pending_from`; a request it took (`accepted`, or carried by a turn) holds no retire or replace: only the agent settles it, and retiring the agent ends that work. A tick that finds the agent working, asking, waiting or with a question open or a request it has not taken yet refuses that ask, records `retire_refused` and sends the agent nothing; the next `fleet retire` of the agent says so first and writes the ask again, and a `fleet retire` of an agent already asked changes nothing and says so. It is refused before anything changes when the swarm is not running, has no such agent, or the role is at its `min` (a `min` of 0 lets you empty a role that neither reviews nor tests; a role that names no `min` keeps its `count`). An agent that hands its parent back `status: done` (a `status` message whose first line is `status: done`) is retired the same way, on its own word: the worker reads each home's inbox once per sample, asks that agent's retire with the reason `handback done`, waits while it works or has a question open or a request it has not taken yet, never takes its role below its `min` (it records `retire_refused` instead), keeps its copy and marks the message read; `status: partial` or `status: blocked` retires nothing, and the fleet sends nothing back. `fleet ledger ID` prints a swarm's ledger, one line per commit, newest first: who approved it and when, and its test line's result, who sent it and when (`none` for a half not seen yet), from the `approved <sha> by <author>: <task>` and `tested <sha>: green|red <lines>` messages its reviewers and testers send their parent, which the worker records and marks read; a line whose sha isn't 40 or 64 lowercase hexadecimal digits, whose author isn't an agent of the swarm or whose result isn't `green` or `red` records nothing. `fleet add ID ROLE [--count N] [--reason TEXT]` adds agents of a role, up to its `max`, under the role's next names, the reason kept on its `agent_added` event; each starts once its host has room, is briefed with the roster, and every other agent is told the new roster. `fleet replace ID NAME` stops an agent at its host's worker's next pass if it runs no turn then and has no question open and no request it has not taken yet, and starts it again by its name, on the tool it runs (its role's fallback tool once it has moved), its conversation kept, with a task naming its brief (a failed or crashed one starts again whatever is open); with `--fresh`, a new agent of its role takes its place under the next name. A running turn, an open question or a request it has not taken yet makes the worker refuse the ask and drop it (`retire_refused`, nothing sent): run the same command again once the agent is idle with neither. An agent whose last turn failed (its `status` row `failed`), or whose process crashed while its container still runs (`crashed`), runs no turn: `fleet replace ID NAME` is its recovery, the product's own (the worker stops it with `stop NAME` and the grow job picks it up by its name with its conversation and its inbox), taken whatever is open; `fleet retire` and `fleet replace --fresh` take it only with no question open and no request it has not taken yet. The engine recovers no failed turn by itself but for the move its role's fallback asks (below). When a swarm is done or cancelled and its branch is merged, `dockingbird fleet prune ID --merged SHA` deletes its agents' kept copies: SHA is the tested head you proved merged in your own checkout (for example with `git merge-base --is-ancestor SHA origin/main`); the engine never checks it, and a commit an agent made but never published goes with its copy. A project's role acts on its own project's workloads only (another project's read as unknown); `fleet_admin` acts on any. The pool belongs to `fleet_admin`: `dockingbird fleet hosts add NAME --os linux --cores 60 --memory 230g --line idle_millicores=4000,8000 --line free_mib=16384,32768 --line psi_io_full=1500,1200` enrols a host of `hosts.toml` with its reservable share and its gate lines (every line its OS requires), `--lease-headroom`, `--agent-cap`, `--rank N`, `--no-swarms` and `--power gcloud` beside them; `dockingbird fleet hosts policy NAME --takes-swarms no` changes its policy or lines, `--rank N` sets its place in the order, and `dockingbird fleet hosts policy NAME --line free_disk_mib=45056,90112` gives it a free-disk line (MiB: the least free disk over its homes and, on Linux, Docker's root; a line for a 60-core VM at an agent cap of 10), which no host must carry, given once the host's sample shows the figure, since a line on a figure its sample lacks is red; `dockingbird fleet hosts drain NAME`, `dockingbird fleet hosts undrain NAME` and `dockingbird fleet hosts remove NAME` take it out of new work, back in, or out of the pool (refused while a workload is reserved on or pinned to it). `dockingbird fleet hosts` with no verb still lists `hosts.toml`. `dockingbird -h` doesn't list `fleet`; `dockingbird fleet -h` shows every action.

Two long-running commands do the fleet's work, each started and restarted by the machine's own service manager and connected as its kind's role in the org pointer (`worker`, `admitter`). `dockingbird fleet worker --host NAME` is one machine's worker, `NAME` its name in the pool: it publishes the machine's sample every `HOST_SAMPLE_INTERVAL_S` (30 s), runs the start jobs the admitter gives this machine, each agent through its home's own `dockingbird start` with the role's limits, then sets each agent's model and sends its brief once, and supervises what it started (the stop after the running turn that pause, cancel and done ask of every agent the home lists alive, whether or not its container is seen; an agent neither listed by Docker nor readable from the home's status waits, unjudged, until the status reads; a memory kill Docker reports; an agent gone). An agent whose process a memory kill ended is picked up while its swarm runs, decided at the worker's next tick and started by a `grow` job, at most `FLEET_DEATH_PICKUPS_MAX` (2) times per agent and swarm: by its name, its conversation kept, while its last context was below its compact point or either figure is unknown, else by a fresh agent of its role under the next name, the share passing to it; at the bound it stays dead and the worker records `pickup_refused`, the swarm running on. An agent that ends at its session life (its role's `session_hours`, else 48 hours) is picked up by its name every time, never read as lost. The worker's homes are the `[[home]]` tables of `hosts.toml`; each home's program is the one its own `program` file names, else the table's `program` line. On a Mac it runs under a LaunchAgent; on Linux under a systemd user unit, with `loginctl enable-linger` so it runs while nobody is logged in. `dockingbird fleet admitter` runs once, on one machine of the pool that stays awake (a Mac under a LaunchAgent with its sleep disabled, or a Linux host under a systemd user unit). It runs the admission pass after each change to the queue or the pool and at least every `HOST_SAMPLE_INTERVAL_S`, and the housekeeping every `HOUSEKEEP_INTERVAL_S` (30 s): stale hosts, stalled workers, expired leases, a stopped `gcloud` VM started when work waits for it. It serves the fleet's metrics, the text `dockingbird fleet queue --metrics` prints, at the org pointer's database host on `FLEET_SCHED_METRICS_PORT`. Both run until stopped. When the database doesn't answer, each ends 69 and its service manager starts it again; when the database turns its login down, each ends 78, and its login needs fixing first (`dockingbird org status`).

A new Dockingbird release reaches a machine's engine in this order, which `dockingbird fleet update` (below) runs on every host of the pool: install it into `installs/<release>/`, run `<installs/release>/bin/dockingbird --home NAME update` from the new install for each home the worker runs, then move `installs/current` to the release and restart the machine's worker and admitter services, which name `installs/current/bin/dockingbird` (kickstart the LaunchAgent on a Mac, restart the systemd user unit on Linux). That update writes the home's `program` file to the install and rolls the home's agents. The worker reads that file first, so it serves the rolled homes meanwhile, within one release of them, and its row reporting the release is the machine's last change: it marks the machine done, which a re-run reads. Restarting the services first would mark a machine done before its homes were updated; this order is safe because a container made before this release never switches, so the first move has no hand-over for an old worker to misread, and from this release on the worker honours a hand-over. The first move to the release that brings this layout points the services at `installs/current/bin/dockingbird` once, by hand (their `ProgramArguments` on a Mac, their `ExecStart` on Linux), with `installs/current` made beside the release folders; from then on `fleet update` moves the link. `dockingbird fleet hosts` says which worker is behind (a worker older than the newest release a home's agents run, or older than what the fleet now writes, which holds it until it is updated) and, per home, which source the worker used for the home's program: `file`, the home's own `program` file, or `table`, the `program` line of its `[[home]]` table, shown with the program, and with the reason the file was refused when the table's program was used instead. The worker reads a home's `program` file first, so editing a `[[home]]` table's `program` line by hand does nothing for a home whose `program` file names another install, until a `start` or an `update` of a newer program rewrites the file.

`dockingbird fleet update` runs that order on the pool's hosts, one after another, in the pool's order (by `--rank`, the unranked after by name), or on the one host `--host NAME` names. It is the admin's alone: a login that is no member of `fleet_admin` ends 77. The release is the one `--release V` names, else this program's own, and its commit is its release tag's, read once from the source by this computer's git ("There is no Dockingbird 0.15.3 to install.", exit 2, when the source lists no such tag). When git here can't read the source at all, it says "Dockingbird couldn't read versions from" the source, exit 1, before anything runs: check the network, and that git on this computer can read that repository, as for `dockingbird update`. Before anything runs it reads each host's newest live worker row: a host whose worker already runs the release is skipped and said; every other needs a live worker row (one beat within `WORKER_STALLED_S`, 3 minutes) that says which homes it serves, waited for at most two samples (60 s) after a worker's start, and a `[[host]]` table in this computer's `hosts.toml` with a `repoint` line: your own command that restarts that host's Dockingbird services (its worker, and the admitter where it runs), run over the host's route as you wrote it, never composed by Dockingbird. Any refusal runs nothing on any host, and ends 2. The services name `installs/current/bin/dockingbird`, the link the command moves, so the line is the restart alone, and it must return without waiting for the services to stop, since a worker's stop can outlast the call's `REMOTE_COMMAND_TIMEOUT_S` (40 s) and a restart that worked would then read as failed: `repoint = "launchctl kickstart -k gui/$UID/<label>"` on a Mac, `repoint = "systemctl --user restart --no-block <unit>"` on Linux. Then, host by host, over the host's route: the release is installed into `installs/<release>/` under the host's data root (`~/.local/share/dockingbird/installs/`), pinned to its release tag's commit, by the `uv` the `[[host]]` table's `path` finds, within `UV_UPDATE_TIMEOUT_S` (15 minutes), and a private source is read with the host's own git credential, since the route forwards no ssh agent; an install whose program already answers the release is kept, and a folder whose program doesn't answer is installed again. Each home of the host's worker runs `update` from that install, in path order, each within `BUILD_TIMEOUT_S` (an hour) plus 330 s, the time a base rebuild and the coordinator's replacement may take; `installs/current` is moved to the release and the `repoint` line runs, each within 40 s; and the command waits for the host's worker to report the release, at most `FLEET_UPDATE_HOST_WAIT_S` (10 minutes). Each step is said as it starts. A step that fails, or a worker that doesn't run the release in time, stops the command, ending 1, with the host and the route's own words; the hosts after it are left as they are and the hosts done stay done, so once it's fixed, run the same command again: it skips the hosts done and repeats the rest, each step safe to repeat. A host's homes finish moving to the release on their own after its `DONE` line, and `dockingbird status` in each of them shows how far it got. This computer, when it is a pool host, is a `[[host]]` with `local = true` and neither `ssh` nor `gcloud`: its lines run here under `sh`, for `fleet update` and for every command that takes `--host`, and `fleet hosts` shows it as `this computer`. A Dockingbird older than this release refuses the whole `hosts.toml` once it holds a `repoint` or `local` key (`FLEET_HOSTS_FILE_INVALID`) until it is updated, so write the two keys on the computer that runs this release; the same `fleet update` restarts that computer's own worker.

### Migrations and older workers

A fleet migration is one named change to the store, which `dockingbird org create` applies and the store records by name. A worker or the admitter of a release refuses to start against a store that lacks one of its build's migrations, naming one it lacks (`FLEET_STORE_BEHIND`), until the admin runs `org create`; a store that names migrations its build does not know is allowed. Each migration's row says whether the workers and the admitter of the release before it keep running against a store it migrated, or restart at its build first, and why: a migration that needs the earlier workers restarted first says so here, and the start-up check then gains a floor.

### The work queue

The work queue is the organisation's board of what is being built, kept in the fleet database as one more schema, `work`, beside `fleet` and `org`, so that a person, a coordinator's hands and a script read and write the same rows from any computer that has the org login. It holds three kinds of row. An item is one unit of work, a feature, a bug, a task, a decision or a program, with its title, its area, its status, its priority and its owner, its ETA and its deadline, the line it is at now and the step it takes next, the items it waits for and, when it waits for you, the ask; every change to an item and every thing that happens to it (a merge, a review, a hand-back, a note) is an event under it, and events are only ever added, so an item's log is its history. An agent's row records one session that works on an item: its task, its role, its model and effort, the item and the pull request it works on, its ETA and why the ETA moved, and, once it ends, its outcome and its result. A request is what an agent asks of the coordinator (a bug it found, a feature, a question or a hand-off, among others), kept with the answers it gets. An item names the fleet's workload that builds it by that workload's id alone. `work` is a command of the host CLI beside `fleet`, and like `fleet` it is not on the top screen: `dockingbird -h` doesn't list it, and `dockingbird work -h` shows every action.

Each `work` action reads this computer's org login first, as every fleet command does (`dockingbird org login db.example.net:5433 --as user --role <role>`, above), connects as the kind `user` unless `--as KIND` names another, and ends 78 naming the login to run when there is none. The queue is read by the admin (`fleet_admin`), by each person's login, through its membership of a project's group (`fleet_submitter_<project>`), and by each machine's worker (`--as worker`). The admin and the people also write it, and so do the coordinators and runners that connect as a person, but a worker only reads, and a write it tries is refused by the database. Each event and each answer records the database login that wrote it, so who wrote a row is read from the row. The schema comes with the store: `dockingbird org create` makes it, with `fleet` and `org`, on a new database; run as the role that owns the `fleet` schema's tables, it applies the migration `0011_work_queue` to a database made before this release, once, after the update, as it applies every migration the database lacks (above), and names the version it reached. Every action takes `--json`, which prints each line as one envelope, and `--as KIND`. A command ends 0 when it did its work, 2 when its words or options are refused before any connection is made, 1 when the store refuses a write, names no such item, agent or request, or the database refuses the login's write (a worker's, `FLEET_NOT_PERMITTED`, as the fleet's commands say it), 69 when the database does not answer, and 78 when its login is missing or turned down.

The commands that read are these. `dockingbird work status`, with `--area A`, `--status S`, `--priority P` and `--all` as options, prints the items in work, those not archived and not in the backlog (`--all` adds the backlog), by priority, then ETA, then id, one line for each with its priority, id, status, owner, ETA and the items it waits for, and under it the line it is at now when it has one, and ends with how many requests are open and how many agents are running (`--area`, `--status` and `--priority` each take one value). `dockingbird work show ID` prints one item's fields, then its events, newest first. `dockingbird work needs-you` prints the items whose status is `waiting-user`, by deadline and then priority, each with the ask it waits on. `dockingbird work check` prints what the schema cannot say by itself, a dependency cycle between items, an agent with no end whose item is archived, a request still open on an archived item, and ends 1 when it prints any. `dockingbird work search TEXT` prints the best 50 hits (`WORK_SEARCH_LIMIT`) over the items, events, agents, requests and answers whose words match `TEXT`, an item whose id or a request whose number is `TEXT` first. `dockingbird work agents` prints the agents that have not ended, each `working` while its ETA is ahead or not set and `past its ETA` after. `dockingbird work requests [--all]` prints the open requests, and with `--all` the answered ones too. `dockingbird work request show N` prints request `N` with its body and each answer it has. `dockingbird work stamp` prints this computer's local time as `YYYY-MM-DD HH:MM ZONE`, the form in which the queue's lines carry a time.

The commands that write record the time of the computer they run on. `dockingbird work new ID --title T --area A --priority P --owner K` makes an item, `ID` its name (a slug), in the backlog and as a feature unless `--status S` or `--kind K` says otherwise, with `--agent ID`, `--project SLUG`, `--observed-at SHA`, `--ask TEXT`, `--depends-on A,B`, `--links L,L`, `--deadline D` and `--now TEXT` to fill in the rest. `dockingbird work log ITEM --kind K --text T` adds one event to an item's log, `K` one of `log`, `merge`, `review`, `launch` and `handback`, with `--pr N[,N]`, `--agent ID`, `--stage S`, `--sha SHA`, `--usd X` and `--ago MIN` (an event noticed late, at most 1,440 minutes ago) beside it, and a `merge` needs `--pr` and `--sha`. `dockingbird work set ITEM FIELD VALUE` changes one field of an item and records the change as an event: `title`, `area`, `status`, `priority`, `kind`, `owner`, `agent`, `project`, `workload`, `observed_at`, `deadline` (a date, a date with a time, or `none`), `depends_on` and `links` (each a comma list that replaces what was), `ask`, `now` (with `--count N --total N --unit U` for a counted step), `next`, and `eta`, which takes only `none` and clears it. `dockingbird work eta ITEM --in 45m --kind estimate` sets an item's ETA that long from now (`45m`, `2h`, `1h30m` and `2d` are the forms), as an `estimate` or as `measured`. `dockingbird work agent start NAME --task T --kind K --model M --effort E` records an agent that has started, with `--item ID`, `--pr N`, `--workload ID` and `--eta 45m` for the item and pull request it works on, the workload whose roster it is in and when it should be done. `dockingbird work agent eta NAME --eta 45m` moves a running agent's ETA, with `--why T` keeping the reason. `dockingbird work agent done NAME --outcome O` records its end, with `--result T` keeping its result. `dockingbird work request new --from X --kind K --title T` files a request, with its body as `--text T` or `--file PATH` and `--to NAME`, `--item ID`, `--priority P` and `--observed-at SHA` beside it, and prints its number. `dockingbird work request info N --text T` adds the requester's own word to a request that waits for more information. `dockingbird work respond N --decision D` answers request `N`, with the answer as `--text T` or `--file PATH` and `--item ID` beside it. A body read from a file, or given as text, is at most 65,536 bytes of UTF-8 (`WORK_BODY_MAX_OCTETS`); a title, an ask, a now line and a log line are one line of at most 1,000 characters (`WORK_LINE_MAX_CHARS`).

The words of a fixed list are a code table of the database, each named after the column that uses it, so a word outside the list is refused by the column's name and the command prints the list. An item's status is `backlog`, `ready`, `in-progress`, `review`, `blocked`, `waiting-user` or `done`; its priority `P0` (now), `P1` (this week), `P2` (soon) or `P3` (when there is time); its kind `feature`, `bug`, `task`, `decision` or `program`; its owner `main` (the coordinating session), `user` (the operator), `agent` (the agent its `agent` field names) or `none`; and its ETA `measured`, `estimate` or `none`. An agent's kind is `coordinator`, `implementer`, `reviewer`, `tester`, `hands` or `reader`, the six roles Dockingbird ships, or `other`, and its outcome is `done`, `partial`, `blocked` or `stopped`. A request's kind is `bug`, `feature`, `question`, `handoff`, `claim`, `progress`, `finish` or `release`, and an answer's decision is `accepted`, `granted`, `refused`, `done`, `needs-info` or `answered`. The commands write an event's kind themselves (`created`, `status`, `eta`, `owner`, `field`, `now`, `archived`, `agent_start`, `agent_eta`, `agent_done`, `request_new`, `respond` and `request_info`), except for the five `work log` takes. An area, a model, an effort and a project are your organisation's own words, never Dockingbird's: an area is a slug (lowercase letters, digits and `-`, up to 63 characters, as a project's name is), a project is the slug of one of your organisation's projects, and a model and an effort are the text an agent was started with. The database keeps its own rules, so every writer meets them. No event is ever changed or deleted: a trigger refuses it, whatever the login, and the submitter role holds no right to either. A request stays open until an answer whose decision is not `needs-info` closes it, and one sender has at most one open request of a title (case ignored): a repeat is refused with the number of the one that is open. An item of kind `bug` names the commit it was seen at (`--observed-at`), as a request of kind `bug` does. An item whose status is `waiting-user` carries its ask. An item that is archived is `done`, and `dockingbird work set ITEM status done` archives it.

A swarm is tracked in the queue from before it is submitted until it is merged, by the coordinator and its hands through the org login of the person they act for, and no commit is made for it. The item for the feature exists before the swarm is submitted (`work new`, or `work set` on one that exists), and when `fleet submit` answers with the workload's id the item takes it, `dockingbird work set ITEM workload ID`, by id alone. Each agent of the roster, whether the fleet or the coordinating session starts it, gets a row with `dockingbird work agent start NAME --task T --kind K --model M --effort E --item ITEM --pr N`, its role as the kind and an `--eta` when it has one, which `work agent eta` moves as the work does. Each merge of a pull request is logged on the item with the pull request's number and the merge commit's sha, `dockingbird work log ITEM --kind merge --pr N --sha SHA`. Each hand-back ends its agent's row: the word of its `status:` line, `done`, `partial` or `blocked`, is the outcome (`dockingbird work agent done NAME --outcome done`). The item's own line, `dockingbird work set ITEM now TEXT` (with `--count` and `--total` for a counted step), is set at each change of state, and its status moves with the work; `dockingbird work set ITEM status done` closes the item and archives it, and it leaves `dockingbird work status`. What is in work, and when each agent ends, is then read from the queue, with `dockingbird work status` and `dockingbird work agents` beside `dockingbird fleet queue`, and never from a folder of files.

### Settings

Dockingbird's runtime settings (the runtime table of parameters: poll intervals, timeouts, page sizes and the like, each a whole number within its bounds) are set in the shell that runs `dockingbird`, as `DOCKINGBIRD_<NAME>`: `export DOCKINGBIRD_DB_QUERY_TIMEOUT_S=60` raises the bound of one database statement for `connect --database`'s check and for the agents' queries alike. Every command passes the settings your shell exports into the containers that read them (Dockingbird itself and each agent), so they take effect there and are never left at their defaults in silence. A value outside its bounds, values that break a rule between settings, a name spelled in another case, or a setting of Dockingbird outside Docker (the database's address and roles, the developer's role switch, the host git's path) stops the command before it runs, naming the variable and never its value; unset it or fix it, then run the command again. A running Dockingbird keeps the settings it started with: after you change one, the next command says "Dockingbird is running with other settings than this terminal's." and names the step, `dockingbird stop`, after which the next command starts it with the new settings; `dockingbird status` shows the same lines under "Needs your attention" and restarts nothing. The settings reach the agents' harnesses too (their Dockingbird MCP server reads them); none is a secret, and `docker inspect` shows them.

### Signing in

Dockingbird uses the Claude and Codex logins already on your Mac. The first start that needs one reads the login Claude Code or Codex uses here (Claude's default profile, the one a plain `claude` uses; Codex's `auth.json`), keeps a copy in the coordinator's store, and follows it from then on; `dockingbird login claude --here` does the same on demand. Claude's login is looked for in three places, in the order Claude Code itself uses them: first a token in `~/.claude/settings.json` (its `env` block's `CLAUDE_CODE_OAUTH_TOKEN`, with the gateway in `ANTHROPIC_BASE_URL` beside it when there is one: a Mac whose Claude Code signs in through a gateway), then the Keychain item, then `~/.claude/.credentials.json`. From the settings file only those two values are read, and only from a file of yours that others cannot write; every other setting is left unread. The gateway must be an `https://` address, or an address of this Mac itself: Dockingbird sends a token only to an `https://` gateway, except when Claude Code here sends its requests to a gateway on this Mac (a loopback host, `127.0.0.1` or any `127.x` address, `localhost` or `[::1]`, with any port and path, such as a proxy of yours at `http://127.0.0.1:59471`), which may be plain `http://`: an agent's Claude then sends its requests to that same gateway with the same token, reaching it as `http://host.docker.internal:PORT` (Docker Desktop's name for the Mac seen from a container; the scheme, port and path are kept), whichever login Dockingbird follows, a settings token, the Keychain item or the login file. Any other plain `http://` gateway is refused by name ("This computer's Claude login goes through http://..., and Dockingbird sends a token only to an https:// gateway. Nothing changed."), and nothing is followed until Claude Code here points at the gateway's `https://` address. A gateway on this Mac is reached only through Docker Desktop on a Mac: on Linux a settings token sent through it is refused by name ("This computer's Claude login goes through http://127.0.0.1:59471, this computer's own address, which agents reach only through Docker Desktop on a Mac. Nothing changed.") and nothing is followed, while a login file beside it is followed without the gateway, which `dockingbird status` names as one the agents don't use; and an agent in the `allowlist` or `models` egress mode cannot reach it either (its proxy admits no address of this computer), so such a start names the gateway and the mode and starts nothing: point Claude Code here at an `https://` address agents can reach, or start the agent in the `full` egress mode (`dockingbird start --egress full`). Beside a Keychain or login-file sign-in, a gateway elsewhere is not followed, and `dockingbird status` says so ("Claude Code here sends its requests through https://..., which the agents don't use"). A changed gateway reaches the store the moment it lands and the next start uses it; an agent already running keeps the gateway it started with. The copy of a Keychain login or a login file leaves out its refresh token; the copy of a settings token is the token and the gateway, which an agent's Claude then uses exactly as your own `claude` does (`dockingbird status` then says "Claude uses this computer's login through https://...", or, for a gateway on this Mac, "Claude uses this computer's login through http://127.0.0.1:59471 (agents reach it at http://host.docker.internal:59471)."). Nothing on your Mac is written, copied or mounted for it: nothing under `~/.claude` but that one read of `settings.json`, not `~/.claude.json`, not `~/.codex`, not the Keychain; the refresh token never leaves your Mac, so no agent can renew or sign out your login, and your own Claude Code and Codex stay the only programs that refresh it. Each tool can also sign in separately, inside Docker, with its own command (`dockingbird login claude`), which then wins until `dockingbird logout claude`.

- **Where the sign-in lives.** Each tool's volume (`dockingbird-home-claude`, `dockingbird-home-codex`) holds its credentials store, `creds/`, and the saved key; both volumes are mounted into the coordinator (`/dockingbird/home/<tool>`) and into the login, tool-help, put and seed containers Dockingbird itself runs, never into an agent. Each agent's tool runs with a private HOME on its container's own volume (`/tmp/home`, on `/tmp`, which no other container mounts); at its start the agent asks the coordinator for its tool's sign-in, saved key and (Claude) its state record, which the coordinator issues under the session's grant, so nothing another agent writes reaches the HOME a tool loads its settings, hooks or plugins from, and no agent can read another tool's secret.
- **Refreshing.** For Claude, one live session at a time holds the sign-in's refresh lease (the coordinator's holder file): it receives the full credential and is the only one whose refreshed sign-in the coordinator accepts back. Every other Claude session gets a copy without the refresh token, so two copies of a rotating token never invalidate each other; a session started while the holder is still signing in waits for its sign-in however long that takes, and stops only if the holder ends without one. Each Codex session receives the whole `auth.json` and sends it back when it changes, and the last writer wins. A running session picks up a sign-in another session stored back (and a change of Dockingbird's copy of your Mac's login, below): an agent working without a terminal gets the new copy within one heartbeat (about 20 seconds), and Claude restarts between two tasks to use it, resuming its conversation, while Codex's next task reads it; an agent in a terminal gets the new copy within one heartbeat as well, and its Claude Code reads it at its next request. Picking up a copy never makes a session the refresh holder: once the holder ends, the next start holds the lease.
- **Your Mac's own login.** `dockingbird status` says when a tool uses it. It is renewed on your Mac by Claude Code or Codex themselves (or by a tool of yours that rewrites the default profile's login, which Dockingbird follows the same way); while Dockingbird is on, it copies the change the moment it lands: a background watcher that every command starting or using Dockingbird leaves running (one per Dockingbird folder, alive while Dockingbird runs, ended when it stops) waits on macOS's change notification for the login keychain's file (`~/Library/Keychains/login.keychain-db`), Claude Code's settings file (`~/.claude/settings.json`, for a changed token or gateway) and the login files (`~/.claude/.credentials.json`, `~/.codex/auth.json`), confirms a notification by the item's attributes (`security find-generic-password` without `-w`, never the secret) or the file's metadata, and copies the changed login into the store at once (well under a second), with no command and no polling. A login tool of yours is followed when it rewrites the Keychain item or replaces the login file by rename; a link left in its place is refused. A changed settings token or gateway reaches the store the same way; an agent already running keeps the token and gateway it started with, and the next start uses the new ones. A login folder that isn't there yet (`~/.codex` before Codex's first run) is watched for through the folder it goes in, so a first login is copied the moment it lands too. The backstops stay: Dockingbird also picks the renewal up at its next command and every minute while an agent runs in a terminal or your own Claude Code's Dockingbird connection is open, and running agents take it up as described under Refreshing (one in a terminal too). A change the watcher saw but couldn't copy shows in `dockingbird status` ("Dockingbird couldn't update its copy of Claude's login 3 min ago: the login here couldn't be read. The agents keep the earlier copy.") and in `dockingbird.log`; on Linux there is no watcher and the interval reads alone apply. If macOS asks whether security may read the login, choose Always Allow: otherwise it asks at every read, once a minute while an agent runs in a terminal. `dockingbird logout claude` stops following it (Dockingbird then has no Claude login until `dockingbird login claude --here` or a separate sign-in). A Claude agent whose copy expired before Dockingbird's next command fails its turn and says so; the next command renews Dockingbird's copy, a new start uses it, and an agent working without a terminal takes it up before its next task; an agent in a terminal reads the renewed copy at its next request. A start on a login that expired here, or that you signed out of here, says so and starts nothing until the login is renewed on your Mac. Dockingbird reads your login only from a shell whose `HOME` is your home folder; from any other it reads nothing and keeps the copy it has. Dockingbird's copy stays valid exactly as long as your own login does: it carries no refresh token, so your own Claude Code or Codex renews it by being used. An agent that must outlive your login signs in for Dockingbird only: `dockingbird login claude`.
- **Reusing a sign-in you made elsewhere.** Run `claude setup-token` in a terminal, copy the token it shows, then `pbpaste | dockingbird login claude --oauth-token -` (and `pbcopy < /dev/null` to clear the clipboard); `cat ~/.codex/auth.json | dockingbird login codex --auth-json -` keeps a Codex sign-in from a file. Both read the value from the pipe only, and the value never appears in a command line, a log or a file on your Mac. A Claude token is the subscription's credential, not an API key: `status` says "signed in", and in a trusted checkout the repo's own settings load for it as for a sign-in. The last login wins: either form removes that tool's saved API key. Both refuse while that tool's agents run, as a sign-in does.
- **Signing in again.** `dockingbird login claude` or `dockingbird login codex` runs the same sign-in in a login container, for an expired or revoked sign-in or another account. It refuses while that tool's agents run. A sign-in that does not finish changes nothing and names the API key route: "Or use an API key: dockingbird login claude --api-key". To quit a sign-in, press ctrl-C: the login container passes it to the tool and waits for it to end, so only those two lines follow, on a line of their own after the terminal's `^C`, never a traceback.
- **Codex.** If Codex's device-code sign-in doesn't finish, turn on device code login in ChatGPT's security settings. If Codex asks you to sign in again while it runs, choose its device-code option, or quit and run `dockingbird login codex`.
- **Signing out.** `dockingbird logout claude` and `dockingbird logout codex` remove that tool's sign-in and saved API key from the coordinator's store (with neither there, "Claude wasn't signed in. Nothing to do.", exit 0); both refuse while that tool's agents run, and both need the coordinator (they start it if it is off). A sign-out revokes nothing at Anthropic or OpenAI (Claude's own `claude auth logout` is no longer run), so if an agent may have copied the sign-in, also sign out in your account.

### API keys

`dockingbird login claude --api-key` asks for an Anthropic API key (hidden), or reads it from stdin without a terminal; Ctrl-C at the question says "No key was saved. Nothing changed." and exits 130. `dockingbird login codex --api-key` does the same for OpenAI. With `--api-key`, `--base-url URL` (an `https://` gateway) sends that tool's requests there, for either tool: Claude takes it as `ANTHROPIC_BASE_URL` in its managed settings, Codex as `openai_base_url` in its `config.toml`. It goes with Claude's token too: `pbpaste | dockingbird login claude --oauth-token - --base-url URL` saves the token and the gateway together, and an agent's Claude then sends its requests there with that token. Give Codex's URL in `OPENAI_BASE_URL`'s form, ending in `/v1`, after which Codex adds `/responses` and `/models`; Claude's is the origin, after which Claude adds `/v1/...`.

- The key goes from the prompt, through a put container's stdin (`--network none`), into the volume's `.dockingbird/keys`, 0600. It is never in an argv, a container environment, `docker inspect`, a log or a file on your Mac.
- Agents mount no tool volume: an agent asks the coordinator for its own tool's key at its start, and the coordinator issues it under the session's grant, so an agent can neither change the key nor read the other tool's.
- Claude reads it through its `apiKeyHelper`, `dockingbird-claude-key`, which asks the coordinator and prints the key and nothing else. Codex takes it with `codex login --with-api-key`, on stdin.
- The last login wins: a plain `login` after `--api-key` removes the key once the sign-in succeeds, and `--api-key` replaces the sign-in. While a key is saved, `status` says "Claude uses an API key".

### Your own rules

Agents get Dockingbird's built-in rules for the coordination tools. To use your own, write `~/.local/share/dockingbird/instructions/claude.md` or `codex.md`. Dockingbird copies a changed file into Docker the same way as a key, read-only to agents, and never mounts it.

A repository's own rules reach every agent started in it: the file `[rules] file` in `.dockingbird/project.toml` names (`.dockingbird/rules.md` when the key is unset) is read from the checkout at each start and given to the agent after Dockingbird's rules and before a config's own instructions, Claude and Codex alike. A rules file the project names that is missing, a link, not UTF-8 text or holding a Dockingbird credential stops the start, and so does one that makes the agent's rules longer than `INSTRUCTIONS_MAX_BYTES` (64 KB). In a repository you marked untrusted (`dockingbird trust --off`) it is not read.

### Update

`dockingbird update` installs the newer release with uv (found in an absolute `PATH` entry) into a folder of its own, `~/.local/share/dockingbird/programs/<version>/`, and points your `dockingbird` command at it with one rename, so a command you start during an update runs whole, on the old release or on the new one; then the new release puts its code into the home's code store, builds the image only when the image's base changed (see "Rolling updates") and swaps the coordinator, rolling back to the old one if the new one doesn't become healthy (an update that moves Dockingbird's PostgreSQL to a new major upgrades the home's database at that swap, in seconds, and, like a records change, can't go back once done), then fetches the latest release of each tool you have used into the program store and says so per tool ("Claude Code 2.1.296 is the latest." or "Got Claude Code 2.1.296."; a tool you never used is not fetched; see "Tool versions"). An install still on Python 3.14 (any made before Dockingbird moved to Python 3.12) moves to Python 3.12 at its next `dockingbird update`: installed from a release tag, from the default branch or from the release index, it is installed into its own folder on Python 3.12 and runs from there; installed from a branch by name, the update, with no agent running, runs `uv tool upgrade --python 3.12 dockingbird` after the upgrade and before the rebuild ("Moving Dockingbird to Python 3.12 ..."). Run that first update with no agent running, because the agents' running commands keep only the parts of Dockingbird they had already loaded. When it replaced Dockingbird, it ends with "Dockingbird 0.15.3 is installed and takes over now." and, after a rebuild, what it kept: your repos, their history, and only the sign-ins and saved API keys there are ("Dockingbird 0.15.3 is installed and takes over now. Your repos, history and your saved Claude API key are kept."); with nothing to change, it says so ("Up to date.", or, installed from a release, "Dockingbird 0.15.3 is the latest. Nothing to do."). With agents running, the new version takes over at once and each agent takes it at its next stopping point, keeping its conversation: see "Rolling updates". While another `update` is installing or switching, it is refused ("Another dockingbird update is under way here."). Installed from a folder on this Mac, it rebuilds only when the image is out of date. Before the first run there is nothing to rebuild: it upgrades only the command (installed from a folder, it says it stays at its version), then says "Dockingbird isn't set up yet; the first dockingbird claude will set it up." and exits 0, setting nothing up. When uv fails, it names the exact command it ran, so you can run it yourself. `dockingbird update --check` only says whether a newer version is out. On a Mac, `update` then installs the Dockingbird GUI the new Dockingbird pins, as `dockingbird ui --install` does, when none is installed (`DOCKINGBIRD_HOME/bin/dockingbird-gui`) and Dockingbird is set up, or puts it in place of one that is another version, gives no version or can't start. The GUI is fetched with git over SSH from its private repository, so this step can fail, as without git or without SSH access to that repository; when it fails, Dockingbird itself is already updated and has said so, and `update` ends with the refusal and its next step, `dockingbird ui --install`, and exits 1 (see "The GUI"). On any other computer, such as a cloud VM, no GUI runs: `update` downloads none, says nothing of it and leaves one already there as it is, and `dockingbird claude --as NAME` there still shows each agent's screen. Then each tab completion script `dockingbird completion --install` wrote in `DOCKINGBIRD_HOME/completion/` becomes the new version's, and `update` says so for each one it rewrote ("Updated tab completion for zsh:" and its path); your shell's startup file is never touched.

Your first `dockingbird update` after the install line moves your command into its program folder. A `uv tool upgrade dockingbird` of your own that gets anything new, or the install line run again, puts it back on uv's own folder until your next `dockingbird update`, and `dockingbird clean` removes the program folders that no home names and no running Dockingbird uses. After a `uv tool upgrade dockingbird` of your own, the next command finishes the update: it switches Dockingbird and waits for that switch ("Switching Dockingbird to 0.9.1 ... done"), and a command that meets the new version in the middle of its work stops instead ("Dockingbird is switching to 0.9.1, so this command stopped."), to be run again once `dockingbird status` shows it; with agents running, the home rolls, as "Rolling updates" says. When the upgrade keeps the version (a newer commit of the same release), no command switches Dockingbird by itself: `status` says the code differs ("This program's code differs from the Dockingbird 0.9.1 running here. To switch to it: dockingbird update"), an agent you start runs the code installed here and says so once ("This agent runs the Dockingbird 0.9.1 installed here, not this program's code. To switch to this program's code: dockingbird update"), and `dockingbird update` from the upgraded program switches it. Two `dockingbird` programs with different code on one home (the one on your `PATH` and a checkout's, or the GUI's) never switch it back and forth: the last switch is noted in `DOCKINGBIRD_HOME/update/`, and a program whose code that switch replaced won't switch the home back by itself ("Another dockingbird program with different code switched this home last, so this one (0.9.1) won't switch it back by itself."); a typed `dockingbird update` decides, and switches to the program you run it from.

### Rolling updates

Dockingbird's own code no longer lives in its image: each release's code goes into the home's code store (a Docker volume), and every container runs the code it was started on, so an update builds the image only when the image's base changed: its operating system, its toolchains, its locked Python packages or its launcher. With agents running, `dockingbird update` puts the new code in the store and starts a background process that replaces Dockingbird's coordinator at once, then asks each running bus or screen agent on other code to take the new code at its next stopping point. `update` names them ("Dockingbird 0.15.3 is installed and takes over now. claude-1 and codex-1 take it at their next stopping point."), after saying, when the new version changes Dockingbird's records, that there is no way back once it takes over ("This update changes Dockingbird's records. Once it takes over, it can't go back to 0.15.2."). An agent switches in place: the same container, the same session and the same conversation, which its tool resumes; its deliveries, held notices and open questions are kept, and before its next prompt, at no cost of a turn, its tool is told ("Dockingbird updated from 0.15.2 to 0.15.3 and resumed your conversation. Continue where you were."). Your agents keep working while the coordinator restarts: their calls are retried through the gap, the claims they hold don't expire because of it, and a question an agent asks meanwhile is retried for a few minutes before the agent is told to ask it again. A command you run meanwhile waits for the coordinator's switch ("Switching Dockingbird to 0.15.3 ..."), minutes at most, never for the agents. Any command of a newer `dockingbird` rolls a home the same way and says so ("Dockingbird 0.15.3 took over. The agents take it at their next stopping point."); a `dockingbird` of the same version with other code, such as a checkout with a local commit, rolls nothing until you run `dockingbird update` from it.

An agent switches only at a stopping point, never inside a turn or a tool call, and no turn is ended for it. A Claude or Codex agent on the bus stops between two turns, when no turn runs; a screen agent at its open gate, once the person's turn has ended; an agent at a terminal never, since a person is at its screen: it keeps its code until its terminal closes, and `update` never asks it. A turn running when the ask comes ends on its own, or at its `turn_minutes` deadline when its command set one, and the agent switches after it. A Claude agent whose own background work (a background command, a subagent or a monitor) still runs when it goes idle waits for that work, up to `SWITCH_BACKGROUND_WAIT_MAX_S`; past it the switch ends the work, and the resumed agent is told that it may have been ended ("A background command of yours may have been ended by the update; check its effect before you run it again."). An agent asked to stop after its turn ends as asked and never switches.

While a roll runs, `dockingbird status` says how far it got ("Dockingbird 0.15.3 is taking over: claude-1 and codex-1 take it at their next stopping point.") and, beneath, what holds an agent back: an ask an idle agent hasn't answered yet ("claude-1 was asked to take 0.15.3 12 min ago and hasn't answered yet."), a turn it is running, at whose end it switches ("claude-1 takes 0.15.3 at the end of its turn (asked 2 min ago)."), background work it waits for ("claude-1 takes 0.15.3 once the work it runs in the background ends (waiting 5 min; at 30 min at the latest)."), an agent at a terminal ("claude-2 on 0.15.2 keeps its own until its terminal closes."), an agent already on a newer Dockingbird, which is never asked to move ("claude-3 on 0.15.4 is newer and keeps its own until it ends."), and an agent that couldn't take it, with why ("codex-1 on 0.15.2 couldn't take 0.15.3 (its restart command was refused) and keeps its own until it ends."). An idle agent that leaves its ask unanswered for `SWITCH_ASK_ANSWER_MAX_S` is left on its code ("claude-1 on 0.15.2 didn't answer the ask for 0.15.3 in 10 min while idle and keeps its own until it ends or answers."). An agent Dockingbird couldn't ask for `SWITCH_ASK_ANSWER_MAX_S` is left on its code and asked again at every check ("claude-1 on 0.15.2 couldn't take 0.15.3 (Dockingbird couldn't ask it) and keeps its own until it ends."). Run again for the same version, `dockingbird update` changes nothing and says the same, or, once no agent is left to take it, "Dockingbird 0.15.3 is in place, and no agent is waiting to take it."

The agents a roll leaves on their old code are its stragglers: an agent at a terminal, a screen agent whose gate stays closed, an agent that couldn't take the new code or never answered, and one whose turn runs on. The roll checks every `UPDATE_ROLL_POLL_S` and waits for them until each has switched or ended, or until `ROLL_STRAGGLER_WAIT_MAX_S` has passed since only stragglers were left; then it ends, and `status` names the stragglers still running, one line per kind ("Dockingbird 0.15.3 is in place. claude-2 on 0.15.2 keeps its own until its terminal closes."). An agent among them that was asked keeps its ask and switches by itself at its next stopping point ("Dockingbird 0.15.3 is in place. codex-1 on 0.15.2 takes it at its next stopping point, or keeps its own until it ends."), an agent Dockingbird couldn't ask keeps its code until a later `dockingbird update` asks it ("Dockingbird 0.15.3 is in place, but Dockingbird couldn't ask claude-1 on 0.15.2, which keeps its own until it ends. To try again: dockingbird update"), and the old code stays in the store while an agent runs it. A later `dockingbird update` asks the bus and screen stragglers again; an agent at a terminal is never asked, so stop it and start it again to move it to the new code.

| Bound | Default | Past it |
|---|---|---|
| `SWITCH_BACKGROUND_WAIT_MAX_S` | 30 minutes | an idle agent's background work is ended and the agent switches, told so |
| `SWITCH_ASK_ANSWER_MAX_S` | 10 minutes | an idle agent that hasn't answered its ask is left on its code, a straggler |
| `ROLL_READ_FAILED_MAX_S` | 30 minutes | the roll stops when Dockingbird here or its code can't be read for that long; once it is fixed, the next command here resumes the roll |
| `ROLL_STRAGGLER_WAIT_MAX_S` | 24 hours | the roll ends with its stragglers |

A roll that fails stops, and `status` says so under "Needs your attention" with what fixes it: the new coordinator didn't come up, and the old one runs again ("Dockingbird didn't switch to 0.15.3, so 0.15.2 still runs. See why and try again: dockingbird update"); the new version changed the records but didn't come up, and the old one can't run on them ("Dockingbird 0.15.3 changed the records but didn't come up, and 0.15.2 can't run on them. Fix and try again: dockingbird update"); Dockingbird here couldn't be read ("Dockingbird 0.15.3 is installed, but Dockingbird here or its code couldn't be read for 30 min, so the roll stopped. Fix it; the next command here resumes the roll."); the new code is gone from the store ("Dockingbird 0.15.3 is installed, but its code is gone from here, so the roll stopped. Run it again: dockingbird update"); or the Dockingbird running here was put on other code by hand twice during one update ("Dockingbird 0.15.3 is installed, but the Dockingbird running here was put on other code by hand twice during this update, so the roll stopped. Run it again: dockingbird update").

One case still waits for the agents to end, as every update with agents running did before. A home whose running Dockingbird is older than `ROLL_FLOOR`, the oldest release a home rolls from in place (the release that brought rolling updates), waits once, for its first update to a release that rolls ("Dockingbird here is too old to take 0.15.3 while agents run, so claude-1 on 0.15.2 keeps its own until it ends."). `update` judges that from the version label of the Dockingbird running here, before it reads anything through it, builds or stages anything: a label it can't read is refused, exit 1 ("Dockingbird can't tell which version runs here, so it can't take 0.15.3. Fix the host, then: dockingbird update"), and so, whatever the floor, is a program older than the Dockingbird here while a bus or screen agent runs ("Dockingbird here is newer than this program, so it can't take over while claude-1 on 0.15.3 runs. Once it has ended, run this again."); an agent at a terminal alone lets it through. Meanwhile `status` says what waits ("Dockingbird 0.15.3 is installed and takes over when claude-1 on 0.15.2 ends: Dockingbird here is too old to switch agents while they run."), and, installed from a release, your commands run an exact copy of the version the agents run, kept under `DOCKINGBIRD_HOME/update/`. The switch then happens by itself: once the last agent ends, and the terminal that showed it or `dockingbird stop` has finished ending it, the background process `update` started stops the old Dockingbird and starts the new one, with no command typed, then puts in place the GUI `update` downloaded for it and rewrites the tab completion scripts; it fetches no tool, so the first start after it gets each tool's latest release, as any start does. A switcher of the kept older copy that is still running when the new release stages is ended by the update. A switcher of an older release that was loaded before an in-place upgrade ends on its own when it next reads the new record; until the next command run here, which starts the new switcher, the staged update has no switcher. After a `dockingbird stop`, the switch still happens and Dockingbird stays off until you next use it (with no copy kept, `stop` says so: "Stopped Dockingbird. It switches to 0.15.3 now and stays off until you next use it."). A start that a base change overtook starts nothing and says so ("Dockingbird's engine changed while claude-1 started, so claude-1 didn't start. Run the same command again.").

An update that changes Dockingbird's engine, the image's base, rolls too: no running container can take a new image, so at its next stopping point each bus or screen agent on the old engine moves to a new container on the new one, keeping its name, its session and its conversation, which its tool resumes. `update` names those agents apart ("Dockingbird 0.15.3 is installed and takes over now. It changes Dockingbird's engine too, so claude-1 and codex-1 restart at their next stopping point and keep their conversation."). Each start keeps a record of how its agent was started, `DOCKINGBIRD_HOME/agents/<name>/spec.json`, and the move starts the new container from it; `dockingbird clean` removes the record with the agent's copy. An agent started by an older Dockingbird has no record, so `dockingbird set NAME --switch-code KEY` with a key that changes the engine is refused for it, exit 2, and asks nothing ("claude-1 can't take Dockingbird 1a2b3c4d: it changes Dockingbird's engine, and claude-1 started before Dockingbird could restart an agent in place. It keeps 0.15.2 until it ends."); a key on the same engine is asked as before.

You can also move one agent by hand, with or without a roll: `dockingbird set claude-1 --switch-code 3f9a0c21` asks it to take the code with that key at its next stopping point ("claude-1 takes Dockingbird's code 3f9a0c21 at its next stopping point. See it: dockingbird status claude-1"), and `dockingbird set claude-1 --switch-code -` takes the ask back ("claude-1 keeps the Dockingbird code it runs: no switch is asked."). A key the store doesn't hold is refused, exit 2 ("Dockingbird has no code 3f9a0c21 here."), and so is an agent at a terminal ("claude-2 runs at a terminal, which keeps its Dockingbird until it closes. Stop it: dockingbird stop claude-2"). Each `set` is a new ask, so one an agent refused can be asked again.

### Reading across versions

Your `PATH` may hold a different Dockingbird from the one a home runs. A home runs the version that last started or updated it. For each home, `dockingbird homes` says what this computer's Dockingbird can do there. It reports two separate things.
- **Readable:** the home's coordinator runs the image this Dockingbird would run there. A command from here leaves that coordinator as it is.
- **Readable for inspection:** the home's coordinator runs Dockingbird 0.6.2 or later, which its `com.dockingbird.version` label shows. Release 0.6.2 is the first whose coordinator answers `inspect`. Three readers can look at such a home: `dockingbird inspect swarm`, `dockingbird inspect config --agent NAME` and the GUI's Swarms tab. Each reads it as `status` reads a home, with one `docker ps` and one `docker exec` in its running coordinator. Each starts, updates and locks nothing.

The list that `inspect swarm` shows comes from the home's own coordinator. One that lists only the running agents shows those, whichever Dockingbird or GUI reads it. An older one lists every agent record, up to 64, until you update it. The GUI runs `dockingbird inspect swarm --roster`, which lists the agents alone, without the pairs. A coordinator of 0.11.1 or later reads only its roster. An older one is read as before and its pairs are left out. Either way the answer is the same: `roster_only` is true and there is no `permissions`. From 0.11.1, `dockingbird --json inspect capabilities` says `roster` and its `version`.

A `dockingbird` older than 0.6.2 on this computer has no `inspect` at all, so the GUI's Swarms tab shows "Inspection unavailable" for every home. A `dockingbird` from before `inspectable` lists no such field. A GUI that reads it falls back to `readable`, and a GUI older than the field reads only readable homes.

The GUI's Inbox tab reads only a readable home. In a home whose coordinator is older, an `inbox` or `questions` call would update that coordinator. Use `dockingbird --json homes` to get `readable`, `inspectable` and `inspect_from` for each home. `inspect_from` is the release that inspection exists from. Use `dockingbird --json inspect instances` to get each home's `inspectable`.

| The home | `dockingbird homes` says | `inspect` and the Swarms tab | A command from here |
|---|---|---|---|
| Its coordinator runs the image this Dockingbird would run there | its line, readable | read it | runs as usual |
| Its coordinator runs 0.6.2 or later, an older image | "readable for inspection; a command from here would update it" | read it | updates its coordinator to this Dockingbird; its running agents follow (see "Rolling updates") |
| Its coordinator runs a newer Dockingbird whose answer this one reads | "readable for inspection; commands from here are refused: it is newer, update this computer's Dockingbird" | read it (the Swarms tab ignores members it doesn't know) | refused: update this computer's Dockingbird |
| Its coordinator runs a newer Dockingbird that answers in a newer form | the same | refused, exit 1, naming both Dockingbirds and both forms ("... answers inspection in a newer form (2) than this Dockingbird 0.9.1 reads (1): update this computer's Dockingbird."); the Swarms tab shows that line | refused: update this computer's Dockingbird |
| Its coordinator runs a Dockingbird older than 0.6.2, or one that names no version | "not readable from here: its Dockingbird 0.6.1 has no inspection (from 0.6.2)" | refused, exit 1, before anything runs in it, naming its version and 0.6.2 ("... runs Dockingbird 0.6.1, which has no inspection (from 0.6.2): nothing was read."); the Swarms tab says why | updates it; with agents running, it switches once they end |
| Its coordinator is stopped | "not readable from here: a command from here would start it" | nothing is read: `inspect` prints the line `status` prints for it, and the Swarms tab says the home's Dockingbird is stopped | starts it |
| A fleet host answers in a newer form (`--host`) | | refused, exit 1, naming the host, this Dockingbird and both forms | |
| Its `state.json` was written by a newer Dockingbird | its line, as before | read the record as before | the commands that use Docker, `update` and `mcp install` are refused (`STATE_NEWER`) |

Three refusals say that a pair can't work, and each names both sides. For `INSPECT_NOT_SUPPORTED`, update the home's Dockingbird. Run `dockingbird --home lab update` for the home named `lab`, or `dockingbird update` with `DOCKINGBIRD_HOME` set to its folder. With agents running, it waits until they end. For `STATE_NEWER` and `INSPECT_SCHEMA_NEWER`, update this computer's Dockingbird (`dockingbird update`).

### Clean

`dockingbird clean` removes old images of this installation and the copies agents left behind, removing a copy that is provably empty at once and asking about each other one first (work not shared yet, changed files, a crash, or an agent that ended before its files were counted; default No). `--yes` removes them without asking. Without a terminal to ask, or with `--json`, `clean` without `--yes` keeps each copy it would ask about, says so, and exits 1. It names what it removed, each copy with what it held, and how much it freed, in MB under a gigabyte ("Removed 2 copies (reviewer: 1 commit not shared; rev2: empty) and temporary files: 300 MB freed."), and "under 1 MB freed" below a megabyte. A copy you answered no for is named too: "Kept claude-1's copy. Nothing else to clean." Ctrl-C at a question is its no, and the no of every question after it: the rest goes on as answered, and `clean` then exits 130. Harbor's jobs and leftovers are `dockingbird harbor clean`'s (see "Harbor benchmark tasks").

`dockingbird clean codex-1` deletes one agent that stopped, or several (`dockingbird clean codex-1 claude-2`): its kept copy, its results folder and its history, so status and the GUI no longer list it and its name is free for a new agent. It asks first about a copy or results that may hold work, as `clean` does (default No; `--yes` deletes without asking), and it deletes an agent whole or not at all: an answer of no, or a copy it could not remove, keeps everything of that agent and says so. A working agent is refused ("codex-1 is running. To delete it, stop it first: dockingbird stop codex-1"), a name it knows nothing of is said as such, and one with nothing left says "Nothing to delete: codex-1 has no kept copy, results or history." It names what it deleted and what that freed ("Deleted codex-1: its copy (1 commit not shared), its results and its history; 300 MB freed."). Names and `--all` do not go together. On the coordinator's side the history is forgotten, not deleted: each ended session of the name is marked so, and its records stay.

`dockingbird clean --all` removes everything Docker mode made: this installation's containers, its five volumes (every agent's copy and history, the sign-ins and the saved key, the tools' store, and the toolchains agents get), every agent's dependency cache, its images, every link in your checkouts' `.git/config` (a renamed branch's too; one git can't change is named), and its files in `DOCKINGBIRD_HOME` (a `config.toml` you wrote in stays), the marker last. With `bin/` goes the link to the GUI beside `dockingbird` on your PATH (`~/.local/bin/dockingbird-gui` for a uv install) when it points at this home's GUI; a file or a link to anything else there stays, and the summary names it ("Kept ~/.local/bin/dockingbird-gui: it isn't the link to the GUI this Dockingbird installed."), as it names the link when its folder refuses the removal ("Dockingbird couldn't remove its link to the GUI, so it stays:"; `--verbose` adds why). `harbor/` goes with them: Harbor's install, its jobs and every container, network, volume and `hb__` image of its jobs, a running job's included, and the list of what is lost names it ("Harbor's jobs and its install go too: ..."). It empties `logs/` but keeps that folder, and so `DOCKINGBIRD_HOME` around it: `logs/` is the folder the coordinator writes its logs to through a mount, and Docker Desktop's file sharing can refuse a folder deleted and made again at the same path until Docker Desktop restarts, so the next start would fail. The summary names it ("Kept the empty folder ~/.local/share/dockingbird/logs, so the next start works."); the next start uses a home holding only that empty folder as its own, and a second `dockingbird clean --all` finds nothing to clean. To remove it after uninstalling, delete it once Docker Desktop has restarted. First it lists what is lost, every item named however long the list, each starting two columns in and its later lines four, so the items never run together: each agent still working, one line each ("  claude-1 is working now: it will be stopped and its copy removed."), each agent that stopped with its copy kept, with what the copy holds when it was counted ("  keep8 stopped with 1 file not committed: its copy will be removed."), and commits the agents shared that you haven't synced, each with the step that keeps them from where you run it ("To keep them: git switch main, then dockingbird sync"; "the agents shared commits you haven't synced" when your checkout lacks their head, uncounted, and "may have shared" only when Dockingbird can't tell); for a branch no longer in your checkout, the commits that only Dockingbird keeps there, synced or not, with the step that makes the branch again ("My App (feature/redo, no longer in your checkout): 2 commits the agents shared are kept only by Dockingbird." and "To keep them: git switch -c feature/redo dockingbird/feature/redo"), and no line when no commit would be lost; for a branch you made under a deleted branch's name, the same count with sync's step, which asks first ("To keep them, say yes when sync asks: dockingbird sync"); then it says "Your code is untouched." and asks you to type `delete` (`--yes` accepts the loss and afterwards names the working agents it stopped; without a terminal and without `--yes` it refuses; any other answer prints "Nothing removed." and exits 1, and Ctrl-C prints it too and exits 130). It also removes, in each linked checkout, the refs Dockingbird keeps the agents' head under, `refs/remotes/dockingbird/*`, each by its full name and no other ref; if git can't, it names the checkout and `git branch -dr dockingbird/<branch>`. Under `--yes`, your own `instructions/` folder and your `versions.toml` are kept; without it, the list names `versions.toml` ("Your tool versions file goes too: ~/.local/share/dockingbird/versions.toml") and it goes. Your `vaults/` folder, where the stores of your vault connections live, is kept whenever anything is in it, with or without `--yes`, and the summary says so ("Kept the stores of your vault connections: ~/.local/share/dockingbird/vaults"); only an empty one goes, and the next start uses a home holding your kept stores as its own. It only ever removes objects carrying this installation's labels, by exact id, and never touches your code, `~/.claude` or `~/.codex`. Docker keeps its build cache, which every project's builds share and which carries no labels, so Dockingbird leaves it alone, and the space it names as freed does not count it. Dockingbird's own build keeps its downloads there too (apt's packages and lists, uv's cache and the pinned tools' archives), so a rebuild fetches only what changed, and Docker's own garbage collection bounds that cache. To reclaim that space too, `docker builder prune` removes the unused build cache of every project on this Docker, not only Dockingbird's, so run it only if that is what you want.

### Licensing

Dockingbird is licensed by seats: **a seat is one person, who may link up to three computers** (the license's computers per seat): a laptop, a desktop and a cloud VM (on arm64, the only platform Dockingbird runs on) are one seat; a second Dockingbird home on the same computer (another `DOCKINGBIRD_HOME`) shares its computer; agents, containers and repos are never counted. The terms are Zeusfyi's end-user licence agreement, published at `https://zeus.fyi/legal/dockingbird-eula`, and the privacy note lists what licensing sends to Zeusfyi: nothing from a repo or an agent.

- **Activate.** `dockingbird license activate` asks for your license key (hidden), or reads it from standard input without a terminal (`pbpaste | dockingbird license activate`), and never from the command line: a key given as a word is refused (exit 2), so it never reaches your shell's history or `ps`. This computer is then linked to the license, and it prints the plan, its seats and when the term ends, then the computers linked of the computers its seats admit ("  Computers linked: 4 of 30 (10 seats, 3 computers each)"), or, with a license client that reports no computers, the seats in use ("  Seats in use: 2 of 10"). A license whose computers are all linked refuses the activation (exit 1): "Every computer this license admits is linked, so this one can't join." and "Free one: dockingbird license activations --release ID", then one line per computer linked, seen longest ago first, each with its id; with `--json` that is one envelope whose fields carry those computers and both counts. `dockingbird license activate --label TEXT` names this computer in the list of computers (by default its hostname, at most `LICENSE_LABEL_MAX_CHARS` characters), and `--accept-terms VERSION` accepts the agreement's version for a scripted install. Activating again on a computer already linked keeps its link.
- **Trial.** `dockingbird license trial` starts a trial on this computer, with no key: one per computer.
- **Status.** `dockingbird license status` shows the state, the plan, the seats and the term's end, then how many computers one seat may link ("  Computers per seat: 3", when the license client reports it), this computer's label, the lease's end and the last check-in, from the license file on this computer with no network; `dockingbird license status --refresh` checks in with Zeusfyi first. `dockingbird status` shows the state in one line once this computer has a license file and the license client is here; it never downloads the client. With `--json` they are fields.
- **Seats.** `dockingbird license activations` lists the computers linked to the license (it asks for the key as `activate` does) under the same count line as `activate`; the list holds at most 80 computers, the ones seen longest ago first, and when the license has more it says how many it shows ("  Showing the 80 seen longest ago of 90"). `dockingbird license activations --release ID` frees one, for a computer lost or wiped, then lists the rest. A computer rebuilt with a new identifier (a re-imaged VM, a cloud instance recreated on each deploy, a container or CI runner without a machine id) is a new computer each time. Before you destroy one, run `dockingbird license deactivate` (or `dockingbird clean --all`); otherwise free it with `dockingbird license activations --release ID`; an unreleased one stops counting by itself after 90 days. `dockingbird license deactivate` gives this computer's seat back. `dockingbird clean --all` gives it back first too; when Zeusfyi can't be reached it says the seat is still held, so you can free it from another computer.
- **Check-ins.** Once licensing is enforced, a start whose last check-in is older than `LICENSE_HEARTBEAT_INTERVAL_S` (a day) checks in with Zeusfyi first, within `LICENSE_HELPER_TIMEOUT_S`, and a failed check-in never stops the start. Without a check-in the license keeps working for its lease, so a computer offline, or an outage at Zeusfyi, interrupts nothing.
- **What a refusal means.** Licensing only ever concerns a new agent's start (`claude`, `codex`, `start`, a config's command and `agent_start` of `dockingbird mcp`); reconnecting to a running agent is not a new start. `sync`, `stop`, `clean`, `status`, `results`, `read`, `inbox`, `serve`, `update`, `login` and every running agent are never stopped by it, so you always get your work back. In this version licensing is not enforced (`LICENSE_GATE_ENFORCED` is 0): a start reaches no network and downloads nothing; it runs the license client only when one is already here (from an earlier `license` action, such as `dockingbird license activate`, or `DOCKINGBIRD_LICENSE_CLIENT_PATH`), reads its state with no check-in, prints one line for any state but a valid license or none ("agents start because licensing isn't enforced yet" for a reason that would refuse), and the agent starts; a client here that can't be used is noted in the error log, and the agent starts. Once licensing is enforced, from the release that sells the first plan: when the term nears its end, the computer has been offline a while, or the term or lease has ended and its grace period runs, a start prints one line saying so and the agent starts. Past the grace period, the start is refused before anything runs (exit 1), with the reason and its next step: `dockingbird license activate` (no license here, a seat freed from another computer, another computer's or an unreadable license file), `dockingbird license status --refresh` once the license is renewed or this computer is back online, or `dockingbird update` when the license needs a newer Dockingbird. A license client that couldn't be downloaded refuses the start too, saying why, with the next step `dockingbird license status`, which tries the download again at once; one that is here but broken or too slow to answer refuses it with the next step `dockingbird update`; never a silent pass.
- **The license client.** Licensing runs Zeusfyi's license client, `zeusfyi-license`: Dockingbird hands it the key on its standard input, reads its answer and shows it, and decides nothing itself. The first `license` action (`dockingbird license activate`, `dockingbird license trial`, and the others) downloads it from Zeusfyi into `DOCKINGBIRD_HOME/bin/`, within `LICENSE_CLIENT_FETCH_TIMEOUT_S` and `LICENSE_CLIENT_MAX_BYTES`, checks it against the sha256 this Dockingbird pins before writing it, and keeps it; a wrong digest leaves nothing. Once licensing is enforced, a start downloads it too when it is missing, and after a failed download a start tries again only once `LICENSE_CLIENT_RETRY_S` (an hour) has passed (the failure's time is kept beside it); a `license` action always tries at once. `DOCKINGBIRD_LICENSE_CLIENT_PATH` names a client of your own instead (an absolute path; tests use it), and `DOCKINGBIRD_LICENSE_AUTHORITY_URL` another license server.
- **Updates from Zeusfyi's index.** Installed from Zeusfyi's package index, `dockingbird update` and `dockingbird update --check` use this computer's activation as the index's password (its download token, read from the license file and given to uv in its environment only, never in a command line or a log). The index serves releases to a current license only: after a term ends, the installed version keeps working, and new releases need the license renewed. Without an activation, `update` says to run `dockingbird license activate` first.

### Toolchains

Each agent runs the language versions its repo names where production reads them: its `mise.toml`, its `.tool-versions`, and the version files its `mise.toml` enables under `[settings]` (`idiomatic_version_file_enable_tools = ["node", "python"]` makes mise read `.nvmrc` and `.python-version`), with `mise.lock` deciding over them, as mise decides. Dockingbird reads none of these files itself: [mise](https://mise.jdx.dev) does, in a container of Dockingbird's own, and installs each version once per Mac into a store every agent mounts read-only. A start says what the repo's agents get on its first line, "Toolchain for myapp: Python 3.12.7 (mise.toml) and Node 20.18.1 (.nvmrc).", and when a version isn't installed yet, installs it with a live line before anything else starts ("Installing Node 20.18.1 ... {elapsed}: <mise's latest line>", then "Installed Node 20.18.1 ({elapsed})."); a second agent on the same repo prints the first line alone. A repo that names nothing starts as before, with the image's versions: "Toolchain for myapp: nothing named; agents get the image's versions." An install that fails stops the start before anything is made, with mise's last lines; `dockingbird claude --no-toolchain` (also on `codex` and `start`) starts with the image's versions for that one start, and `--no-deps` keeps the toolchain and skips the repo's dependency install (below). Neither is remembered. Ctrl-C while a version installs ends the start (exit 130) and leaves the install going, so the next start uses it. A running agent keeps the versions it started with; `dockingbird status` says when its repo now asks for others.

`dockingbird env` shows the table for the repo you are in: each tool its files name, with the request and its file, beside the version agents get, "(locked)" when `mise.lock` names it, "(not installed yet)" when no start has installed it; then the image's Python, Node and Go that nothing names; then how many toolchains this Mac holds, and how to change one:

```text
myapp (main)   repo wants         agents get
  Python       3.12 (mise.toml)   3.12.7 (locked)
  Node         20 (.nvmrc)        20.18.1
  Go           nothing named      1.27.2 (the image's)
Dependencies: none preinstalled (no lock file).
Downloaded: 2 toolchains. Unused ones go with: dockingbird clean
Change one: dockingbird env use TOOL VERSION
```

It runs mise's look in a container, with your checkout mounted read-only, and writes nothing in it. Before the store's line it names the dependency installs a start runs for a repo that names a toolchain, read from the lock files on your Mac ("Dependencies: uv sync --locked (uv.lock) and npm ci (package-lock.json)", or "Dependencies: none preinstalled (no lock file)."); for a repo that names none, whose agents get the image's versions and install nothing, it says "Dependencies: none preinstalled (the repo names no toolchain).". With Docker off it shows the heading, says the versions need Dockingbird running, and shows the store's line from its last record and the dependencies line from the lock files, which then can't tell whether the repo names a toolchain. Outside a repo it says so and exits 1. In a narrow pane each tool's two values stack under its name; with `--json` each line is one envelope, a tool's row adding `tool_word`, `locked` and `installed`. `dockingbird env install` installs those versions now, so the next start waits for none, and writes nothing in your checkout. `dockingbird env lock` writes each version, exact, into the repo's `mise.toml` and locks it in `mise.lock`, and says to commit both (`git add mise.toml mise.lock`): every Mac, and every agent, then gets the same. `dockingbird env use node 22` writes one version into the repo's `mise.toml`, making the file when there is none, and installs it: "Wrote mise.toml: node = "22" (was .nvmrc: 20; mise.toml wins now). Agents started from now get Node 22.11.0.", then the running agents that keep theirs until restarted. Its TOOL is one of python, node, go, java, rust, ruby, bun, deno, zig, pnpm, yarn and npm, and its VERSION a version number (`22`, `3.12`, `1.82.0`; Go's `prefix:1.20`; Java's `temurin-21`, or `21` for mise's default vendor), never `lts` or `latest`, which it refuses with an example; another tool mise knows goes into `mise.toml` by hand. `dockingbird clean` removes the versions no running agent and no repo's last look names, and clears mise's download cache; `dockingbird clean --all` removes the store with the other volumes.

**Dependencies.** Before its tool starts, an agent whose repo names a toolchain installs the repo's dependencies in its own copy (one with the image's versions installs none), from the lock files at the repo's top, with the toolchain's own package managers, as production would: `uv.lock` runs `uv sync --locked`, `package-lock.json` `npm ci`, `pnpm-lock.yaml` `pnpm install --frozen-lockfile`, `yarn.lock` `yarn install --immutable` (Yarn 2 and later) or `yarn install --frozen-lockfile` (Yarn 1), `go.sum` `go mod download`, `Cargo.lock` `cargo fetch --locked` and `Gemfile.lock` `BUNDLE_FROZEN=true bundle install`. A lock file that doesn't match its manifest fails the install, as it would in production; a Maven or Gradle build and a `requirements.txt` without a lock file get nothing. Only a checkout you trust gets them, since install scripts are the repo's code: in one you marked untrusted the agent gets its toolchain alone and says "Dependencies: skipped (untrusted checkout; dockingbird trust allows them).". The agent shows "Installing myapp's dependencies: uv sync --locked (uv.lock)", the command's own lines as they come, then "Dependencies installed ({elapsed})." on its screen at a terminal, or in its log on the bus, where `dockingbird status` shows it as "preparing: installing dependencies". An install that fails ends the agent before its tool starts ("claude-1 stopped before it started: its dependencies couldn't be installed."). `dockingbird status` then names the command, its last lines and the way on without them: `dockingbird claude --as claude-1 --no-deps`. Downloads from npm, uv and Go go to a cache of the agent's own, the Docker volume `dockingbird-cache-<agent>` at `/dockingbird/cache`. A restart of the same agent keeps it. The other package managers keep their caches in the agent's own HOME. `dockingbird clean` removes an agent's cache with its kept copy. `dockingbird clean NAME` removes it with the agent, and `dockingbird clean --all` removes all of them. An agent whose egress is `none` or `models` reaches no registry. It runs each command's offline form (`uv sync --locked --offline`, `npm ci --offline`, and so on) from what is cached. When a package isn't cached, the agent ends ("its dependencies couldn't install offline"). `dockingbird status` then names two ways on. One is `dockingbird claude --as claude-1 --egress full`, whose egress reaches the registries. The other is `dockingbird claude --as claude-1 --no-deps`, which skips all of it ("Dependencies: skipped (--no-deps).").

A repo's mise config can do more than name versions. Its `[env]` sets variables and its `[settings]` change how mise installs. Both load only in a checkout you trust. Every checkout counts as trusted, unless you marked it with `dockingbird trust --off` or made untrusted the default (see "Trust"). In a checkout you marked untrusted, a config that needs trust stops the start, and `env` does the same, with mise's own words and two ways on. The first is `dockingbird trust`. The second is a start with the image's versions, `dockingbird claude --no-toolchain`. A `mise.toml` of plain versions, a `.tool-versions` and the version files need no trust. For an agent whose repo names a toolchain, a config's `[env]` (see "Your own commands (configs)") arrives through mise too, before the repo's own. The repo's `mise.toml` entry of a name therefore wins. A config's `mise_env` names mise's environments for its agents (`mise_env = "ci"` makes mise read `mise.ci.toml` over `mise.toml`), for their toolchain's install and for their environment.

### The GUI

`dockingbird update` on a Mac installs the GUI this Dockingbird pins, and `dockingbird ui --install` installs it on any computer. Until one is installed, `dockingbird ui` prints `GUI_MISSING`, as [the GUI](guides/gui.md) shows.

`dockingbird ui` opens the Dockingbird GUI, `dockingbird-gui`, in the terminal you run it in: a terminal program built from [herdr](https://github.com/herdrdev/herdr) (Apache-2.0), with herdr's colours, layout and plugins, that shows every agent and runs Dockingbird's actions. It is mouse first: click a pane, a tab, a workspace or a row to focus it, drag a border to resize a split, drag over text to copy it, and right-click for a menu; every action has a key too. Its header shows a small bird beside "Dockingbird" and its version (one line and no bird on a terminal under 20 rows or 60 columns). Each running agent at a terminal gets a tab of its own, named after it, whose one pane is the agent's screen, in a workspace for its repo and branch, named as status names them ("My App (main)"); a tab you close stays closed until you open it from the agent's row. The pane runs `dockingbird claude --as NAME` (or `codex`, or its config's command), typed with the full path of the `dockingbird` the GUI reads with, in the agent's checkout when status names one, else in the folder you started `dockingbird ui` in, so it takes the agent over from a terminal that shows it, as that command does anywhere. Under the workspaces, above herdr's own agents panel, the section "dockingbird" shows once Dockingbird has something to show (with no agent, no message and no question there is no section and no command bar, and `ctrl+b d` still works): first a row for the inbox, "Inbox (3)", then a row for each agent whose container runs, those on the bus too, each agent once: in each home the agents that ask first, then those `working`, `preparing`, `waiting`, `idle`, `failed`, `crashed`, `stopped`, `done` and `ended`, in status's order within one state. An agent whose container is gone, the kept copy of a stopped or crashed agent or one that ended, has no row here; `dockingbird status` still lists it. A row has up to three lines: its name and its state as Dockingbird writes it (`working`, `idle`, `asks 1`, `stopped`, `failed`, `done`); its tool and the computer it runs on, then "no screen" for an agent without one (`claude · local-macbook-pro`); and its repo and branch (`my-app · feat/x`), a line only an agent with a branch has. The computer is named after the Mac's model as macOS gives it, such as `local-macbook-pro` on a MacBook Pro; on Linux, or when macOS gives no model, it is `local-` and the first part of the hostname. The row of the selected agent, the one the command bar shows, takes the active row's colour. When a read fails, a line "status: ..." with the error follows the inbox row, and the rows of the last good read stay; rows that do not fit end in "+2 more". A click on an agent's row, or Enter on it after `ctrl+b` and the arrows past the last workspace, opens the agent's screen: its tab comes forward, or opens and runs its command, and when the pane's shell is idle in front (after a detach or a takeover) the GUI types the command there again. An agent on the bus has no screen with this Dockingbird: a click on its row only selects it, for the command bar, and `a` on it says "it has no screen to open". A pane's state (working, blocked or idle) is Dockingbird's own record of the agent: the GUI reports it for the pane, and that report wins over what herdr reads on the agent's screen, so an agent that asks you something is blocked, "asks you 1 question(s)", and one that works is working whatever its screen shows. The GUI reads `dockingbird --json status` and `dockingbird --json inbox`, and `dockingbird --json questions` while a question waits, when it starts and then 2 minutes after each read ends, and again at once for `r` and when a command's popup ends; a start here, a pick-up that starts an agent and a click that opens a tab wait for the next read, so a new agent's row can take up to 2 minutes unless you press `r`. An agent that ends keeps its tab until you close it; while its container runs its row shows how it ended, and the command bar shows its next step.

herdr's prefix is `ctrl+b`: press it, let go, then press a key, as `ctrl+b ?` lists every binding (Dockingbird's layer is one line there); pressing `ctrl+b` twice sends the pane a plain `ctrl+b`. Dockingbird's actions are a layer under the prefix, `ctrl+b`, then `d`, then a letter: `n` starts an agent (a form of four questions: here, in a tab of its own, or in the background on the bus; the tool, `claude`, `codex` or a config's command; its name; and, in the background, its task), `x` stops a working agent with `dockingbird stop NAME --yes` (the same as `dockingbird stop NAME`, which asks nothing, since its work is kept) or, after a y, deletes a stopped one, `R` saves its results, `y` syncs the folder you started the GUI in, `p` picks up an ended agent, `a` opens its screen, as a click on its row does, `i` opens the inbox tab and `r` reads everything again; `Esc` or any other key leaves the layer and runs nothing, `m` and `s` too: the GUI has no form that changes a model, effort or compact point or sends a message (`dockingbird set NAME` and `dockingbird send NAME TEXT` do, in a shell). A right click on an agent's row opens a menu of the same actions for it: "Stop" ("Delete..." once it ended), "Results", "Pick up" (an ended agent with a command to pick it up), "Answer in its screen" (while it asks), "Start an agent...", "Sync", "Inbox" and "Read everything again". A key that needs an agent acts on the agent of the focused pane, else on the only agent, else asks "which agent?". Each action composes the exact `dockingbird` command: a stop, a delete, results, a sync, a start in the background and a pick-up that starts no agent show it on the first line of a popup and run it there, in a pane of its own, and the GUI reads Dockingbird's state again when it ends, while a start here and a pick-up that starts an agent type it in the agent's tab. `x` on a stopped codex-1 asks "delete codex-1? its records go too; type y to delete" and runs `dockingbird clean codex-1 --yes` only after your y, and `n` in the background with `claude`, notes-2 and a task runs `dockingbird start --bus --as notes-2 --harness claude TASK`. Under the panes, one row is the command bar, for the selected agent, the one whose pane has the focus, else the row you clicked last: on its left its name, tool and state, its model, effort and context in status's short marks (`->` while a `set` change is on its way) and one note, the first that applies (that it asks you, its pane's trouble, what the GUI typed for it or waits for, or an ended agent's next step, "next: ..."); on its right its buttons, each the layer's key for that agent: `results`, `stop`, `answer` while it asks, `sync` when status names its checkout (a sync in that checkout), `inbox`, `start` and `refresh` for a working agent; `pick up` when it has a command, `delete`, `results`, `inbox`, `start` and `refresh` for one that ended; `start` and `refresh` with none selected. The inbox is a tab, "inbox", that `i`, the bar's `inbox`, a click on the inbox row or the menu's "Inbox" opens, or brings forward: the questions first, each with its options numbered under it, then the messages, or "Nothing waits for you."; the arrows (or `j` and `k`) and the wheel select a row, Enter or a click on a message runs `dockingbird read 3` and shows its output in the tab (`Esc` goes back), Enter or a click on a question opens the asking agent's screen, where you answer it, `r` reads again at once (else it reads every 2 minutes) and `q` closes the tab. The inbox view over the panes is gone, with its reply, its digits that picked an option and its typed answer. Nothing in the GUI answers a question or sends a message. You answer in the agent's screen (see `answer` under "Delegated agents"). With an agent's tab open, the GUI types one thing Dockingbird holds for that agent, and never an answer: a change you made with `dockingbird set claude-1 --effort low` to a Claude agent at a terminal. It types it at the agent's next idle prompt with nothing typed in it (see `set`).

`ctrl+b q` detaches. The GUI's server keeps running in the background, with every pane and its agent, as it does when you close the terminal window. `dockingbird ui` attaches to it again, with the panes as you left them. This computer has one GUI server, whichever `DOCKINGBIRD_HOME` and whichever folder you start `dockingbird ui` from. Its herdr session is `dockingbird`. On a computer whose GUI ran before Dockingbird 0.4.4, it is the session the GUI had then, `dockingbird-` and the default home's profile id, for as long as its folder in `~/.config/dockingbird-gui/sessions` is there. The first `dockingbird ui` starts the server. Every later one, from any home and any folder, attaches to it. It shows every Dockingbird home that `dockingbird homes` lists: the home you started it from, and every other home while its agents run. The GUI runs in your home folder (`HOME`, else `/`), never in the folder you typed `dockingbird ui` in. Its commands, popups and a start here outside a checkout run there. When the session 0.4.4 started runs beside the one from before, `dockingbird ui` says so before the GUI opens, with the commands that open it and end it. Nothing in either is ended. `dockingbird ui stop` stops that server, and every attached view ends. It needs no terminal, so it runs in a script too. It runs the GUI `dockingbird ui` finds, with that session and herdr's `server stop`. A `dockingbird-gui` you run bare from your `PATH` targets herdr's default session, not Dockingbird's, which is why `ui stop` exists. Closing a pane leaves its agent working, as closing a terminal window does. The GUI's own files are named `dockingbird-gui`, never `herdr` (its settings are `~/.config/dockingbird-gui/config.toml`), so a herdr of your own is untouched, and it makes no network call of its own: no update check, no announcements, no release notes. The sidebar's borders move with a drag, and the one under the pointer is drawn in the theme's accent colour: the line between the sidebar and the panes, which you can grab in three columns (the sidebar's last column, the line itself and the pane's border beside it), sets the sidebar's width (18 to 36 columns; a second press within 350 ms puts back the default, 26), the rule under the workspaces sets their share, and the rule above herdr's agents panel, with the two title rows under it, sets the Dockingbird section's share (until you drag it, the section takes the rows its agents need). Each is saved when you let go, under `~/.local/state/dockingbird-gui` (`$XDG_STATE_HOME/dockingbird-gui` when that is set), and read back next time. When the GUI is not connected to its server, the keys and clicks you send a pane are dropped, never sent later, and a yellow card at the top right says so once for that spell, for 8 seconds: "Input not sent", "Local is not ready, so your keys and clicks were not sent. Send them again once it is online."

`dockingbird ui --install` installs the GUI, or puts the version this Dockingbird pins in place of another: it fetches that version, checks the file's SHA-256 against the pinned one and puts it at `DOCKINGBIRD_HOME/bin/dockingbird-gui`, and a link to it next to `dockingbird` on your PATH (`~/.local/bin/dockingbird-gui` for a uv install), so `dockingbird-gui` works as a command; run bare it opens herdr's default session, not Dockingbird's (herdr's session `dockingbird`): use `dockingbird ui`, and `dockingbird ui stop` to stop the server ("Installed dockingbird-gui 0.1.0:", its path, "On your PATH:" and the link's, then "Open it: dockingbird ui"). A link already there is replaced; a file of your own in its place is left as it is and named ("Dockingbird left this as it is, since it didn't make it:"), and a folder that refuses the link is named too ("Dockingbird couldn't put dockingbird-gui on your PATH here:"); the GUI is installed either way, and `dockingbird ui` runs it. It needs no terminal, so it runs in a script and with `--json` too. A download whose checksum differs installs nothing: it names both checksums and says "Nothing was installed, and the dockingbird-gui you had stays." When the fetch fails, it shows what git said, and a build with no pinned checksum yet is not installed at all ("Dockingbird installs nothing it can't check."); each of these exits 1. The GUI is built for Apple silicon Macs and arm64 Linux, and anywhere else it says "dockingbird-gui has no build for" the platform. On a Mac, `dockingbird update` installs the GUI and keeps it at the pin: when `DOCKINGBIRD_HOME/bin/dockingbird-gui` is missing and Dockingbird is set up, or is another version, gives no version or can't start, it installs the pinned one after its own last line, and when it is at the pin but its link is missing or points elsewhere, it makes the link again ("dockingbird-gui 0.1.0 is on your PATH now:"). On any other computer, such as a cloud VM, `update` gets no GUI and leaves one already there as it is; `dockingbird ui --install` still installs it there when you ask. `dockingbird ui` runs the GUI that `DOCKINGBIRD_GUI` names (a path, for development; nowhere else then), else `DOCKINGBIRD_HOME/bin/dockingbird-gui`, else the first `dockingbird-gui` on your `PATH`, and only the version this Dockingbird pins: without one it says "The Dockingbird GUI isn't installed. Install it: dockingbird ui --install", for another version "The Dockingbird GUI at <its path> is 0.0.9, and this Dockingbird needs 0.1.0. Install that one: dockingbird ui --install", for a file it can't run "The Dockingbird GUI at <its path> can't be run. Install it again: dockingbird ui --install", and for a `DOCKINGBIRD_GUI` that names no file "There's no Dockingbird GUI at <its path>, which DOCKINGBIRD_GUI names. Unset it to use the installed one: unset DOCKINGBIRD_GUI", each exit 1. In the same way, for development and tests, `DOCKINGBIRD_GUI_SESSION` names another session for the GUI than the one every home shares (`dockingbird ui` and `dockingbird ui stop` then run in that one), and set but empty it is refused: "DOCKINGBIRD_GUI_SESSION is set but empty, so it names nothing to run the GUI in. Unset it to use the GUI's own: unset DOCKINGBIRD_GUI_SESSION", exit 1. It needs a terminal: in a pipe or a script, and with `--json` (`dockingbird --json ui`), it prints "dockingbird ui needs a terminal: run it in Terminal, not in a pipe or a script." (under `--json`, that message's envelope) and exits 1.

### Delegated agents

Besides `dockingbird claude` and `dockingbird codex`, which you work in, Dockingbird runs agents you hand a task to and talk to through its message bus, each in its own container with its own copy, as today. Every exchange command acts as one client of yours on this Mac (the "host" client), so a question an agent asks you waits in one inbox, and every message you send names you as its sender, so the agent can answer you.

**Starting one.** `dockingbird start "Fix the failing test"` starts an agent on this repo, in its own container and without a terminal, and returns once the agent is running, which takes about half a minute; it prints a line for each step it waits on (preparing the agent's copy, starting its container, sending the task). The task is the first message of the agent's own thread, and the command names the agent, the thread and the way to follow it: "claude-1 started on myapp (main)." then "Thread <id>. Watch: dockingbird wait claude-1". It runs Claude unless `--harness codex` says otherwise, and names its agents as the tool's own command does (`claude-1`, `claude-2`, and so on). `--task -` reads the task from standard input, and `--file PATH` attaches a text file to it (repeatable). Without a task the agent starts idle, and the command says how to send it its first one. `--terminal` runs the agent attached to this terminal instead; `--bus` names the bus, the mode a start takes when no config fixes the terminal, and a config whose `mode` fixes the other one refuses either flag ("review runs with mode = terminal: .dockingbird/app.toml says so") instead of running the mode you didn't ask for; both flags at once are refused too. `--cpus N` and `--memory SIZE` limit the agent's container (`--cpus 2`, `--cpus 1.5`, `--memory 4g`, `--memory 512m`; a memory limit leaves it no swap), on `claude` and `codex` too, and a config's `[limits]` table sets them as `cpus = "2"` and `memory = "4g"`, which a different flag can't override; without them the container has no limit of its own. `status NAME` shows them, an `--as NAME` pick-up keeps them unless you give others, and `set` can't change them: they are fixed when the container starts. `--compact-at N` sets the context size at which the agent's tool compacts its conversation, in tokens or `auto` (`500000`, `500k` and `1M` are the forms `set` takes; Claude Code takes 100K to 1M, Codex any count of tokens); the start asks it of the agent's session as it opens and before its container is made, as `set NAME --compact-at` asks it of a running agent, so the tool applies it from the agent's next turn on (a Codex agent at a terminal, whose session takes no such ask, gets it as Codex's own word after the tool's arguments, `-c model_auto_compact_token_limit=N`, and `auto` adds none); an `--as NAME` pick-up of an agent whose last session had a point asked keeps it, by asking it again, unless you type another; a point outside the range is refused before anything starts. `--session-hours N` sets how long the agent may run before it ends itself, a whole number from 1 to 168 hours (a config's `session_hours` may go as far as the installation's maximum); without it the agent gets its config's `[limits]` `session_hours`, 12 hours when the config names none; with no config a bus agent gets the installation's default of 12 hours, and an agent at a terminal runs with no session limit; the connections an added config grants it end with that life. A config whose `[limits]` names a `session_hours` fixes it, as it fixes `cpus` and `memory`: a different `--session-hours` is refused and the same value is not. An `--as NAME` pick-up of an agent started with `--session-hours` asks for the same life again unless you type another; a value outside the range is refused before anything starts. `--as NAME` names the agent: a name whose agent has ended picks up where it left off and gets what waited for it, by that agent's own command or in the default environment it ran in, whatever the checkout's default, each such message marked as delivered again after the restart so that the agent acknowledges work it already finished instead of repeating it (`--new` starts it afresh), and a name still running is refused, with the step that sends it a task instead. `--command NAME` runs a config's command (below); with no command named, a checkout whose `.dockingbird/` marks one command `default = true` runs that one and says so first ("Using review from .dockingbird/app.toml for this checkout"), and any other checkout runs the default environment, the agent you get with no config. The words after `--` go to the tool as its own arguments, except the flags Dockingbird sets itself for an agent without a terminal and the hook-trust bypass, which are refused before anything runs. An agent without a terminal can't sign in, so a start refuses a tool that has neither a sign-in nor a saved API key, with the step to sign in first.

**Between agents.** An agent sends to another agent of the project by name: in its `bus_send` it sets `to=<name>` (the name `dockingbird status` shows, such as `claude-2` or `review-1`), and Dockingbird delivers the message to that agent's inbox; you do nothing for it to arrive, and a name no agent has, or an agent that has ended, is refused with the reason (`AGENT_UNKNOWN`, `AGENT_ENDED`). Dockingbird also tells each agent who works with it: when other agents are already on the same work (the same repository and branch, or the same starter for a scratch-folder agent) as it starts, its first delivery names them (an agent that starts alone gets no such delivery), and every agent on that work gets `Agent <name> joined your work` the moment one starts there and `Agent <name> left your work` the moment one ends or is stopped; an agent on the bus gets such a notice with its next delivery, as a line above it, never as a turn of its own (the notice waits in its inbox until that turn completes), and one in a terminal at its next prompt. An agent of a swarm role that names `send_to` reaches its parent and the agents of its own swarm whose role its `send_to` names alone: any other send is refused `FORBIDDEN` with the reason `NOT_IN_SEND_RULES`, its first delivery names only the others it may message, and it hears of an agent joining or leaving only when it may message that agent. To read what your agents sent each other, when you choose: `dockingbird inbox claude-2` lists the deliveries waiting in claude-2's inbox, and `dockingbird read 7c3d...` (the id a row shows) reads one; from your harness, `agent_inbox` with `agent: "claude-2"` lists them and `agent_read` with that `delivery_id` reads one. Reading another agent's delivery changes nothing: it stays pending for that agent.

**Results.** `dockingbird results notes-1` saves the files of the agent's task thread: the thread its start opened, which every later task you send continues, so a follow-up's files are saved too. A file attached to a message outside it (a question it opened on its own) is reached through the file rows `dockingbird read 3` prints.

**Its screen.** An agent on the bus can run its tool's own screen, as an agent at a terminal does, while its messages keep arriving whether or not anyone looks: Dockingbird's supervisor types each message into the tool's prompt itself. A tool runs this way only once a probe of its version has passed: Claude Code and Codex do, and `dockingbird status` says which agents have one (`--json`'s `screen`, above). A start that gives the tool words only a run without a screen takes, after `--` (Claude's `--max-turns`, for one) or in a config's tool arguments, runs without one and says so: "notes-1 runs without a screen: its arguments are for a run without one." So does a start where the tool would ask whether to trust the folder, which nobody at an agent's screen answers: a checkout marked untrusted, or a config that leaves its repository settings off (`repo_settings = true` in it turns them on): "notes-1 runs without a screen: its tool would ask whether to trust this folder." A start that works in a scratch folder (`workspace = "scratch"` in its config) takes the screen form: its container trusts the agent's own folder for Codex and answers Claude's question there, so neither tool asks. `dockingbird claude --as notes-1` (or `dockingbird codex --as notes-1`) shows the screen of a running agent named `notes-1` and lets you work in it as in any terminal, `/model` and `/effort` included; closing the window, or Docker's detach keys, leaves it working, and the next look redraws the screen. `dockingbird status notes-1` names both ways to reach it, the send and the screen. Once you type in its screen, no message is typed there until you send a prompt of your own in it, the tool ends the turn it is working on, or Dockingbird clears what you left (below); a command such as `/model`, a menu you closed or a box you cleared yourself does not count. While what you typed waits unsent, `dockingbird status` says "A message or a set's command waits until you finish typing in notes-1's screen." under "Needs your attention"; it does not say so while the tool works on a prompt you sent. Claude tells Dockingbird when such a turn begins. Codex does not, so with Codex your Enter on what you typed begins it, until Codex says the turn is done or its screen stays still for `TUI_STILL_MS` (2 s), as it does after an Enter that only picked from a list. A turn Codex starts by itself, from text you queued while it worked, shows as its screen still drawing. A message that has waited five minutes is told once in its own thread, with how long it waited and why: someone is typing in the screen, the tool hasn't started yet or is still working, or its screen is still drawing. Sending a prompt in that screen lets in a message your typing held. If you leave it unsent instead, Dockingbird clears it for you: once that message's wait has been told and no key has come from you for five minutes (`TUI_HOLD_REPORT_S`), it empties the box once with the keys you would press, ctrl-K and then ctrl-U, says so in the message's thread ("Cleared unsent text left in notes-1's screen. This message had waited 5 min."), and the message goes in once the screen is still. A key you press puts that off, so a box you are still typing in is never cleared. Two things the clear cannot reach, since Dockingbird does not read the screen: a box taller than the screen, and a menu or picker left open. The message then joins what was left or goes into the menu, and its turn is told as failed instead of counted as delivered. A Claude turn that took its prompt and then drew nothing for 10 s (TUI_PROMPT_ACCEPT_MS) with no end signal and no open question ends by itself: Dockingbird presses Esc once, waits AGENT_STOP_GRACE_S for an end signal (`interrupted`), else tells the turn `failed` with what it saw, with the fault `STALLED`, so the fleet's row reads `failed` and `fleet replace` recovers the agent, and the next message goes in at the open gate; what the Esc does to a dialog the tool shows is the tool's own (Claude Code 2.1.318's usage-credits prompt takes its default and runs the prompt on it). A `set`'s command waits at the same gate: a box your Esc or ctrl-C left touched holds it for TUI_HOLD_REPORT_S, then Dockingbird clears the box and types the command. A question the agent's tool asks waits on the bus as before, so `dockingbird answer 3 "Use Vue."` still answers it, and shows in its screen as soon as you look at it there. `dockingbird set notes-1 --model claude-sonnet-5-5` changes it as any agent on the bus, "applied at its next idle prompt": its supervisor types the tool's own commands there (Claude), types them again at a later pause between turns when the tool missed them, and after repeated misses starts the tool again between turns with the change; a Codex agent's tool is started again with the change. Words after `--` that are only the tool's model and effort flags, each followed by its value, keep the screen, at a start or a pick-up alike: for Claude `-- --model claude-opus-5-5 --effort max`, for Codex `-m MODEL` (or `--model MODEL`) and `-c` with its `KEY=VALUE`, such as `-c model_reasoning_effort=high`. Every Claude agent starts with agent view off, so agent view, `--bg` and `/background` are not in its screen and a message is never typed into a background session. Dockingbird's managed Codex configuration hides the dialog Codex shows near a rate limit to suggest a smaller model (`[notice] hide_rate_limit_model_nudge = true`), so a message pasted into a screen session no longer answers that dialog instead of reaching the agent. A pending switch to a new release waits at the screen as a held message does, told after `TUI_HOLD_REPORT_S` and named by `status` ("notes-1's update waits until you finish typing in its screen."; see "Rolling updates").

**Turns and errors.** After each turn, an agent on the bus sends you a status message: `turn 3` with its final text, at `P3`, the lowest priority, so every question and task sorts before it. An error comes at once, at `P1`, so it sorts before every summary, task and question in `dockingbird inbox` and `dockingbird wait` returns with it: `turn 3 failed` with its tool's own error text (a usage limit, a refused sign-in, any error its tool reports) or, for a turn that gave no end signal, what Dockingbird saw, `notes-1 stopped: its tool exited` when its tool exited or crashed (for Claude, with the exit status), and `notes-1 stopped: the bus refused its session` with the refusal's code. The agent is each message's sender, and the last two come before its session ends. If that message can't be sent, the agent's log names the refused send (`FEED_REFUSED` for `messages.send`, or `CRASH_STATUS_FAILED`), and `dockingbird status` still shows a failed turn with its error line, and a crash once Dockingbird's sweep has ended that session. When Anthropic refuses a Claude agent's sign-in during a turn (as when the login changes on the Mac while agents still hold the old one), Dockingbird tries that turn again by itself once its `turn 3 failed` has reached you: at most `SIGN_IN_RETRY_MAX` (3) times, after 30 s, 60 s and 120 s, each try a `SIGN_IN_RETRY` line in the agent's log, with `dockingbird status` saying "retrying after a sign-in refusal (1 of 3)" meanwhile; a stop, or a message you send, during a wait ends the tries, and if the last one fails too, `status` shows the failed turn and its recovery. When a Claude agent's turn ends because the model API could not be reached (Claude's `server_error`, such as a refused connection), Dockingbird tries that turn again by itself after `API_RETRY_WAIT_S` (60 s), and again after each try that ends the same way, each try an `API_RETRY` line in the agent's log, with `dockingbird status` saying "retrying since <first failure's time> (retry 1)" meanwhile; a stop, or a message you send, ends the tries. A failed turn's subject also names the class Dockingbird read from its error, `turn 3 failed (rate_limit)`: one of `rate_limit`, `usage_limit`, `auth`, `billing`, `server`, `network`, `invalid_request`, `context`, `cap`, `refusal`, `exited` and `other`, which `dockingbird status` names after "failed" and `--json` carries as `last_turn_class` (null for an agent an older Dockingbird started). An agent with fallback rules (next) may retry the turn or move to its other tool first; an agent without them reports every failure as above.

**A fallback tool.** An agent on the bus can follow rules for its failed turns and move to the other tool with its conversation. A config's `[fallback]` table sets them (the example under [Your own commands (configs)](#your-own-commands-configs) shows each key), and `start`'s flags fill the keys a config leaves unset: `--fallback codex` (the tool to move to, never the agent's own), `--fallback-model M` and `--fallback-effort E` (that tool's model and effort; without them, its own defaults) and `--fallback-placement any` or `require-login` (below). A flag that differs from a value the config sets is refused, as `--cpus` is, and so are a model or an effort with no tool to move to and any of these flags at a terminal. Each class has a rule, the table's `[fallback.on]` or its default: `retry` (the turn again after `retry_wait`, 5 minutes unless the table says otherwise, at most `retry_max` times in a row for one delivery, 3 unless it says otherwise), `retry-then-fallback` (those retries, then the move), `fallback` (the move at once) or `report` (the failure reported and left, as with no table). With a tool to move to, `refusal` (a safety system refused the model's response or the request) is the one class that moves; `rate_limit`, `network`, `auth` (after the sign-in retries above), `billing`, `server`, `usage_limit` and `cap` retry, and the rest are reported. A move changes the model in the middle of a task, so a table that wants one for another class names it (`server = "fallback"`); without one (a table with no `harness`, an agent that has already moved as often as it may, or a fallback that is off here, below), `rate_limit`, `network`, `usage_limit` and `cap` retry and the rest, `refusal` among them, are reported. `exited` is always reported. A `usage_limit` retry takes neither `retry_wait` nor `retry_max`: it waits 1, 5 and 15 minutes, then every 30 minutes, until 24 hours after the first failure, and is then reported (or, under `retry-then-fallback`, the agent moves); a retry that completes starts it over, and a pick-up of the agent within those 24 hours carries it on. While a retry waits, `dockingbird status` says so under "Needs your attention" ("claude-1 is retrying after rate_limit (1 of 3), next in 5 min.", or for a usage limit "(attempt 5), next in 30 min, until" the end of its 24 hours), and `--json`'s `rule_retry` is the attempt.

**The move.** The agent ends its turn and stops, its copy kept: you get `claude-1 stopped after server: moving to Codex` at `P1`, with its tool's error line, and Dockingbird's next sweep ends its session and keeps the copy. `dockingbird start --as claude-1 --fallback` then continues it on the fallback tool, with its conversation and what waited for it, under the fallback's model and effort. A config's agent moves the same way by its own command (`dockingbird review --as review-1 --fallback`), and Dockingbird's fallback watcher on this computer runs that pickup for you, at most three times for one agent, then names the command under "Needs your attention". That pick-up is refused when the agent records no tool to move to (`FALLBACK_NONE`; `--fallback codex` names one), when it has already moved as often as an agent may, once by default (`FALLBACK_MAX`), and when this home can't sign that tool in (`FALLBACK_NO_LOGIN`, with the `dockingbird login codex` step). `dockingbird status` shows the move under the agent's kept copy, "claude-1 is moving to Codex after server; nothing here picks it up, so run:" and that command, before that sweep and after it (after it, without the class when the copy's summary names none). Before the sweep, an agent the fleet engine started says "its pickup is running" instead, and under `--json` the kept row carries the ask as `fallback_ask` (its `state`, `class` and `error`); every agent row's `fallback` is the table its agent records, or null. Afterwards the agent keeps the tool it ran last: `dockingbird start --as claude-1` picks it up on Codex, and a `--harness` that names the other tool is refused. `dockingbird status claude-1` says how it got there: "moved from Claude Code to its fallback tool". A start whose fallback tool this home can't sign in runs with its fallback off under `placement = "any"`, the default, and says so once ("claude-1 starts with its fallback off: no Codex sign-in here."), its rules taking the defaults without a tool; under `require-login` it is refused (`FALLBACK_NO_LOGIN`) and nothing starts.

**Configs.** `--command NAME` starts an agent of a command that a config adds, and so does the command's own name after `dockingbird`: `dockingbird start --command review "Check the login flow"` is `dockingbird review "Check the login flow"`, and its agents are `review-1`, `review-2` and so on. [Your own commands (configs)](#your-own-commands-configs), below, explains configs: what they are, where they come from, a complete example, and how to run, list and remove their commands.

**Connections.** A connection lets the agents of a config that names it fetch and push one GitHub branch, and none of them ever holds the key. Inside the repo's checkout, on the branch the agents work on, run `dockingbird connect github --github someone/myapp` (`github` is the connection's name; `--branch` names another branch Dockingbird has copied). When Dockingbird hasn't copied the branch you are on, connect copies it first, as a start does ("Copying myapp (main) for the agents ... done"), then connects; for another branch, switch to it and run connect there. Dockingbird tries the key files your own ssh would use for GitHub (`ssh -G github.com`), in that order, until GitHub accepts one, or takes the one `--key PATH` names: a file of yours that only you can read, never a link. When the key has a passphrase, `ssh-keygen` asks you for it once, on your terminal, to make Dockingbird's copy without one; Dockingbird never sees it. Without `--key`, it asks only when GitHub accepted none of your keys without one, and only for the first. Dockingbird then checks the copy with GitHub from this Mac, against GitHub's own host keys, and names the account it signed in as: "Connected github: someone/myapp (main) over SSH as somebody, with a copy of ~/.ssh/id_ed25519 (no passphrase) kept in Dockingbird until you disconnect." `dockingbird connect github` copies the SSH key your own git uses for GitHub into Dockingbird's volume, without its passphrase, so agents can fetch and push while you are away; `dockingbird disconnect github` or `dockingbird clean --all` removes the copy. The key reaches every repository your account can, as it does for you; Dockingbird pushes only the branch you connected. To limit it to one repository, use a deploy key: `dockingbird connect github --github OWNER/REPO --key PATH`. `dockingbird connect github --github OWNER/REPO --agent` uses your Mac's ssh-agent instead of a copy of your key: Docker Desktop forwards the agent into Dockingbird's coordinator, which signs in to GitHub with the keys it holds, as your own git does; no key is copied anywhere. It pushes only the branch you connected, but the keys reach every repository your account can; `ssh-add -D` or quitting Docker Desktop ends that at once. To limit a connection to one repository, use a deploy key with `--key PATH`. Dockingbird checks your shell's agent with GitHub first, restarts itself to take the forwarded agent when no agent runs ("Restarting Dockingbird to use your Mac's ssh-agent ... done"; while agents run, at its next start, and `status` says so), then asks the agent Docker Desktop reaches whether it has a key: Docker Desktop opened from the Dock or Spotlight has no agent of its own session, so open it from a terminal (`open -a Docker`), and load your key with `ssh-add --apple-use-keychain ~/.ssh/id_ed25519`. `--agent` needs Docker Desktop; the plain Docker Engine forwards no agent. If your Mac's agent restarts, its forwarded socket may stop answering: requests then fail "your Mac's ssh-agent isn't reachable", and `dockingbird stop`, then any command, starts Dockingbird with the socket bound anew. A config names the connection in its `connections` list (`connections = ["github"]`); its agents ask for a fetch or a push with `bus_request`, and Dockingbird's coordinator runs it: a fetch leaves the branch as a bundle file in the agent's log folder, with its SHA-256, and a push sends the head the agents published, never an agent's working copy. A push needs a fetch of the same connection first, and fails when GitHub's branch has commits the published head lacks: an agent merges its newest fetch into its work and shares it, then pushes again, fetching again first when GitHub's branch moved since that fetch. `dockingbird connections` lists each connection with what its agents may do with which repo and branch; `dockingbird status` shows each connection after the sign-in line, and `dockingbird status NAME` the agent's last request, and why it failed, in plain words. A push that stopped midway, after which GitHub's branch moved, has a result Dockingbird can't tell: it holds every other push back and shows under "Needs your attention"; check the branch on GitHub, then run `dockingbird connections --release`. Fetch and push over SSH are what connections run today; HTTPS tokens and the cloud accounts' requests are later work.

**Folders, databases and services.** A connection is a GitHub repo, a folder of this Mac (read-only unless its config says `write`), a database (read-only, or written through the broker with `--writes`), a service (a program of this Mac you declare), an MCP server or a browser (Google Chrome, Firefox or Safari on this Mac, lent while you run `dockingbird serve chrome`, or the same for the name you gave Firefox or Safari); the forms follow.

- **A database (read-only; PostgreSQL only this round).** `dockingbird connect app-db --database postgres://reader@host.docker.internal:5432/app --password` connects it for the configs that name `app-db`. The URL holds the role, the server's host name in lowercase, the port (5432 when you leave it out) and the database name, and nothing else: a role or database that is not a plain PostgreSQL name (lowercase letters, digits and `_`, not starting with a digit, at most 63 characters), a query, a fragment or a password in the URL is refused before anything is saved, and a password in it is never shown again. `--password` asks for the role's password on your terminal, hidden (without a terminal it is read from what you pipe in), never empty, and keeps it inside Dockingbird, never in a file of yours or on a screen; leave `--password` out for a role the server lets in without one.
  Before it says done, Dockingbird opens the database itself, from its own side and through the same path an agent's query takes, and checks it. The role must not be able to write, itself (the role it logs in as, whatever role its sessions start as) or through any role it can switch to: not a superuser, not a role that can create roles or databases, replicate or bypass row security, not a member of any role that can write or that reads or writes the server's files, runs its programs, ends other connections, runs maintenance or forces a checkpoint, owning no table and not the database, with no MAINTAIN right on a table, and with no right to call the function that writes a message into the server's log of changes, nor, in any schema, `dblink`, `dblink_exec` or `dblink_connect` (a second connection, outside the read-only transaction), `lo_export`, `lo_import`, `pg_switch_wal`, `pg_create_restore_point` or `pg_stat_reset`. The server must allow no prepared transactions (their maximum is 0, which is PostgreSQL's default). A database that fails is refused with the fix, the connection is removed again, and nothing is kept; one that passes prints `Connected app-db: host.docker.internal:5432/app as reader, read-only, checked from Dockingbird.` and the line that names it in a config. Dockingbird checks again before every query an agent makes.
  A role made for this is read-only, owns no table, has no MAINTAIN right and is not the database's owner: `CREATE ROLE reader LOGIN;`, `GRANT CONNECT ON DATABASE app TO reader;`, `GRANT USAGE ON SCHEMA public TO reader;`, `GRANT SELECT ON ALL TABLES IN SCHEMA public TO reader;`, and, once for each database, `REVOKE EXECUTE ON FUNCTION pg_catalog.pg_logical_emit_message(boolean, text, text, boolean), pg_catalog.pg_logical_emit_message(boolean, text, bytea, boolean) FROM PUBLIC;`. That revoke is the cost of the check: every role may call the function by default, it writes a record to the server's log that a rollback does not undo, and it changes the database for every role, not only this one. On PostgreSQL 16 and earlier the function has no fourth parameter, so name its two forms without it. Where the `dblink` extension is installed, `CREATE EXTENSION` lets every role call `dblink`, `dblink_exec` and `dblink_connect`, so the check refuses every role of that database until, once for it and with `dblink`'s schema on the search path, `REVOKE EXECUTE ON FUNCTION dblink(text), dblink(text, text), dblink(text, boolean), dblink(text, text, boolean), dblink_exec(text), dblink_exec(text, text), dblink_exec(text, boolean), dblink_exec(text, text, boolean), dblink_connect(text), dblink_connect(text, text) FROM PUBLIC;` (every form the extension declares), or `DROP EXTENSION dblink;`. PostgreSQL grants the other functions above to no role by default. If the server asks for a password for the role, give the role one (`ALTER ROLE reader PASSWORD 'a long password';`) and add `--password`; the message that says so names the role.
  An agent of a config that names it asks Dockingbird for one SQL statement that returns rows, and reads the rows as a file of JSON lines in its log folder. It never sees the database, its address or the password; a statement that writes, changes the transaction or runs past its time limit fails and changes nothing, and what the database says in its own words is never shown. The server must accept connections from Docker: on Docker Desktop your Mac is `host.docker.internal`; on a plain Linux Engine name the bridge's address instead, and let the server listen on it (`listen_addresses`) and accept it (`pg_hba.conf`). `--to AGENT --until ISO` gives the database to that running agent too. `dockingbird disconnect app-db` removes the connection and the password it kept.
- **A database the broker writes to.** `--writes` beside `--database` registers the database for writes through the broker: an agent's `bus_request` with `db.execute` gives one statement as `sql`, the values its `%(name)s` placeholders bind as `arguments` (each a whole number or a text; `{}` for none) and, optionally, the most `rows` it is answered; the broker runs it on its own connection in one read-write transaction, under the statement timeout and the row and byte bounds of a query, commits it when it succeeds and rolls it back on any refusal, and answers its rows (none for an `INSERT` without `RETURNING`). `db.query` keeps its proof that the role cannot write, so on a role that writes it is refused `role-can-write`, as today: such a connection's agents read with `db.execute` too.
- **A password vault (gopass).** `dockingbird connect logins --vault gopass --login alice https://site.example alice@site.example --totp alice` connects a gopass store for the configs that name `logins`: an agent of such a config, lent your Chrome (`--browser chrome`, below), can ask Dockingbird to sign in to `https://site.example` as the login `alice`, and Dockingbird types the stored password and, with `--totp`, the current one-time code itself, in a tab of its own, and leaves the agent's tab signed in. Each `--login` names a login by three words: its name (a slug, the agent's word for it and the store entry's name, never the site's), the site's address (its origin, `https://host` or `https://host:port`, stored as the browser serialises it) and the username; `--totp NAME` marks a login whose entry holds a time-based code. The store's passphrase is asked on your terminal, hidden (without a terminal it is read from what you pipe in), never empty, and kept inside Dockingbird as a database password is; a password or a code is never asked, read or shown by any Dockingbird command. The store is yours: a gopass store under `DOCKINGBIRD_HOME/vaults/logins` (the connection's name; `--store NAME` names another folder there), which Dockingbird reads from its own side only, read-only, with the gopass inside its image; Dockingbird runs no gopass on your Mac. You make the store with gopass 1.17.4, the version Dockingbird's image carries, from gopass's release at https://github.com/gopasspw/gopass/releases/tag/v1.17.4: the archive `gopass-1.17.4-darwin-arm64.tar.gz`, whose sha256 is `b052f36631e619fa9391edeee581d1f3937c4c41d432aa4ba673b53401800c0f` (check it with `shasum -a 256` before you open it), holds a `gopass` program to put on your `PATH`. Then, once per store: `GOPASS_HOMEDIR=~/.local/share/dockingbird/vaults/logins GOPASS_AGE_PASSWORD="<the passphrase>" gopass setup --crypto age --storage fs` (the `vaults/logins` folder of your Dockingbird home, which is `~/.local/share/dockingbird` unless you set `DOCKINGBIRD_HOME`: use that folder then) makes the store with an age identity under that passphrase (a bare `gopass init` fails: it needs an identity first); and for each login, `GOPASS_HOMEDIR=... GOPASS_AGE_PASSWORD=... gopass insert alice` with the password on the first line and, for a login with a code, the `otpauth://totp/...` line from the site's two-factor enrolment in the body (a counter-based `otpauth://hotp/...` entry is refused when used). Keep the whole folder `setup` made, its `.config` and `.cache` included: the reads need them. Before it says done, Dockingbird checks each word and that the store is a real folder of yours there, and prints `Connected logins: a gopass vault with 1 login.` and the line that names it in a config; `dockingbird connections` lists the vault by its logins' names only, `dockingbird status` by its store and those names, and `dockingbird clean --all` keeps your vaults folder whenever anything is in it. What an agent can do: ask for one sign-in at a time, by the login's name and the sign-in page's address on that site, naming the password field (and a username or code field) by CSS selector; it is told success or a refusal in words (the page not on the login's site, the field not a password field, the vault unreadable, the site not accepting the sign-in, a counter-based code, a browser without a window), never the password, the code, or how long either is. What it cannot do: read, list, add or change a login or the store; sign in on your own Chrome profile (sign-ins run only in a temporary profile, so Chrome's save-password offer and your Google account never see the password); ask on Firefox or Safari (refused in words: Chrome only in this release); do anything in the browser while the sign-in is typed (its commands are refused in words until it ends). The agent keeps the site session the sign-in made: its tab is signed in until the browser session ends with the agent. `dockingbird disconnect logins` removes the connection and the passphrase it kept; the store stays yours to delete.
- **Checking an agent's log for a value Dockingbird holds.** The coordinator can tell whether a text, or a running agent's harness log, holds any value it keeps (a vault passphrase, a database password, a sign-in's token, a saved key). It answers `{"holds": true}` or `{"holds": false}` and never the value, a count or a position. No Dockingbird command runs this check yet.
- **A folder of this Mac.** `dockingbird connect notes --folder ../notes` connects the folder for the configs that name `notes`: each of their agents reads it at `/dockingbird/folders/notes`, read-only, from its next start; an agent can read there, and cannot write, rename or delete there, unless the config gives it write access: a `[folders]` table beside `connections = ["notes"]`, with `notes = "write"` in it, mounts the folder read-write, and the agent can then create, change, rename and delete there, each change on this Mac at once; `read` is the default, and may be written out. None of this needs a git repo or GitHub: an added config with `workspace = "scratch"` runs its agent in an empty folder of its own, and every command of the route runs from any folder, your home included. Dockingbird must be set up once first, which `dockingbird login claude` (or `dockingbird login claude --api-key`) does from any folder; until then `connect` stops with status's "Dockingbird isn't set up yet." line, which names that step. To have an agent read a folder and write an analysis into it, once that is done: `dockingbird connect data --folder ../my-folder`; a file `analyst.toml` holding `command = "analyst"`, `workspace = "scratch"`, `connections = ["data"]` and a `[folders]` table with `data = "write"`; `dockingbird config add analyst.toml`; then `dockingbird start --command analyst "Read /dockingbird/folders/data and write analysis.md there."`, and `analysis.md` is in `../my-folder` the moment the agent writes it. Two agents with write access to one folder change the same files: Dockingbird locks nothing there, and the last write wins. Dockingbird records the folder's real path (a link on the way is followed; a path that is itself a link is refused, with the folder it points at to connect), refuses `/`, its own folder and a path with a character a mount can't take, and checks at every start that the folder is still there and still a folder; otherwise the start stops before anything is made and says so. Reads there aren't logged; the grant to each agent is, and agents can't ask for a folder they weren't given: it reaches them only as the mount. The folder must be under a path Docker Desktop shares (`/Users`, `/Volumes`, `/private` and `/tmp` by default); for another the start stops with the setting to change (Docker Desktop > Settings > Resources > File sharing). `dockingbird revoke notes --to reader-1` takes the folder from that agent by stopping it, since a mounted folder can't be taken away from a running agent, and names the command that continues it; `dockingbird disconnect notes` stops the agents that have it and names them.

- **A service (a program of this Mac).** `dockingbird connect convert --service ../convert.toml` connects a program of yours for the configs that name `convert`: their agents may ask to run it with arguments you allow, and it runs here, as you, only while you run `dockingbird serve convert`. The file says what runs and what an agent may choose; it must be yours, readable by you alone, not a link and not in `DOCKINGBIRD_HOME`:

  ```toml
  # ../convert.toml: what dockingbird serve convert runs when an agent asks.
  # The program, and the checkout it lives in at this commit (both or neither); serve won't run it once the checkout moved.
  program = "/path/to/convert/bin/convert"
  checkout = "/path/to/convert"
  commit = "9fceb02d0ae598e95dc970b74767f19372d61af8"
  # The most seconds one run may take; then it is stopped.
  timeout_s = 600
  # Its words: {output} is the folder it writes its result to (once), each {NAME} an argument below.
  argv = ["--pages", "{pages}", "--mode", "{mode}", "{output}"]

  # A whole number from 1 to 500.
  [arguments.pages]
  type = "int"
  minimum = 1
  maximum = 500

  # One of these words. A text argument is type = "text", with max_chars.
  [arguments.mode]
  type = "choice"
  choices = ["fast", "best"]
  ```

  `connect` checks every key and that `argv` uses each argument the file declares, checks that the checkout is at that commit, and runs nothing; it then names the program and the line that names it in a config (`connections = ["convert"]`). An agent of such a config asks for a run with `bus_request` and the arguments; its request waits for you, and `dockingbird status` says so ("runner-1's request to convert waits for its runner." and "Start it: dockingbird serve convert"). In a terminal, `dockingbird serve convert` checks the checkout once more, says "Serving convert: agents' requests to it run here, as you, one at a time.", and runs the waiting requests oldest first, one at a time. Before each run it checks the request again and refuses one that came too late, names a program or arguments the file doesn't allow, or finds the checkout moved or the program gone, a link, or writable by anyone else; nothing runs then. A `text` argument reaches the program as the agent typed it, so a program that reads one as a path or a command's name gives the agent that reach: declare `choice` or `int` where the program takes a path, a name or a mode. A run is the program alone, never through a shell, its words the file's with the request's checked arguments in their places, in its checkout, with five variables and nothing else of your shell's: `PATH` (the system's folders and Homebrew's), your `HOME`, `LANG=C.UTF-8`, a `TMPDIR` of its own and `DOCKINGBIRD_SERVICE_OUTPUT`, which holds the output folder's path, the path `{output}` stands for. Past `timeout_s` it is stopped, `SIGTERM` and then `SIGKILL` 10 s later (`SERVICE_STOP_GRACE_S`). The output folder is the result: what the program wrote there, with its output and errors (`stdout.txt` and `stderr.txt`), at most 64 MiB and 10,000 entries, links left out. It lands in the asking agent's log folder (`log/connections/<job>/`), the run's own folder on this Mac is removed, and `serve` names how the run ended ("Ran convert for runner-1: done in 3 s."). Ctrl-C, closing its terminal or ending `serve` (`SIGTERM`) stops it and a program it is running, and the agent learns its request didn't run. `dockingbird disconnect convert` removes the connection.

- **A service's credential and its Python body.** A service file may add `uses`, the database connection of the home whose credential each run gets (`uses = ["scores"]`): the broker puts its host, port, database and role, and the role's password when it has one, into that run's environment alone as `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER` and `PGPASSWORD`, never into a file, a log or an agent. A run's variables are one database's, so a run whose `uses` names more than one, or a connection that is not an enabled database of the home, is declined before it starts; the agent needs no grant on that database, its grant is the service's. In place of `argv`, a `[call]` table names a Python function in the checkout: `python`, the interpreter, relative to the checkout; `module`; and `function`. A run calls the function with the request's checked arguments as keyword arguments, and its return value, as JSON, is the run's `result.json`.
- **Serving every connection of a home.** `dockingbird serve --all` serves every service and browser connection of the home in one process, each as `serve NAME` does; `dockingbird serve --unit` prints the unit that runs it under the machine's service manager (a launchd property list on a Mac, a systemd user unit on Linux) and installs nothing: the fleet host's setup installs it, so a swarm's brokered commands run with no terminal open. `serve --all` never starts Docker or Dockingbird: while Docker does not answer (it is off, or restarting itself) or no coordinator runs, it ends with exit 1, and the unit starts it again every `SERVE_UNIT_RESTART_S` (10 seconds) until they answer; your `dockingbird stop` ends it with exit 0, and the unit leaves it stopped.
- **An MCP server.** `dockingbird connect search --mcp https://mcp.example/mcp` registers a streamable-HTTP MCP server for the swarm roles that list `search` in their `connections`: each of their agents' harness gets it as an MCP server beside Dockingbird's own at every start and uses its tools. The URL is `https` with a lowercase host, an optional port, a path and a query, no user and no fragment, at most `MCP_URL_MAX_CHARS` (2048) characters; nothing else is kept, and a server that needs a key is not served yet.
- **A role's grant, revoked and given back.** `dockingbird connect NAME --revoke --role ROLE` stops every running agent of the swarm role `ROLE` from using `NAME` at its next request, with no restart, and keeps it from every agent of the role that starts later (a restart, a replacement, a pickup, an added agent), which `fleet why` shows as `denied_by_role`, until `dockingbird connect NAME --to-role ROLE --until ISO` lifts the denial and grants the connection to the role's running agents until then; `--swarm KEY` narrows either to one swarm. `dockingbird disconnect NAME` still takes the connection from everyone.

- **A browser (Google Chrome or Firefox on this Mac).** Lending a browser needs a Mac host: on any other computer, `serve` refuses a browser connection before it opens anything. `dockingbird connect chrome --browser chrome` connects Chrome for the configs that name `chrome` (`connections = ["chrome"]`), and `dockingbird connect firefox --browser firefox` connects Firefox the same way (Safari is in the next item). An agent of such a config asks for the browser and waits until you run `dockingbird serve chrome` (or `dockingbird serve firefox`) in a terminal on this Mac: `serve` then lends the browser to the agent that asked, one at a time, either your own browser, with its logins, cookies and open tabs, or a fresh one that Dockingbird starts for that session alone, with none of your logins, and removes afterwards. Each request picks which, and your own is the default.
  For your own Chrome, open `chrome://inspect/#remote-debugging` in it once, turn remote debugging on, keep Chrome running and click Allow when Chrome asks (it asks for each use). For your own Firefox, quit Firefox before the first request that asks for it: `serve` then starts Firefox on your profile with remote control on, keeps it for its later requests and closes it when `serve` stops; a Firefox you opened by hand instead is refused with that step, since Firefox takes remote control only when started with it, and Firefox shows no dialog. The agent browses any website and Dockingbird restricts nothing it does there; in your own browser it can act as you on every site you are signed in to. It keeps the browser until it lets go, its container ends, the browser closes, the session's time limit (`SERVICE_JOB_MAX_S`) passes or you press Ctrl-C, which also stops `serve`; a fresh browser and its folder are then removed, and your own browser and its tabs are left as they are (in your own Firefox, the tabs the agent opened, and the pages those tabs opened, are closed when its request ends; your tabs stay, those you opened meanwhile too). The browser loads pages with your Mac's network, not the agent's, so the agent's network access setting does not limit what it reaches through it.
  The agent's clicks, typing, key presses, scrolling, hovering and dragging on a page are real mouse and keyboard input on this Mac when the browser has a window on screen: `serve` moves your pointer along a human-like path and types at a person's pace, brings the browser to the front for that command alone, and refuses when another app's window is in front of the target, so nothing lands in another app. That needs Accessibility for the app you run `serve` from (System Settings > Privacy & Security > Accessibility: turn the app on, reopen it, run `serve` again), and a screenshot of your own Safari needs Screen Recording (Screen & System Audio Recording) the same way. Start `serve` from Terminal with Terminal turned on: a `serve` started by an agent app (Codex) counts as its own program, which no app's switch covers. `serve` says at its start which switch is off, says each input as one line (what the agent did and where, the path's points and milliseconds, and whether it was real input or the browser's own input along the same path) and says each refusal. The pointer and keyboard are shared while an agent acts; moving the pointer into a corner of the screen stops an input (the fail-safe). A temporary browser started with `DOCKINGBIRD_BROWSER_HEADLESS=1` in `serve`'s environment has no window, so the agent's input is the browser's own along the same path; the tests use that.
- **Safari on this Mac.** `dockingbird connect safari --browser safari` connects it the same way, for the configs that name `safari` (`connections = ["safari"]`), and `dockingbird serve safari` lends Safari to the agent that asked, one at a time: either your own Safari, with its logins and open tabs, or an automation window that Dockingbird opens for that session alone through Apple's `safaridriver` (Safari's own isolated window with the orange address field, which starts from a clean slate and cannot reach your history, AutoFill or logins) and closes afterwards. Each request picks which, and your own is the default.
  Once, in Safari, open Settings > Advanced and turn on "Show features for web developers"; then in Settings > Developer turn on "Allow Remote Automation" (for the automation window) and "Allow JavaScript from Apple Events" (for your own Safari). The first time an agent uses your own Safari, macOS asks whether the app running `dockingbird serve safari` (your terminal app) may control Safari: click OK; `serve` says so and waits. A screenshot of your own Safari needs Screen Recording permission for that app (System Settings > Privacy & Security > Screen Recording). In your own Safari the agent works in a Safari window of its own, which each request opens, and leaves your windows as they are (it can still switch to one of your tabs, which brings that window to the front), so you can keep using Safari meanwhile; its window and tabs stay open afterwards. There the agent acts as you on every site you are signed in to, and its clicks and keys are the page's own events (a site that reacts to real input alone ignores them). In the automation window a mouse click reaches the page only while Safari is the frontmost app; otherwise the agent's click is sent as the page's own event, and the agent's answer says which it got (`event`: `mouse` or `page`). Dockingbird never activates Safari, never closes its windows and never quits it. If `serve` says Safari still keeps the automation of an earlier request that was cut short, quit Safari and open it again, then let the agent ask again; don't close the orange automation window, which can crash Safari.
- **A browser of its own, in Docker (`browser = "chrome"`).** An added config with `browser = "chrome"` gives each of its agents a Google Chrome of Dockingbird's own: a full, headed Chrome on a virtual screen, in a container beside the agent's (`dockingbird-browser-<name>`, see "What lives where"), on the agent's network and behind its proxy under `allowlist` or `models`, so the agent's network setting bounds what the browser reaches. No `connect` or `serve` is needed, nothing runs on your Mac, and no login of yours is in it. The agent drives it through the same browser tools, which it has whatever the config's `tools` key says; its clicks, typing and keys are real mouse and keyboard input on that screen (a page sees them as a person's, `isTrusted: true`), and the agent reaches the browser only through a socket the two containers share, never its screen or its debugging port; what the browser itself can read (a `file://` address of its own container's files, its password for `watch` among them) the agent can read through it, and nothing of your Mac is there. Only a config you added may ask for one: a repo's own config that does is refused at its start. `dockingbird watch NAME` shows that screen in your VNC viewer and lets you take over (see "The commands"); anything you type there is the agent's to read. What a page sees there: a Linux Chrome (`navigator.platform` `Linux x86_64`, the client hints `Sec-CH-UA-Platform` `Linux` and `Sec-CH-UA-Arch` `arm`), `navigator.webdriver` false, a 1440x900 screen and no WebGL, as a Chrome on a Linux computer without a supported GPU shows (a page that needs WebGL shows its fallback). Its fonts show Latin, Greek and Cyrillic, Chinese, Japanese and Korean, Arabic, Hebrew, Thai, Devanagari (Hindi), Bengali, Tamil, Armenian and Georgian text, and emoji, so a page in any of these shows its letters, not empty boxes. Dockingbird passes your Mac's time zone and language to the browser's own process, and the image's Chrome follows them (the zone follows `TZ`, the language follows `LANG`, so a German Mac gives pages `de-DE`). Dockingbird spoofs no other identity: a site can tell it from a Mac.
- **A local model on this Mac (`local_model`).** An added config with `local_model = "ai/qwen3:4b-instruct-2507-mlx-4bit"` runs its agents' Claude Code or Codex against that model, which Docker Desktop's Model Runner serves on this Mac with its vLLM backend: the model runs on the Mac, since a container gets no Metal GPU, and the agent reaches it at `http://model-runner.docker.internal`. Set it up once, yourself: Docker Desktop 4.62 or later on macOS 15 or later; Model Runner turned on (Docker Desktop's Settings > AI > Enable Docker Model Runner, or `docker desktop enable model-runner --tcp 12434`; it is off until you turn it on); its vLLM backend installed with `docker model install-runner --backend vllm`; the model pulled with `docker model pull ai/qwen3:4b-instruct-2507-mlx-4bit`; and, when a turn is refused for its length, a larger context with `docker model configure --context-size` (Claude Code's first request is long, and it takes an unknown model's window to be 200k). Dockingbird turns nothing on, installs nothing and pulls nothing. A config for it is three lines, `command = "local"`, `local_model = "ai/qwen3:4b-instruct-2507-mlx-4bit"` and `egress = "models"`, added with `dockingbird config add PATH`. The tag is the model's whole tag as `docker model ls` lists it, at the config's top level or in a command's table, and only a config you added may name one: a repo's own config that does is refused when it is read, and so is a config that also sets the model in `harness_args`, since the agent's tool gets the model as `--model` and the tag; a start of such a config that gives `--model`, `-m` or `--fallback-model` after `--` (or a pick-up that carries one from the agent's last start) is refused the same way, and so, for Codex, is one that would send its requests elsewhere (`--oss`, `--ignore-user-config`, `--profile`, or `-c openai_base_url=...`); `-c model=...`, `-c model_provider=...` and `-c model_providers...` pass, since Codex keeps the config's model and the image's `openai` provider over them. Such an agent gets no saved key and no sign-in of yours: its tool talks to Model Runner with a fixed placeholder key, which is no secret. In `models` and `allowlist` its own proxy admits Model Runner, and no other agent's proxy does; in `full` it reaches Model Runner directly; in `none` it has no network to reach it on, so that start is refused. Before it makes anything, the start checks the egress mode, then `docker model status --json`, then `docker model ls --json`, and each missing piece stops it in words that name your command: Model Runner off (the switch, and the command that turns it on), a Model Runner other than Docker Desktop's, the vLLM backend missing (`docker model install-runner --backend vllm`), still installing or in error (`docker model status` shows it), the model not pulled (`docker model pull` and its tag), or an answer Dockingbird doesn't read (the command to run, to see what it says). `dockingbird status NAME` shows a `local model` row from what the start recorded, with no call to Docker. Tool calls need a model whose chat template the Hermes tool parser reads, which Model Runner's vLLM backend always uses (a Hermes-style `<tool_call>` template, as Qwen3-4B-Instruct-2507's); a small model may still answer a tool call as text. What this release does not do: a bus start still needs the tool's sign-in on this Mac, though such an agent never uses it; Dockingbird has no context-window setting of its own; `dockingbird set local-1 --model claude-opus-5-5` does not change such an agent's model, since Model Runner serves only the model the config names: it is refused and changes nothing, while `--effort` and `--compact-at` alone still apply; there is no GUI form for it; and Model Runner on Docker Engine (Linux) or Docker Cloud is not supported.

**What the labels mean.** A message delivered is not a message accepted, and an agent's "done" is its own report, never Dockingbird's verification: read its results before you rely on them.

**Status.** `dockingbird status` shows what needs you first: each question an agent asked you that is still open, of every kind, the ones `dockingbird questions` lists ("notes-1 asks" and its first line), with the `questions` command that shows it whole by its row number, each agent that has ended with messages still waiting for it (how many wait, and the command that continues the agent and hands it them: "pick it up: dockingbird notes --as notes-1"), and each agent running in a terminal with messages waiting for it ("manual wake required: type anything in its terminal"). An answer you give settles its question, which then leaves the list. Below that, each repo's agents: a config's agent is labelled with its command and mode ("notes-1 (notes, bus)"), an agent of the default environment with its name alone. When nothing needs you, the screen ends with "Nothing needs your attention." It only looks: it reads the questions when an agent's row counts one, the inboxes only while your host client is open, and opens nothing itself.

**Clean.** `dockingbird clean` asks about an ended agent's results with its kept copy, and removes them only together; `dockingbird clean --all` names the agents whose results go and the configs you added, then removes the agents' proxies and networks (and the shared `dockingbird-out` bridge), `results/`, `configs/`, `trust/`, `untrusted/` and `connections/` with the rest (a `config.toml` holding anything you wrote, your `trust` line among it, stays; one holding only Dockingbird's own build-timer line goes), and disconnects each harness `dockingbird mcp install` connected with that harness's own remove command, run from the `claude` or `codex` your `PATH` gives now, naming the command to run for one it could not (and then exiting 1). A repo's own `.dockingbird/` folder and the copies `dockingbird results notes-1 --to DIR` made are never touched.

**Egress and networks.** Each agent started for a task gets its own network, `dockingbird-net-<name>`, that no other agent joins. In `allowlist` and `models` that network is internal (no route out, no gateway address, no IPv6), and the agent's own egress proxy, `dockingbird-proxy-<name>`, sits on it and on `dockingbird-out`, the one NAT bridge the profile's proxies share and no agent joins; under `full`, the default, the network is an ordinary bridge with NAT out and no proxy, and with `--egress none` there is no network (`--network none`). `stop` removes the proxy, then the network, after the agent's container; the sweep removes a crashed agent's proxy and network with its container (and any an agent left behind, and the bridge once no proxy is left), and a start removes a leftover of its own name before it makes a new one. "Egress and what stays open", below, says what each mode reaches.

**What an agent can run.** Inside its container an agent has git, `python3` (3.12.14, also `python3.12`) with `uv`, the C and C++ build tools (`gcc`, `g++`, `make`, `pkg-config`), Node.js 24 (`node`, `npm`, `npx`) and Go 1.27, ripgrep 15.2.0 (`rg`) and ast-grep 0.51.0 (`ast-grep`), the code-finding tools the agent's rules name, all read-only and pinned in the image. `pip3`, `pip` and `pip3.12` are that interpreter's pip. Anything else its repository needs it installs under its own HOME with the plain commands: `pip install` (or `pip3`, `python3 -m pip`) lands in `~/.local`, which `python3` reads (Dockingbird's own environment never does), `npm install -g` lands in `~/.npm-global`, and `go install` in Go's workspace under the home, whose `bin` folders come first on its `PATH` (`uv`, `rustup` and `foundryup` work there too); that HOME, with every cache under it, is on the container's own volume on Docker's disk (no size cap but that disk's space) and goes with the container, so such installs repeat at every start, and `apt-get` does not work there (no root, read-only root). A repository whose `go.mod` asks for a newer Go gets it through the `go` command itself, checked against Go's checksum database.

### Your own commands (configs)

A config is a small TOML file that adds commands of your own to Dockingbird, such as `dockingbird review "Check the login flow"`. Each command runs Claude Code or Codex, never any other program, with the settings you chose filled in: the model, a skill as the agent's first turn, instructions for its role, where it works (a copy of this repo, or an empty scratch folder), and whether it works in the background on the message bus or at your terminal. Its agents are named after it: `review-1`, `review-2`. A command is a preset, not a new tool: `dockingbird review "Check the login flow"` is `dockingbird start --command review "Check the login flow"`, and the agent it starts is a delegated agent like the ones above.

**Dockingbird ships no such command.** Every command of this kind comes from a config file in your repo, or one you added. The names in this guide, `notes`, `review` and `triage` (and agents such as `notes-1`), are examples. None of them exists until a config of yours adds it.

**Where configs come from, and which wins.**

- **This repo's own.** Each `*.toml` file in the `.dockingbird/` folder at the top of a checkout is a config. Its commands exist in that checkout only, with nothing to register, and the file is read again at every start, so an edit counts from the next one. Commit the folder and every clone of the repo has the commands.
- **Added.** `dockingbird config add agents/triage.toml` copies a config, with the files it names, into Dockingbird (`DOCKINGBIRD_HOME/configs/`), and its commands then work in every repo. The copy is what runs: after you change the file, add it again (it says "Replaced triage (was 7608094fd9980624; connections: github-issues)"). An added config takes its file's name unless you give it another as you add it (`dockingbird config -h` shows how), and its commands can't be another added config's.
- **One name in both.** In that checkout the repo's own command wins, and `dockingbird -h` says so: "configs/triage/config.toml: commands.triage is replaced here by this repo's own".
- **One name in two of the repo's configs.** Neither runs: "... is in another config too, so neither runs".
- **A built-in's name.** A config whose command is named like one of Dockingbird's own (`status`, `start` or `claude`, for example) is refused whole: none of its commands exist, `config add` refuses it, and `dockingbird -h` and `dockingbird config list` show it as ".dockingbird/app.toml: invalid (command: a name Dockingbird keeps)". A built-in command always wins.
- **The default.** One command of a repo's configs may say `default = true`: in that checkout `dockingbird start "Check the login flow"`, with no `--command`, then runs it and says so first ("Using review from .dockingbird/app.toml for this checkout"). Two configs that each mark one cancel each other out, a config that marks two is refused whole, an added config's is ignored, and `dockingbird claude` and `dockingbird codex` never use one.

**A complete example.** This config, in the repo's `.dockingbird/` folder, adds `dockingbird review`. It sets every key a config of one command can hold but `connections` and `browser`, which only an added config may use (below), each under a comment that says what it does and its default; leave a key out to take its default.

<!-- config-example:project app -->
```toml
# .dockingbird/app.toml: adds dockingbird review in this checkout. Every key is optional.

# The command: dockingbird review "...", agents review-1, review-2. Default: the file's name, app.
command = "review"
# Its one line in dockingbird -h and config list, and for your own harness through dockingbird mcp. Default: none.
summary = "Review this branch and list what to fix"
# true: dockingbird start with no --command runs review in this checkout. Default: false.
default = false
# On the bus, this file's text, with $TASK replaced by the task, is the first turn. Default: none.
skill = "skills/review.md"
# Role text, given to the agent after Dockingbird's own rules. Default: none.
instructions = "review-role.md"
# claude or codex. Default: claude. Set here, it is fixed: a start's --harness can't change it.
harness = "claude"
# repo: a copy of this repo; scratch: an empty folder of its own, no git repo needed (an added config's command then runs from any folder). Default: repo.
workspace = "repo"
# bus: in the background, through messages; terminal: at your terminal. Default: bus. Set, it is fixed.
mode = "bus"
# kept: one conversation for all its deliveries; fresh: every task delivery starts a new conversation, under the same rules (bus only). Default: kept.
context = "kept"
# true: load the repo's own Claude Code or Codex settings, hooks and MCP servers, once trusted. Default: false.
repo_settings = false
# Its tools: "bus" (messages and files), "default" (claims and commits) or "full" (both). Default: "bus".
tools = "bus"
# allowlist: through a proxy of its own, its tool's hosts and those of allow; models: its tool's hosts alone; none: no network, not even its model's API; full: its own network, open to the internet. Default: full, or what dockingbird egress set.
egress = "allowlist"
# With allowlist, what else it may reach: the presets registries (package registries) and github (GitHub's content), or hosts such as "docs.python.org" and "*.corp.example". Default: the list dockingbird egress set, else nothing beyond its tool's own hosts.
allow = ["registries", "github"]
# Fixed arguments for the tool, such as its model. Default: none.
harness_args = ["--model", "claude-haiku-5-5"]
# Its harness's own settings file, the base under Dockingbird's own keys: a path beside this file, or a table by harness. Default: none.
harness_config = { claude = "claude-settings.json" }
# mise's environments for its agents, comma-separated: "ci" makes mise read mise.ci.toml over mise.toml (MISE_ENV). Default: none.
mise_env = "ci"

# Variables the agent's tool sees: settings, never secrets. Default: none.
[env]
REVIEW_STYLE = "short"

# Bounds on an agent that works on the bus.
[limits]
# A turn that runs longer is interrupted and reported; at least 1.
# Default: no turn deadline (a stuck turn ends with the session).
turn_minutes = 20
# The agent stops itself after this many hours; at least 1, and at most
# the installation's maximum (168 by default). Default: 12.
session_hours = 4

# What a failed turn does on the bus: a retry, or a move to the other tool with the agent's conversation ("A fallback tool", above). Default: none (every failure is reported).
[fallback]
# The tool to move to: claude or codex, never the harness above. Default: none (no move; the rules still retry and report).
harness = "codex"
# That tool's model. Default: the tool's own.
model = "gpt-6-luna"
# That tool's effort. Default: the tool's own.
effort = "high"
# any: start anyway where that tool isn't signed in, with the move off; require-login: start only where it is. Default: any.
placement = "any"
# The wait before a retry, in seconds, minutes or hours (30s, 5m, 1h), at most 24h. Default: 5m.
retry_wait = "5m"
# The retries in a row of one delivery, from 1 to 100. Default: 3.
retry_max = 3

# Each class's rule: retry, retry-then-fallback, fallback or report (exited is always report). A class left out takes its default.
[fallback.on]
refusal = "fallback"
server = "retry"

# Skills its tool lists (Claude Code's Skill tool and / menu, Codex's $ mention): one skills folder, or skill folders, each a path from this checkout's top. Default: none.
[skills]
path = ".agents/skills"
# Where they go in the agent's home: both (~/.claude/skills and ~/.agents/skills), claude or agents. Default: both.
into = "both"
```

The skill it names, `.dockingbird/skills/review.md`, is plain Markdown:

```markdown
Review the changes on this branch for this task:

$TASK

List what to fix, file by file, in a Markdown file you attach, then mark the task done.
```

`.dockingbird/review-role.md` holds the role in a few lines of your own, such as "You review code; you never change it." Some keys need more than their line:

- **`[limits]` fix what they name.** When the config or its command names a `[limits]` key, its agents run with that value, the way `harness` and `mode` fix theirs. With `cpus = "2"`, `dockingbird review --cpus 4` is refused ("review runs with limits.cpus = 2: .dockingbird/app.toml says so."). `--memory` and `--session-hours` are checked the same way against a `memory` or a `session_hours` the file names. Typing the same value is no clash. A key the file leaves out is set by the flag. A config that names no `session_hours` runs its agents for `--session-hours`, else the default, 12 hours.
- **`harness` and `mode` fix what they set.** This file sets both, so `dockingbird review --terminal` is refused ("review runs with mode = bus: .dockingbird/app.toml says so."). So is `--harness codex`. When a key is left out, each start chooses it with `--terminal` and `--harness`.
- **`tools` decides whether the agent can share commits.** With `bus`, the default, the agent reports through messages and the files it attaches, and shares no commits. `full` adds the claim and submit tools, so its commits reach you through `dockingbird sync`, as every agent's do. A config with a browser (`browser = "chrome"`) has the browser tools whatever `tools` says.
- **`skill` is the first turn on the bus only.** At a terminal the task arrives as a message, and the skill isn't used yet.

A config can also hold several commands. Write one `[commands.NAME]` table for each (`[commands.review]`) in place of `command`, `default` and `skill` at the top. Each table may set its own `summary`, `default`, `skill` and `instructions`. It may also set any other key to override the config's. The keys at the top become every command's defaults, with two exceptions. The top `instructions` come before each command's own. A top `summary` reaches no command, so give each table its own.

This added config gives every repo `dockingbird triage`, with Codex:

<!-- config-example:registered triage -->
```toml
# agents/triage.toml, in a folder of yours (not Dockingbird's own).
# dockingbird config add agents/triage.toml then adds dockingbird triage to every repo.
command = "triage"
summary = "Sort the failing tests and open TODOs into a short plan"
harness = "codex"
# An added config's harness_args and [env] apply at once: you chose to add it.
harness_args = ["--model", "gpt-6-luna"]
# Connections you recorded with dockingbird connect, by name; only an added config may name one.
connections = ["github-issues"]
# chrome: a Google Chrome of Dockingbird's own, in a container beside the agent's, which dockingbird watch shows; only an added config may ask for one. Default: none.
browser = "chrome"
```

`dockingbird config add agents/triage.toml` says `Registered triage: dockingbird triage "task" (connections: github-issues)`. The keys it leaves out take their defaults. It leaves out `mode`. So `dockingbird triage --terminal` runs Codex at this terminal, and `dockingbird triage "Sort the failing tests"` runs it on the bus.

**Chrome extensions and policies.** An added config whose browser is Chrome may give it extensions and Chrome policies too. Two more keys do that. `browser_extensions` is a list. Each entry is a Chrome Web Store link (`https://chromewebstore.google.com/detail/...`, or the older `https://chrome.google.com/webstore/detail/...`), a bare 32-letter extension id, or a folder of yours that holds a `manifest.json`, its path starting with `/` or `~/`. `[browser_policy]` is a table of Chrome policies by Google's names, with their values. For example:

```toml
browser = "chrome"
browser_extensions = [
  "https://chromewebstore.google.com/detail/ublock-origin-lite/ddkjiahejlhfcafbddmgiahcphecmpfh",
  "/path/to/my-extension",
]
[browser_policy]
URLBlocklist = ["file://*"]
```

- **Only an added config, and only with a browser.** A repo's own config that names either key is refused, as one that names `browser` is. Either key without a `browser` is refused too. A command may set its own list or table, which replaces the config's.
- **The policies Dockingbird keeps.** It refuses the policies that would cut its own control of the browser (its DevTools port, its proxy, its profile) and the two it writes itself: `RemoteDebuggingAllowed`, `DeveloperToolsDisabled`, `DeveloperToolsAvailabilityAllowlist`, `DeveloperToolsAvailabilityBlocklist`, `ProxyMode`, `ProxyServer`, `ProxyPacUrl`, `ProxyBypassList`, `ProxySettings`, `ProxyServerMode`, `UserDataDir`, `ExtensionInstallForcelist` and `ExtensionSettings`. `DeveloperToolsAvailability` may be 0 or 1 only.
- **Folders are packed when you add the config.** `dockingbird config add agents/surf.toml` packs each folder as an extension, signed with a key Dockingbird keeps for that folder under `configs/.extension-keys` in its folder. The same folder therefore keeps its extension id whichever config names it. A folder you move gets a new key and a new id. The command says each folder's id and version. Files and folders whose names start with a dot are left out, and it says how many. To change the extensions or the policies, edit the file and add it again. The packed copy is what runs, so a change to a folder counts once you add the config again, and only agents started after that get the new set.
- **Web Store extensions need the internet.** Chrome downloads them from Google at each start, so a start with egress `none` is refused; under `allowlist` or `models` the agent's proxy admits Google's two update hosts, clients2.google.com and clients2.googleusercontent.com, and since the browser shares the agent's proxy, the agent can reach them too, which the start says.
- **What Chrome shows, and what Dockingbird says.** Chrome shows "Managed by your organization" in its menu. `dockingbird status NAME` shows the agent's extension ids and each policy's state as Chrome's own policy page showed it (applied, not applied with Chrome's words, or not on the page), or that the page could not be read, and the start says which policies Chrome did not apply or could not be read for. An extension that never starts stops the browser, and the start fails naming it.

**Skills.** A skill is a folder holding a `SKILL.md` and the files it uses (scripts, references, Codex's `agents/openai.yaml`), named by its folder, and a config's `[skills]` table gives its agents skills their tool lists as its own, and `dockingbird set NAME --skills PATHS` adds more to a running agent from its next turn (see [Delegated agents](#delegated-agents)). (`skill`, singular, is another key: the first turn's text; `skills` are the tool's skills.)

- **`path`** is one skills folder, each of whose folders holding a `SKILL.md` is one skill (`path = ".agents/skills"`), or a list of folders, each one skill or a skills folder (`path = [".agents/skills/review", "tools/skills"]`). A repo's own config names paths from the checkout's top. An added config's are relative to its file's folder, and `config add` copies them with it, so its skills are the ones it had when you added it, until you add it again.
- **`into`** is where they go in the agent's home: `both`, the default, writes each skill to `~/.claude/skills`, where Claude Code finds personal skills, and to `~/.agents/skills`, where Codex finds a user's; `claude` or `agents` writes only that one.
- **Trust.** A repo's own config's skills apply only in a checkout you have not marked untrusted (below); an added config's, and the ones `--skills` names, apply everywhere.
- **`SKILL.md`** is placed as it is, its frontmatter and any hooks it names included. Codex lists no skill whose `SKILL.md` lacks a frontmatter naming a `description`, while Claude Code lists one with no frontmatter among its slash commands.
- **One name in two places.** When the checkout's own `.claude/skills` or `.agents/skills` holds a skill of the same name and its tool loads it, Claude Code lists only the one in your personal folder, the one Dockingbird wrote; Codex lists both.
- **How each tool lists them.** Claude Code lists them within 1% of its context window, each description cut at 1,536 characters. Codex shows a table of its skill roots, each with an alias (`r0`, `r1`, ...), `~/.agents/skills` among them, and one line per skill naming its `SKILL.md` under its root's alias; its list fits in 2% of its context window (8,000 characters when it doesn't know the window), each description cut at 1,024 characters, and past that budget it shortens the descriptions, then leaves out whole skills, user skills (the ones in `~/.agents/skills`) first. For an agent with skills, Dockingbird sets Codex's `skills.max_context_tokens` to its cap, 10,000 tokens. A skill whose `agents/openai.yaml` turns implicit use off (`allow_implicit_invocation: false`) is left out of Codex's list and reached by a `$` mention alone.

**Running and seeing them.**

```bash
dockingbird review "Check the login flow"                   # review-1 starts in the background
dockingbird start --command review "Check the login flow"   # the same, spelled out
dockingbird triage --terminal                               # Codex at this terminal
dockingbird -h                                              # every command, with its summary and file
dockingbird config list                                     # every config here, and what can't run
dockingbird status review-1                                 # one agent in detail
```

- **Options.** A command takes all of `start`'s options except `--command`: `--terminal`, `--harness`, `--compact-at`, `--session-hours`, `--as`, `--new`, `--file`, `--task -`, `--skills`, and the tool's own arguments after `--`. `dockingbird review -h` shows `start`'s help, since that is what it runs. Without a task the agent starts idle and waits for one, such as `dockingbird send review-1 "Start with the parser"`.
- **`dockingbird -h`** lists each command after the everyday ones, with its summary and the file it comes from (`.dockingbird/app.toml`, or `configs/triage/config.toml` for an added one), then a line for each config, key or command that doesn't apply, naming its file and key, and why for a config it refuses, never a value.
- **`dockingbird config list`** shows each config, this repo's first: its name, where it comes from ("this repo" or "added"), its commands, workspace, mode and connections, and the start of its digest, with the config's summary under its row when it has one; then the same lines about what doesn't apply.
- **`dockingbird status`** labels a config's agent with its command and mode ("review-1 (review, bus)"), and `dockingbird status review-1` shows it in detail, with the connections its start granted. You talk to an agent on the bus as to any delegated agent: `dockingbird wait review-1`, `dockingbird inbox`, `dockingbird read 1` and `dockingbird results review-1`.
- **Your own harness.** Your own Claude Code or Codex can start these commands too, through `dockingbird mcp` (next section).

**Removing them.** `dockingbird config remove triage` removes an added config's copy ("Removed triage."). A repo's own command goes when its file leaves `.dockingbird/`. Either way, agents already running keep the config they started with. `dockingbird clean --all` removes the added configs with everything else, and never touches a repo's `.dockingbird/` folder.

**Trust and secrets.**

- **Trust.** A repo's own config comes with the repo: whoever can push to it, or wrote a repo you cloned, decides what it says. So in a checkout you marked untrusted (`dockingbird trust --off`) five of its keys are off: `harness_args`, `[env]`, `[skills]`, `harness_config` and `repo_settings = true`. Until `dockingbird trust` marks it trusted again its commands run without them, and `dockingbird -h` and `dockingbird config list` name its `harness_args`, `[env]`, `[skills]` and `harness_config` (".dockingbird/app.toml: harness_args applies after dockingbird trust", ".dockingbird/app.toml: env applies after dockingbird trust", ".dockingbird/app.toml: skills applies after dockingbird trust"). An added config's `harness_args`, `[env]`, `[skills]` and `harness_config` apply everywhere, since you chose to add it; its `repo_settings = true` still loads a repo's own settings only in a checkout you have not marked untrusted.
- **Tool arguments.** `harness_args` take only Claude Code's `--model`, `--fallback-model`, `--max-turns` and `--effort` (one of `low`, `medium`, `high`, `xhigh`, `max`, exactly: Claude Code would take another word with a warning and run at its default effort), and Codex's `--model`, `-m` and `-c model_reasoning_effort=LEVEL` (its effort, any level its model takes), each followed by its value. Dockingbird places them after its own flags and before your arguments after `--`; a flag you give after `--` replaces the config's same flag, so Codex never sees its model flag twice. Anything else, such as a settings file or the hook-trust bypass, is refused, and the refusal names the flags that are allowed.
- **Credentials.** Only an added config may name your credentials, and only by the names of connections you recorded with `dockingbird connect`, never as a value: `connections = ["github-issues"]`. A repo's own config that names one is refused at its start, with the step to add it instead. Each start of an added config's command grants its connections to that agent's session, for at most its `session_hours`, and a name you haven't recorded, or have disabled, stops the start. `dockingbird status triage-1` lists them, and its newest request through them.
- **Secrets.** A value in any config's `[env]` flows unchanged into the agent's environment, where the agent can read it and send it out, so a key or a password goes in an added config, never in the repo's `.dockingbird/app.toml`, which is the repo's content. To share a secret with a team, use mise's sops route: make an identity with the age tool (`age-keygen -o key.txt`; mise has no command of its own for this), encrypt the file to its recipient (`sops encrypt -i --age "age1..." .env.json`), commit the encrypted file, and list it in the repo's `mise.toml` as `_.file = { path = ".env.json", redact = true }`. Then give your agents the identity as `MISE_SOPS_AGE_KEY = "AGE-SECRET-KEY-1..."` in an added config's `[env]`, never in the repo's `app.toml`: mise decrypts the file as it sets up the agent's environment, the agent's tool gets the values and the key, and mise shows the key's value as `[redacted]` in output it captures. A file that doesn't decrypt stops the agent before its tool starts, with mise's own words. An SSH key is not an identity for a sops file: make an age identity. Dockingbird refuses a config holding one of its own tokens, and at a start one holding a sign-in or API key it keeps; it guesses at no other format.

**Continuing an agent.** Continuing one of these agents after it ended is covered under **Names** in [Your first run and a normal day](#your-first-run-and-a-normal-day).

### Harbor benchmark tasks

Dockingbird's `harbor` commands run the Harbor benchmark tasks you write (one task per branch of the task repository) on this Mac, with Harbor pinned to the commit the task repository's CI pins and installed under Dockingbird's own folder: nothing to set up, and nothing left behind.

- **What to type.** In the task's folder, `dockingbird harbor baseline` runs the two checks the task repository asks for in one command: an `oracle` job (its `solution/solve.sh` must score 1), then a `nop` job (an agent that does nothing must score 0); `dockingbird harbor baseline -k 3` runs the oracle three times. It ends with "Both baselines pass: oracle scored 1 and nop scored 0 on every attempt." or names each failing trial with the last lines its verifier printed. `dockingbird harbor run -a claude-code` runs one real trial with Claude Code and your own login (below). `dockingbird harbor run` passes every other word to Harbor's own `run` as Harbor reads it (`-k 3`, `--timeout-multiplier 2`, `--ak version=2.1.285`), after Dockingbird's checks; `--harbor-commit SHA` runs another Harbor commit, and `--keep-images` keeps the images a job built, for a faster next run. `dockingbird harbor jobs` lists what ran, `dockingbird harbor results JOB` shows each trial's reward, `dockingbird harbor clean` removes the jobs, and `dockingbird harbor version` shows the pin. `dockingbird harbor check`, which would pass a bundle to `harbor check` (a model reads it, and your subscription or key pays), is not built yet and says so; nothing else will ever run it.
- **The first run.** The first command that needs a commit installs it under `DOCKINGBIRD_HOME/harbor/install/`: a clone of Harbor at that commit, its own locked packages in a virtual environment made from Dockingbird's interpreter, and a check of the private Harbor attributes Dockingbird's plugin relies on; one live line shows the step. The commit comes from `--harbor-commit`, else the task repository's `.github/workflows/validate-harbor.yml`, else Dockingbird's own pin; `dockingbird harbor version` says which. A commit the plugin was not tested with runs `oracle` and `nop` and refuses `claude-code`, unless `--harbor-commit` named it.
- **Where the jobs are.** `DOCKINGBIRD_HOME/harbor/jobs/<job>/`, named `<task>-<agent>-<date>-<time>` unless you pass `--job-name`. Each holds Harbor's own files (each trial's `result.json` and its `agent/`, `verifier/` and `artifacts/` folders, which Harbor makes writable by everyone, `chmod 777`, inside Dockingbird's folder that only you can enter) and Dockingbird's `dockingbird.json`: the pin, the task, the agent, the credential's kind, the times, Harbor's status and what was removed. `-o DIR` puts a job in a folder of yours instead; it must exist already (Dockingbird makes no folder outside its own), and `dockingbird harbor jobs` does not list it. A job is `running` while the command that started it runs (it holds the job's lock), `done` once Harbor wrote its result, else `stopped`. With `--json`, Harbor's own output goes to the job's `dockingbird.log` and the envelope stands alone.
- **Your login for a real trial.** `-a claude-code` needs a Claude credential inside the task's container for the whole trial, and Dockingbird lends one from its own store, in this order: a token or key you saved (run `claude setup-token` in a terminal, then `pbpaste | dockingbird login claude --oauth-token -`; or `dockingbird login claude --api-key`), else the copy of this Mac's own login that Dockingbird follows, but only when that login's expiry covers the trial: the task's `[agent] timeout_sec` and its `[environment] build_timeout_sec` (600 s when unset), each times the multiplier you pass (`--timeout-multiplier`, or the phase's own), plus Harbor's set-up and a margin (`HARBOR_SETUP_ALLOWANCE_S` and `HARBOR_SIGNIN_MARGIN_S`), the trial's run counted for every wave of its attempts (`-k` attempts, `-n` at a time, each retried `-r` times) with the verifier's timeout and a retry's wait between one run and the next. A login that ends sooner is refused before anything runs, saying how long it has and how long the trial needs; so is a task that sets no `[agent] timeout_sec` on that path; with neither a saved token nor a login, "No Claude sign-in or saved key is stored, so a claude-code trial can't run." Keep a token saved if you run trials often: a login your own Claude Code refreshes lasts hours, a `setup-token` token much longer. The value reaches the task's container through a pipe and a file inside the container, never a command line, a log or a file on this Mac; `dockingbird.json` records only its kind. A saved `--base-url` is not lent: the trial talks to Anthropic as the platform's does. Harbor installs Claude Code in the task's container at its latest release, over the network, as the platform does; `--ak version=2.1.285` pins it.
- **Trust the task.** The task's image owns its container: as root there it can read the credential, copy it anywhere its network reaches, or write it into the trial's `agent/` folder on this Mac. Run `claude-code` only on a task whose `environment/` you trust, as on the platform. Never pass a credential with `--ae` or `--ve`: it would land on a command line and in the trial's logs; save it with `dockingbird login claude --oauth-token -` or `dockingbird login claude --api-key` instead.
- **What a task may hold.** Dockingbird reads the task before anything runs and refuses what would reach this Mac, naming the file and the key and never a value. A network policy other than `public` in any section is refused (the platform runs tasks open), as is a multi-step or Windows task. The task folder must be one Harbor would run as one task: `environment/`, `instruction.md` and `tests/test.sh` real files and folders, no other `task.toml` in a sub-folder, and no `environment/.env` (compose would read it on this Mac; put the task's variables under `[environment] env`). Its `environment/docker-compose.yaml`, a verifier's `tests/docker-compose.yaml` and each `--extra-docker-compose` file may hold services, builds and networks from a fixed list and nothing else: no host mount (`volumes`), no `ports` (a trial never needs a port on this Mac; `expose` passes), no device, privilege, host network or external or named network, no build path outside the file's own folder (links followed), no `.rego` beside a build's Dockerfile, no YAML alias or tag; a build path or a label may not hold `$` at all, since compose would interpolate it (`$$` is refused there too; elsewhere in the file `$$` is compose's literal dollar); and a label may not hold `com.dockingbird.` or `com.docker.compose.` anywhere. A task whose verifier runs in its own container has its `tests/` checked the same way: no link, no `.env`, the same compose rules. A task's build keeps no `Dockerfile.rego` beside its Dockerfile, and its Dockerfile is no link leading out of its folder. The options Dockingbird refuses, each by name: a mount of this Mac (`--mounts`, `--mounts-json`); an environment class of its own (`--environment-import-path`); a task or dataset it hasn't checked (`-d`, `-t`, `-c` and the git and registry options); `--env-file`, which would change the environment Dockingbird gives Harbor; the classes Harbor runs the job with (`--plugin`, a verifier, a user agent, a bridge); the options that send the job to Harbor Hub or Hugging Face; a device of this computer (`--override-gpus`, `--override-tpu`); and any option it doesn't know at this Harbor commit. A task that asks for more CPUs or memory than Docker's VM has runs anyway, with a line naming `--override-cpus` or `--override-memory-mb`.
- **What is removed.** When a job ends, however it ends (Ctrl-C too: Harbor gets it first and stops its containers, then Dockingbird waits and sweeps), its containers, networks and volumes go, and so does every image the job built that nothing uses, unless `--keep-images`. An image that appeared while the job ran but that the job didn't build (another program's or another Dockingbird folder's, a base image the task pulled, another job's) is never removed, and a line says how many stayed ("Kept 1 image that appeared while the job ran: not made by it."). The job folders stay until `dockingbird harbor clean`, which removes them after one question (`--yes` asks nothing), together with the leftovers of earlier jobs and Harbor's own images (`hb__...`) that nothing holds; `--all` removes Harbor's install too, and the next run installs it again. A job that starts while the question is open is spared, and so is one that is still running. A job killed outside Dockingbird (a crash) leaves its built images until `dockingbird harbor clean`, and a base image a job pulled stays: that, and Docker's build cache, which only `docker builder prune` removes, are the residue. `dockingbird clean --all` names `harbor/` and removes it with the rest.

### Agents your own harness starts: `dockingbird mcp`

`dockingbird mcp` is an MCP server for the harness you work in on this Mac (Claude Code or Codex): through its eleven tools, that harness starts agents in Dockingbird (`agent_start`), sends them messages (`agent_send`; its `reply_required` and `requires_ack` are `send`'s `--reply-required` and `--requires-ack`), reads what they send back (`agent_wait`, `agent_inbox`, `agent_read`, `agent_status`, `agent_list`; the last two show each agent's model and effort, asked beside what its tool reports; `agent_inbox` with `agent` lists what the other agents sent that agent, and `agent_read` reads one of those too), saves their artifacts (`agent_results`, under `results/<agent>/` in Dockingbird's folder), changes a running agent's model or effort from its next turn (`agent_set`, as `dockingbird set NAME` does) and stops one (`agent_stop`, its container only, by its exact id). Your harness starts the server; you never run it yourself. `dockingbird mcp install` connects each harness it finds with that harness's own `mcp add` command and prints the undo; for another harness, or by hand, the server definition is `{"command": "dockingbird", "args": ["mcp"]}` over stdio.

`agent_inbox` and `agent_wait` share the row numbers of `dockingbird inbox` and `dockingbird wait` (Dockingbird keeps them in its `state.json`): a message `agent_inbox` listed counts as seen, so `agent_wait` waits for the next one, and a message one wait told, `dockingbird wait` or `agent_wait`, no later wait tells again.

The server works in the folder your harness runs in. It reads that checkout's `.dockingbird/` configs and the ones `config add` registered once, when it starts, and its instructions name the commands they add, the default first; `agent_start` with no command leaves the choice to Dockingbird, as `dockingbird start` makes it: a new agent runs the checkout's default command, else the default environment, and `agent_start` with the name of an agent that ended continues it as it ran; the reply says which (`applied`), and the agent's `state`, `preparing` until its tool starts (see "Status and stop"). `agent_start` never waits for a toolchain: while the repo's versions still install, it answers `PROJECT_BUSY` with the cause `TOOLCHAIN_FETCHING` at once, the install going on, and your harness tries again; a try after an install that failed gets the failure's words once. The harness can name a command, a task, an agent's name and its tool, never a path, a config's content, a mount or an environment. Everything an agent writes comes back framed as data (`from`, `kind`, `provenance`, `body`, its control characters escaped), and Dockingbird never acts on it; whether your harness does is your harness's own setting. A tool that changes something takes an `idempotency_key` and returns it. A retry with the same key and the same arguments gets the first answer back without running again (a read whose page filled the answer reads again), and the same key with other arguments is refused (`IDEMPOTENCY_CONFLICT`). The server keeps the last `HOST_KEY_OUTCOMES_MAX` (256) answers while it runs and nothing on disk: a retry after an unknown outcome, or after the server restarted, runs the request again, so a message can then arrive twice.

It reaches Dockingbird as `status` does, by `docker exec` into the coordinator, as the host's client session, and it reads no token. `agent_start` first makes Dockingbird ready as `dockingbird start` does, starting Docker and Dockingbird when they are off, and the server's first call of a tool that acts as the client session (`agent_send`, `agent_read`, `agent_artifact_put`) does the same before it opens that session. Otherwise the server never starts Docker or Dockingbird, so while Dockingbird is off its reads say it is unavailable, and `dockingbird sync`, `claude` or `codex` turns it back on.

### What lives where

**`DOCKINGBIRD_HOME`** is Docker mode's folder on your Mac, `~/.local/share/dockingbird` by default. Setting `DOCKINGBIRD_HOME` to another absolute path gives a second, fully separate installation, with its own containers, volumes and image tag (its names end in `-<id>`, where the id is the first hex digits of the SHA-256 of the folder's real path). Choose a path without a space or `%$"'\`: `connect` passes a folder below it to ssh, which cannot take those characters. Dockingbird refuses a `DOCKINGBIRD_HOME` that is `/`, your home folder or a folder above it, one that already holds `operator.token`, `mode.json` or `pg`, and an existing folder with files in it but no marker (the empty `logs/` that `clean --all` keeps, your own `instructions/` and `vaults/` folders, your `versions.toml`, `config.toml`, `browser-solver.json`, `hosts.toml` and `fleet.toml`, and Finder's `.DS_Store` don't count). Any other variable starting with `DOCKINGBIRD_` that no Dockingbird command reads stops the command before it does anything, naming the variable (exit 2); the runtime settings ("Settings", above) and `DOCKINGBIRD_TEST_*` switches pass, and a setting of Dockingbird outside Docker (the database's address and roles, the developer's role switch, the host git's path) stops the command the same way, since Docker mode never uses it.

`--home NAME` before a command runs it in the home `<data root>/homes/NAME`, where `<data root>` is the default home's folder: the first command that claims it (`dockingbird --home lab egress full`, for one) makes the folder, `homes/` above it 0700 and its marker. NAME is lowercase letters, digits and `-`, a letter or a digit first; `--home default` is the data root itself, as no `--home` is. It goes before the command (`dockingbird --home lab status`; after the command, `--home` is the option of `--host`, below, and names a home of that host), and it is refused, exit 2, when `DOCKINGBIRD_HOME` is also set ("--home and DOCKINGBIRD_HOME both name a home; use one of them."), when it is given twice, and when NAME is not such a name. `dockingbird homes` lists the home by that name from then on.

The **marker**, `.dockingbird-home`, is a small JSON file Dockingbird writes first into a new `DOCKINGBIRD_HOME` (0600, never a link). It is how Dockingbird knows the folder is its own: a folder without it is never written, and `clean --all` removes nothing from it.

**Docker's own configuration.** Dockingbird runs every docker command with its own `docker-config/` (0700, its `config.json` 0600), never with your `~/.docker` (or `DOCKER_CONFIG`), so your saved registry logins and your credential helper are never used: a helper that hangs, on a keychain prompt or after Docker Desktop crashed, can no longer freeze setup. Dockingbird needs no login: its image is built from pinned public base images, pulled without your login, and it pushes nothing. From your configuration it copies only `proxies` and `cliPluginsExtraDirs` (and adds your `cli-plugins` folder, where Docker Desktop links buildx), and it reaches the daemon your `DOCKER_HOST`, `DOCKER_CONTEXT` or current context names. Your `proxies` reach every container Dockingbird creates, as Docker's client applies them, and the harness inside it, a user name and password in the proxy URL included (the harness's subprocesses hold them, and Claude's session settings file in the container's private HOME holds them too). Behind a proxy that every connection must use, start with `--egress full`: the egress proxy of `models` and `allowlist` connects to each host directly. It reads your `config.json` and the context's `meta.json` without following a link and within `DOCKER_CONFIG_MAX_BYTES`; if it can't (a symlink, a file too large or not JSON), or the context uses TLS over TCP, docker runs with your own configuration, as before.

**Tool versions.** Claude Code and Codex run from the program store, a Docker volume (`dockingbird-tools`) that holds one folder per downloaded version of each tool. The first `dockingbird claude` (or `codex`, `start`, `login`, or `dockingbird claude -- --version`) that finds no version of that tool downloads the latest release into it and waits for it, with or without `--json`, verifies it (Anthropic's signed manifest for Claude Code; OpenAI's Sigstore bundles and published digests for Codex), checks that it starts and prints its version, and only then runs it; the line "Getting Claude Code 2.1.296 ..." shows while it downloads. A later start runs the version it has; `dockingbird update` fetches the latest of each tool you have used, after its rebuild, and says so ("Claude Code 2.1.296 is the latest." or "Got Claude Code 2.1.296."). To choose a version yourself, `dockingbird pin claude 2.1.285` (or `codex 0.162.1`) writes `versions.toml` in `DOCKINGBIRD_HOME`, one line per tool, which you may also edit by hand; `dockingbird pin --clear claude` follows the latest again. A line is `claude = "2.1.285"` or `codex = "0.162.1"` (a version Dockingbird then downloads if it does not have it; it is never changed by a start or an update, and `dockingbird --version` shows it as pinned: "Claude Code 2.1.285 (pinned)"; `dockingbird status NAME` shows the version that agent runs); `"latest"`, or removing the line, returns the tool to the latest release, and `"stable"` is Claude Code's slower channel. A line that is not one of those, an unknown key or a file that is not plain TOML of yours stops the command and names the line ("versions.toml: the claude line isn't a version, latest or stable."), so a pin you wrote is never silently ignored. A config you added with `config add` can pin its own tool instead, `version = "2.1.285"` at its top level or in one of its commands; a repo's own config can't (`dockingbird -h` and `dockingbird config list` say that `version` works only in a config you add, and a start of its commands says to add the config first). A download that fails verification is never installed and is said out loud; a version that does not start is set aside until `update` ("Claude Code 2.1.296 didn't start, so Dockingbird keeps 2.1.285."), unless you pinned it, in which case it runs anyway. Nothing in the store is ever run by the container that downloads it, and every other container mounts the store read-only. Every start that follows a channel asks it first, with one small conditional request from your Mac (at most `TOOLS_CHECK_TIMEOUT_S`, no credential, no redirect followed; a 304 means nothing new): when it names a newer version, a start waits for the download up to `TOOLS_FOREGROUND_WAIT_S`, at a terminal with a live line ("Getting Claude Code 2.1.296  [########........]  45 MB of 89 MB", then "Getting Claude Code 2.1.296 (89 MB) ... done (12 s)"), and past that runs the version you have ("Still getting Claude Code 2.1.296; this start uses 2.1.285. The next start uses the new one.") while the download goes on in its own container; when the download it waited for is another command's (an `update`, or a start in another terminal), the line says so and the next start checks again ("Another command is getting Claude Code 2.1.290; this start uses 2.1.285. The next start checks again.", or, before that download has named its version, "Another command is getting the latest Claude Code; this start uses 2.1.285. The next start checks again."); an agent your own harness starts over MCP (`dockingbird mcp`), the one start that doesn't wait, runs the version you have at once, or, with none yet, is refused as busy, to be tried again ("Claude Code is being downloaded; try again in a minute.", `PROJECT_BUSY` with cause `TOOL_FETCHING`). Every start from the command line, at a terminal, on the bus and with or without `--json`, always waits for a first download and for a version you pinned, up to `TOOLS_FETCH_TIMEOUT_S` (15 minutes); a script or agent that gives `dockingbird start` a timeout of its own shorter than that should run `dockingbird claude -- --version` (or `codex`) once first, which waits for the same download with its progress lines, and start after it; an agent started over MCP is refused that same way for both. When the check gives no answer (offline, a TLS or DNS failure), the version you have runs and only `--verbose` says why; a channel never moves a tool to a version below the one you have. A download that finished after its start gave up waiting is picked up by the next command that needs that tool, or by the sweep of the next start, `sync`, `stop` or `clean`, and checked before it runs; `dockingbird --version` reads only what Dockingbird recorded and asks Docker nothing, so it names a version once the start that waited for it has finished, and a download another command left going (an agent started over MCP, or a start past its wait) only once one of those commands has picked it up; a download container left running past `TOOLS_FETCH_TIMEOUT_S` is stopped and removed, and `stop` stops one in progress. Unused versions are removed after a download, by `update` and by `dockingbird clean` (the store keeps every version a container uses, in any state, the current and pinned ones, one previous version for an instant rollback, and the one being started).

**Docker volumes**, never on your Mac: `dockingbird-state` (PostgreSQL, the broker's socket, tokens, the agents' protected copies of each linked branch and every agent's own copy), `dockingbird-tools` (the program store: each downloaded version of Claude Code and Codex, see "Tool versions"; mounted read-only into every container that runs a tool and read-write into the short-lived tools container alone), `dockingbird-home-claude` and `dockingbird-home-codex` (each tool's credentials store, its `.dockingbird` with the saved key and your rules' copy; mounted into the coordinator at `/dockingbird/home/<tool>` and into the login, tool-help, put and seed containers, never into an agent, which gets its secrets from the coordinator at its start), and `dockingbird-browser-sock-<name>`, one per agent whose config asks for a browser (the socket folder the agent's browser container and the agent's container share; made before the browser container, removed once the agent's container is gone, and swept with the other leftovers when a start was cut short).

**Containers**, all from one locally built image (Ubuntu 24.04, git 2.43, PostgreSQL 18, with PostgreSQL 17's programs kept for one release for the upgrade, Python 3.12.14 (the agents' `python3`, `python` and `python3.12`, and the base of Dockingbird's own venv), the C and C++ build tools, Node.js 24, Go 1.27, ripgrep 15.2.0, ast-grep 0.51.0 and gopass 1.17.4, the password manager the coordinator reads the vaults with; Claude Code and Codex come from the program store, see "Tool versions"), all unprivileged (`--cap-drop ALL`, `no-new-privileges`; the coordinator, agent, proxy and login containers also with a read-only root file system):
- `dockingbird-coordinator`, with `--network none`: PostgreSQL, the broker and the worker that runs the connections' fetches and pushes, and the only container that holds the operator token and the copies of your connections' keys and, after `connect --agent`, your Mac's ssh-agent socket, which Docker Desktop forwards and which the coordinator joins the root group to open; the only container that mounts `DOCKINGBIRD_HOME/vaults` (read-only, at `/dockingbird/vaults`; each start makes the folder 0700 and refuses to start when it can't, or when a link or a file is in its place); its one way out is SSH to the hosts of the connections you registered, through the relay;
- `dockingbird-relay`, while a connection exists, on Docker's default bridge: `dockingbird-relay` carries the agents' fetches and pushes to the hosts you connected; it stays up after Dockingbird's idle stop, until `dockingbird stop` or `dockingbird clean --all`. It carries the coordinator's SSH bytes to each connection's host and port and nowhere else, over Unix sockets in the state volume's `relay/` folder, which no agent mounts; it listens on no TCP port and holds no key;
- `dockingbird-agent-<name>`, one per running agent, on its own network, `dockingbird-net-<name>` (internal, with its proxy beside it, under `allowlist` and `models`; an ordinary bridge with NAT under `full`, the default; none under `--egress none`): its own copy, its repo's protected copy (read-only), its own token (read-only) and log, the broker's socket folder (read-only) and the program store (read-only, see "Tool versions"); no tool's credentials volume (it asks the coordinator for its tool's secrets at its start). No agent has a bind mount but the folders you connected, read-only;
- `dockingbird-proxy-<name>`, one per agent under `allowlist` or `models`: Stripe's Smokescreen, pinned by its checksum, started by the image's own `egress` command from a short policy (the hosts it admits and the refusal message, in the container's one variable), with the agent container's hardening, no mount, no published port and no health check, on the agent's network and on the shared `dockingbird-out` bridge;
- `dockingbird-browser-<name>`, one per agent whose config asks for a browser (`browser = "chrome"`, in an added config): the agent's browser on a virtual screen, in its own container from the image's browser stage, on the agent's network and behind its proxy under `allowlist` or `models`, started and waited for before the agent's container is created and stopped and removed after it; the agent's container reaches it only through the socket volume `dockingbird-browser-sock-<name>`, which both mount, and no port is published;
- short-lived login, put and seed containers, and the help run of `dockingbird claude -- --help`;
- `dockingbird-tools-<tool>`, the short-lived container that downloads, verifies and installs a version of that tool into the program store (on the default bridge, the store read-write and its own `/tmp` volume, nothing else mounted; one per tool at a time), and the check run that starts a freshly installed version with `--network none` and the store read-only to compare its version line.

Every object carries the labels `com.dockingbird.profile=<id>`, `com.dockingbird.kind` and `com.dockingbird.version` (agents also `com.dockingbird.session`, `com.dockingbird.metrics-port` and `com.dockingbird.metrics-path`, the port and path the agent's supervisor serves `GET /metrics` on inside the container), and Dockingbird finds and removes its own objects by those labels, each by exact id. The image also carries `com.dockingbird.commit`, the commit the installed package was built from when it came from git (`docker image inspect` shows it, and `dockingbird --version` names the same commit): a reinstall of the same bytes keeps the image and its label, so the label names the commit that built that image. Your checkout gets one line per linked branch in `.git/config`, `branch.<branch>.dockingbird`, which `git branch -m` moves with the branch (status, `stop`, the start's refusals and `clean --all` follow the rename at once, by that line; the next start on it records it) and `clean --all` removes from whichever branch holds it, and, from the first start on a branch, `refs/remotes/dockingbird/<branch>`: the head the agents' copy started from, then their commits as of your last sync, which `clean --all` removes too. `git branch -d` removes the line with the branch but leaves that ref, so every step for a copy or commits kept on that branch says it is "no longer in your checkout" and makes it again first: "git switch -c feature/x dockingbird/feature/x, then dockingbird claude --as NAME" ("git switch -c feature/x" when the ref is gone too); the start, and `dockingbird sync`, then link it again ("Linked myapp (feature/x) to its agents' copy again."). A new branch you make under a deleted branch's name is never linked to that branch's agents' copy unasked: when that copy has commits the new branch lacks, the start and `dockingbird sync` ask first ("myapp (feature/x) has the name of a branch you deleted.", those commits, then "Carry on from them here? [y/N]"; picking up an agent whose work is kept on the branch you deleted, `dockingbird claude --as keep9`, names it first: "keep9's work is on the feature/x you deleted." and "Carry on from them here, and pick keep9 up? [y/N]", and its no says "Nothing linked; keep9's work stays kept."), and `status`'s heading says so ("has a deleted branch's name, so sync asks first: dockingbird sync"), as does sync's line about it after a sync on another branch. Yes links it and goes on as before (the start's and sync's own merge questions included); no, the default, or Ctrl-C links, starts and syncs nothing, and without a terminal (or with `--json`) nothing is linked either. To keep the new branch apart, rename it (`git branch -m feature/x NEWNAME`, as the no says): no link line names it yet, so the next start gives it its own copy (the start's no says "rename it, then run this again"; sync's says only to rename, since sync on the renamed branch has nothing to take). A checkout cloned again at the same place, a branch made from the agents' ref as above, and one that already has the agents' commits are linked without a question. Once linked, `git branch -m` keeps the link.

### Egress and what stays open

- **Egress, by mode.** `--egress MODE` on `dockingbird claude`, `codex` and `start`, or `egress` in a config (which a flag can't change), picks how far an agent reaches; with neither, the installation default applies (`dockingbird egress` shows and sets it; Dockingbird's own is `full`, no limit). `allowlist` reaches its tool's own hosts (the model API and the sign-in), the hosts of its presets (`registries`: the package registries of the ecosystems GitHub's recommended allowlist names, npm and Yarn, PyPI, crates.io, the Go module proxy and checksum database, RubyGems, Maven Central and the Gradle plugin portal, NuGet, Packagist and pub.dev, and Hex; `github`: `github.com`, `api.github.com`, `codeload.github.com` and `*.githubusercontent.com`) and the hosts of its config's `allow`, through a proxy container of its own, and nothing else. `models` reaches its tool's own hosts alone. `none` has no network at all, the model API included. `full` is the agent's own network with NAT out and no proxy, as every agent had before, and, with the connectors off, nothing of your accounts. `full` is the default, so a hijacked agent can send out the repo it works on and its own Docker sign-in or key to any host. `dockingbird egress allowlist` closes that for the agents you start from then on: with the registries and GitHub allowed (its list when you give no `--allow`), installing dependencies and reading GitHub's content still work, while sending something out needs a credential the agent does not hold.
- **Your claude.ai connectors never load in an agent.** Claude Code fetches the connectors of a claude.ai login (Gmail, Drive, Calendar and the rest, which act with your own accounts) at every start; the image's managed settings turn that off (`disableClaudeAiConnectors`), in every mode, `--egress full` included, and a repo's or an agent's own settings cannot turn it back on. An agent gets a document by `send`'s `--file` or an artifact, never through your accounts. That holds from Claude Code 2.1.273 (2.1.290 for a trusted repo's own MCP entries); the default channel is past both, so only a pin you write to an older one can let them load, on a Team or Enterprise login.
- **An agent's Claude Code runs with background sessions and agent view off.** Every Claude agent starts with `CLAUDE_CODE_DISABLE_AGENT_VIEW=1` and with `disableAgentView` set in the settings Dockingbird writes, so `claude agents`, `--bg`, `/background` and the background-session supervisor are off in its screen and a repo's or an agent's own settings cannot turn them back on: an agent's screen is the one session Dockingbird feeds and updates in place. The image's managed settings take the same key at the next image build.
- **What a blocked host sees.** A host outside the list gets the proxy's `407` and a message that names Dockingbird and the way out ("Dockingbird's egress proxy refuses with 407 a host that is not in the allow list or whose address is not public, and a request that names an upstream proxy of its own: allow a public host with allow in the config, or start with --egress full. A host in the list whose name does not resolve, or that does not answer, gets 502, 504 or 500 instead."), so a tool fails with its own proxy-refused error and not a timeout. A host in the list whose name does not resolve gets the proxy's `502` (`Failed to resolve remote hostname`, the same message appended), as the lookup would fail anywhere. TLS is never opened: the proxy tunnels the connection and sees the host name and the port and nothing inside it, and the tool's own certificate check runs against the real server.
- **In `allowlist` and `models`, a tool that ignores the proxy fails; it does not get around it.** Its network has no route out, no gateway and no IPv6, and its only resolver, Docker's, answers the names of containers on that network and no outside name, so a lookup meant to carry data out gets no answer either. A connection to an IP address or an IPv6 literal, and any other traffic (UDP, QUIC, ping), has no route, or is refused at the proxy.
- **A name whose address is not public is refused whether or not it is allowed.** The proxy refuses every address that is not public: a connection to the Mac, your LAN, `host.docker.internal`, Docker's own ranges or another agent's address gets the same `407` and message, and so does a name in the list that resolves to one of them (`allow = ["host.docker.internal"]` resolves to a private address and is still refused); `--egress full` is the way to reach them. The one exception is an agent started with a local model (`local_model` in a config you added): its own proxy admits `model-runner.docker.internal` on port 80, at the addresses that name resolves to when the proxy starts, and no other agent's proxy does. Under `full` there is no proxy, so an agent's own browser (`browser = "chrome"`) reaches this Mac's loopback services through `host.docker.internal` as any `full` agent can; a browser agent that must not reach them uses `allowlist` or `models`.
- **What the list does not limit.** An entry names a host, not a port: an admitted host is open on every port. A host you allow is a host the agent can post to, so allow only hosts you would let it send the repo to. A `*.` entry (`*.corp.example`) admits every name under that domain: the agent picks the name it asks the proxy for, and the proxy's lookup of it reaches that domain's own nameservers. An internationalized name (an `xn--` label) is not admitted this round; an `allow` entry holding one is refused when the config is read.
- **What widens or narrows it.** Add hosts with `allow` in a config (`allow = ["registries", "github", "docs.python.org"]`) and change one start with `--egress`. A proxy mode needs Docker Engine 28 or later, for the agent's network's isolated gateway (`gateway_mode_ipv4=isolated`), and Dockingbird checks no version: Engine 27 refuses the network's create with Docker's own error (shown as `EGRESS_PROXY_FAILED`), and Engine 26 or older ignores the option, so the agent's internal network keeps an address on the Docker host, where the agent can reach what listens on that host outside the allowed hosts. Update Docker Desktop before using a proxy mode on an older Engine; `full` works on any. About 30 networks fit in Docker's default address pools, shared by every Docker network on the computer (this home's agents, another `DOCKINGBIRD_HOME`'s and other programs'): a start that finds no range left, in any mode, is refused with `START_NETWORK_POOLS_FULL`, which names the steps (`docker network ls` lists the networks; `docker network prune` removes every network no container uses, other programs' included; or give Docker more pools with the Docker Engine setting `default-address-pools`). The start's sweep has already removed this home's unused networks, so Dockingbird has nothing more to free. Behind a proxy that every connection must use, only `--egress full` works (see "Docker's own configuration"). A project config in a checkout you marked untrusted can only narrow (`none`, `models`, or a list the default already covers); anything wider is refused with the step `dockingbird trust`. Set the default for new agents with `dockingbird egress`.
- **The default for new agents, `dockingbird egress`.** `dockingbird egress` shows what the agents you start from now on may reach, and whether `egress.toml` in Dockingbird's folder sets it or it is Dockingbird's own default. `dockingbird egress models` or `dockingbird egress allowlist --allow docs.python.org` sets it for this Mac (an `allowlist` with no `--allow` takes the presets `registries` and `github`, and one with entries is exactly them, besides the tool's own hosts), and `dockingbird egress --reset` removes the file. A config's own `egress`, or the flag on a start, still wins for that agent, and an agent you pick up again keeps the mode its last start ran: the default is for new agents. A file that cannot be read as the command writes it (not TOML, another key, a mode or an entry outside the grammar, or no regular file of yours) refuses every start with the file and the key named, and `dockingbird status` and `dockingbird egress` say so in place of the default; none of them ever falls back to Dockingbird's own default, `full`. `dockingbird egress --reset` removes the damaged file and a new mode writes over it; a folder at that name is the one thing both refuse (they say so), so you remove it yourself and run the command again.
- **An agent can read its own credential**: its tool's sign-in, or the saved key, which it can read but not change. That is inherent to running the tool. It is a Docker-only sign-in, so nothing an agent does touches your Mac's own sign-in. A saved API key (`dockingbird login claude --api-key`, or `codex` for Codex) is checked with its provider before the tool starts, through the agent's own proxy in `allowlist` and `models` and directly in `full` (`none` has no network, so nothing is checked there), so a key the provider refuses is refused in seconds ("its provider refused the saved Claude key"), never after the tool's own timeout; a gateway the proxy's list does not name is refused there, for the check as for the tool.
- **The shared credentials store.** Any agent of a tool can corrupt, replace or delete that tool's store, hold its lock or Claude's lease (a denial of service the next start names), or swap later sessions onto another account. Its harness HOME is private, so planted settings, hooks or plugins never load in another agent.
- **Resume carries the earlier run's files.** A resumed copy gets its `.git/config` and hooks reset, but not its files, so a hostile earlier run under the same name can leave content the next one reads (prompt injection, not code execution on your Mac).
- **Filling the disk.** An agent can read its repo's whole history and fill its copy, its `/tmp` volume or Docker's disk. `clean` frees it, and a start offers to when Docker is almost out of space. Dockingbird sets no process limit on its containers, and no CPU or memory limit unless you give one (`--cpus`, `--memory`): Docker's own limits apply beyond that.
- **Compilers and runtimes in the image** add no privilege: they run as your uid on a read-only root, nothing in them is setuid, and an agent could download the same tools itself; what the image adds is that they are pinned and checked at build.
- **Holding a lock, keeping Dockingbird awake.** An agent can flock its read-only protected copy or the socket folder, blocking its repo's shares or a broker restart, and an agent that stays alive keeps Dockingbird from its idle stop. `dockingbird stop claude-1` ends it.
- **Agents cannot reach each other except through Dockingbird.** Each is on a network of its own that no other agent joins. The proxies share one NAT bridge, but a proxy refuses every address that is not public, another proxy's among them, so two agents have no channel through it. Their one channel is the message bus (`bus_send` with `to=<name>`, "Between agents" above), which the coordinator checks and you can read.
- **Trust answers.** An agent can edit the remembered trust answers in its tool's state. That grants nothing: the repo's own layers load only with the coordinator's `trusted` file on the read-only config mount, written from the checkout's mark on this Mac (every checkout is trusted unless you ran `dockingbird trust --off` in it), and only for a tool in `PINNED_HARNESSES` (both today), whatever the agent's tool remembers.
- **Your git after sync.** Sync's protections cover sync's own git calls. Your later git commands in that checkout apply the agents' `.gitattributes` with your configured filters; sync says when that file changed and shows the new lines. Review stays yours, as with any pull request.
- **Same uid everywhere.** Every container runs as your uid. The isolation between the coordinator and the agents is what each container mounts, not the uid.
- **Prompt injection** through repo content is not addressed. The rules only make the coordination tools the path of least resistance.
- **The coordinator.** The coordinator has no network but SSH to your connections' hosts, through the relay; an agent can ask it for a fetch or a push of its connection's branch, never for the key, and a hijacked coordinator could reach every repository the copied key reaches.
